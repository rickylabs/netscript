# oRPC v2 readiness and migration strategy

> **Draft evaluation notice.** This document is a **Draft** evaluation RFC produced for technical review. It does not authorize implementation, dependency, or lockfile changes under `packages/`, `plugins/`, `docs/site/`, `.github/`, `deno.json`, or `deno.lock`. Every statement about current NetScript or oRPC behavior below is tagged as **source-inspected** or **measured** (baseline inventory refreshed to `origin/main` `00325a531` with `@orpc/*@^1.16.6` and Deno `2.9.8`; historical `87965d800` / `^1.15.5` / `1.16.5` throwaway `2.0.0-beta.53` prototype measurements preserved in `.llm/runs/plan-rfc-orpc-v2-readiness-2672--rfc/evidence/v2-beta53-prototype-summary.md`; standalone probes in `probes/v2-behavior-probes.ts` verified on `1.16.6` vs `2.0.0-beta.53` under Deno `2.9.8`); proposed architecture and migration steps are tagged as **derived**. Phase 0a targets milestone `0.0.10`; Phase 2 (oRPC v2 GA cut-over) targets `0.1.0`. Companion pipeline evaluation: draft PR #2673 (tracking issue #2671).

## Summary

NetScript's contract, service, SDK, telemetry, logging, plugin, desktop RPC, and CLI scaffolding layers depend on `@orpc/*@^1.16.6` across **181 non-`.llm`, non-lock files** on `origin/main` (`00325a531`, after `#2690` moved the workspace from `^1.15.5` to `^1.16.6` and `#2689` pinned Deno `2.9.8`; **source-inspected**). Upstream oRPC v2 is in beta (`2.0.0-beta.53`, 2026-11-23) and introduces pervasive breaking changes—including **silent data/runtime hazards** verified empirically against `1.16.6` vs `2.0.0-beta.53` in `probes/v2-behavior-probes.ts`: mixed v1/v2 RPC calls silently mis-decode `bigint` (`10n` → `"10"`) and degrade error messages; default `RPCHandler` rejects `GET` (breaking NetScript's 52 declared `GET` procedures); `StandardHandlerPlugin.init` requires returning options AND renaming `rootInterceptors` → `routingInterceptors` (while v1 `StandardHandler` ignores `routingInterceptors`, so switching before `0.1.0` breaks v1!); unmapped error codes flip from HTTP `500` to `400` (while a naive unknown-code Proxy without upstream `COMMON_ERROR_STATUS_MAP` overwrites built-in `PAYLOAD_TOO_LARGE` `413` and `TOO_MANY_REQUESTS` `429` to `500`!); `ORPCError` ignores constructor `defined: true` and removes `status`; middleware deduplication is removed (running router+procedure middleware twice); and default `RPCLink` follows cross-origin `307` redirects, leaking custom headers, `traceparent`, and bodies. Prototyping an unmodified bump to `2.0.0-beta.53` in a throwaway worktree (historical `87965d800` snapshot, **measured**) produced **411 raw diagnostics across 13/13 target groups** (186 raw diagnostics across the 11 core/plugin-core groups deduplicate to **99 unique sites in 25 files**, roughly half of which are `.route()` calls). We recommend a **staged, split-Phase-0 readiness strategy** (**derived**): **Phase 0a** (`0.0.10`, safe once authorized on current `^1.16.6`: `@orpc/*` workspace catalog consolidation via `package.json` `"catalog:"` while preserving the standalone `desktop-native` fixture import map + updating isolated e2e frozen-lock tests off `1.15.0` with a distinct absent rejection requirement + `@orpc/*`-scoped CI catalog check, pruning stale `1.15.0` root lock entries, moving `ORPCError` off `@orpc/contract`, plugin `name`/return-`init` keeping runtime attachment on `rootInterceptors` behind a NetScript helper + real-`RPCHandler` tests, additive `getErrorHttpStatus` + relaxed `DefinedErrorLike`, server-only `X-NetScript-RPC-Protocol` readiness with CORS wrapping `426` and v2-encoded `CLIENT_PROTOCOL_UNSUPPORTED` without emitting any new v1 client header in `0.0.10`, and `redirect: 'error'`); **Phase 0b** (`0.0.11`, held until accepted: TanStack `streamedKey`/`streamedOptions`/`liveKey`/`liveOptions`/`fnOptions` aliases, v1-compatible `accessMeta`/`policyMeta`/`defineContractErrors` while explicitly retaining `.route(...)` on v1 `0.0.x` until `0.1.0`, and RFC A Stage 1b); **Phase 1** (maintained `chore/orpc-v2-shadow` branch running weekly CI against latest beta/RC); and **Phase 2** (`0.1.0` after `@orpc/*@2.0.0` GA, shipping breaking v2 `CORSPlugin` tightening, `X-NetScript-RPC-Protocol: orpc-v2` client emission + CORS-wrapped `OPTIONS`-exempt `426` guard with wire-compatible error envelopes, `routingInterceptors` flip, `COMMON_ERROR_STATUS_MAP`-seeded `500` unknown-code normalization, server-free `routeMeta` cut-over, contract `GET`/`HEAD`/`PUT`/`PATCH`/`DELETE` parity, and RFC A Stage 2, while keeping `release/orpc-v1` on `0.0.12+` for 90 days post-GA).

## Motivation

### Why evaluate oRPC v2 readiness now? (**source-inspected** & **measured**)

1. **Wide surface coupling & manifest drift:** `@orpc/*` spans **181 non-`.llm`, non-lock files** across 18 workspace groups plus 5 RFC files on `origin/main` (`00325a531`, up from 179 files on historical `87965d800` after RFCs 0009 and 0010 merged). Although `#2690` updated root `deno.json` `"catalog"` to `^1.16.6`, **11 workspace `deno.json` manifests** and inline workspace test specifiers (`packages/cli/e2e/src/application/gates/scaffold/prepare-flow-b-fixture.ts`, `packages/sdk/tests/type-fixtures/service-query-utils-upstream_type.ts`, `packages/sdk/tests/client-contribution-observability_test.ts`, `packages/cli/src/kernel/templates/aspire/helpers/tests/installation-provisioning_test.ts`) still bypass `package.json` `"catalog:"`, `packages/contracts/package.json` still carries an unused `"@orpc/server": "catalog:"` entry, standalone `packages/cli/e2e/fixtures/desktop-native/` carries a shipped standalone import map + frozen lock that must remain explicit and version-synced, and root `deno.lock` still retains stale `1.15.0` entries for `@orpc/client` and `@orpc/tanstack-query` (plus transitive `1.15.5` deps of `1.15.0`), already flagged as `WARN DEPS-NPM-CATALOG` by `.llm/tools/deps/scan-npm-catalog-compliance.ts`.
2. **Silent security, data-integrity, and observability traps on v2 (**measured** in `probes/v2-behavior-probes.ts` on `1.16.6` vs `2.0.0-beta.53`, Deno `2.9.8`):**
   - **Silent mixed-version RPC corruption (B1):** A `1.16.6` `RPCLink` calling an unguarded `2.0.0-beta.53` `RPCHandler` succeeds on plain JSON calls, **silently delivers `bigint` `10n` as the string `"10"`**, and degrades custom error messages (`"nope"` → `"Not Found"`). Stale browser tabs, cached Fresh islands, and installed desktop clients cannot upgrade atomically with servers; meanwhile a naive bare-JSON `426` guard placed outside CORS causes cross-origin browsers to drop the response (`Access-Control-Allow-Origin` missing) and causes `1.16.6` `RPCLink` to decode `MALFORMED_ORPC_ERROR_RESPONSE` and v2 `beta.53` to throw `MalformedResponseError`.
   - **GET-first queries break on cut-over (B2):** NetScript's SDK issues `GET` for every procedure declaring `method: 'GET'` (**52** first-party contract/template declarations across 25 files, plus CRUD `list`/`get`), driving `DedupeRequestsPlugin` and `force-cache` groups. Default `RPCHandler@2.0.0-beta.53` returns `matched: false` (404) for `GET`.
   - **Silent interceptor, error-status, and middleware-dedup regressions (B4):** `LoggingPlugin` and `TracingPlugin` push to `rootInterceptors`, which compiles against NetScript's structural `GenericHandlerOptions` while silently dropping all request logs and root spans on v2 (`routingInterceptors`); server-side `error.status` readers misclassify client errors as server errors; unmapped error codes flip from HTTP `500` to `400` (while a Proxy fallback not seeded from `COMMON_ERROR_STATUS_MAP` clobbers built-in `PAYLOAD_TOO_LARGE` `413` and `TOO_MANY_REQUESTS` `429` to `500`); `new ORPCError(..., { defined: true })` is ignored (`plugins/auth/services/src/routers/v1-handlers.ts:97`); and router+procedure middleware runs **twice** (charging RFC A quotas twice).
   - **Cross-origin `307` redirect leakage (B7):** Removing `redirect: 'manual'` causes v2's default `RPCLink` to follow a cross-origin `307`, leaking custom headers (e.g., `x-api-key`), `traceparent`, and the full request body to the foreign origin and returning its response as the RPC result; meanwhile `redirect: 'manual'` silently resolves with `undefined`.
3. **Co-design with companion RFC A (PR #2673 / issue #2671):** Aligning RFC A's Stage 2 (`createRouterClientTransport`) and HTTP-edge v2 matcher (`RPCMatcher` + `OpenAPIMatcher`) with RFC B's `0.1.0` v2 GA cut-over avoids forcing downstream applications through two separate migrations.

## Guide-level explanation

> **Derived design.** All TypeScript idioms below are **type-valid** against `@orpc/*@2.0.0-beta.53` (and v1 `0.0.11` guidance is verified against `@orpc/*@1.16.6` in `probes/v2-behavior-probes.ts`). Note that oRPC contract builders (`oc`, `baseContract`) have **no `.use()` method** on v1 or v2. On **v1 (`0.0.x` / `@orpc/contract@^1.16.6`)**, callers **MUST retain `.route(...)`** until the `0.1.0` cut-over (because `.meta(...)` on `1.16.6` does not populate native `~orpc.route`, causing `inferRPCMethodFromContractRouter` to send `POST` for declared `GET` procedures!); `accessMeta`, `policyMeta`, and `defineContractErrors` can be adopted safely on `0.0.11`. At **`0.1.0` (v2 GA)**, routes and metadata are composed via server-free, browser-safe `.meta(routeMeta(...))`, `.meta(accessMeta(...))`, and `.meta(policyMeta(...))` helpers backed exclusively by `@orpc/contract` `defineMeta` (keeping `@netscript/contracts` strictly free of `@orpc/server` and `@orpc/openapi` runtime dependencies!).

### Contract authoring

**Phase 0b (`0.0.11`, v1 `^1.16.6`) — retain `.route(...)` alongside additive metadata/error helpers:**

```ts
import {
  accessMeta,
  baseContract,
  defineContractErrors,
  policyMeta,
} from '@netscript/contracts';
import { z } from 'zod';

export const orderErrors = defineContractErrors({
  ORDER_LOCKED: { status: 409, message: 'Order is locked', data: z.object({ orderId: z.string() }) },
});

// On v1 (`0.0.x`), retain `.route(...)` so `inferRPCMethodFromContractRouter` preserves GET!
export const getOrder = baseContract
  .route({ method: 'GET', path: '/orders/{id}' })
  .meta(accessMeta({ authentication: 'required', authorization: { scopes: ['orders:read'] } }))
  .meta(policyMeta({ cache: 'force-cache' }))
  .errors(orderErrors.definitions)
  .input(z.object({ id: z.string() }))
  .output(z.object({ id: z.string(), totalMinor: z.number().int() }));
```

**Phase 2 (`0.1.0`, v2 `^2.0.0`) — server-free `routeMeta` + exact-key `accessMeta` & `policyMeta` (automated by `netscript migrate orpc-v2`):**

```ts
// `@netscript/contracts` imports ONLY `@orpc/contract` and `zod` (browser-safe; zero `@orpc/server` dependency!).
// `routeMeta` writes `'~openapi'` (read natively by `@orpc/openapi` `getOpenAPIMeta` & `OpenAPIGenerator`),
// `accessMeta` writes `'access'` (`meta.access`), and `policyMeta` writes `'policy'` (`meta.policy`).
import {
  accessMeta,
  baseContract,
  defineContractErrors,
  policyMeta,
  routeMeta,
} from '@netscript/contracts';
import { z } from 'zod';

export const orderErrors = defineContractErrors({
  ORDER_LOCKED: { status: 409, message: 'Order is locked', data: z.object({ orderId: z.string() }) },
});

export const getOrder = baseContract
  .meta(routeMeta({ method: 'GET', path: '/orders/{id}' }))
  .meta(accessMeta({ authentication: 'required', authorization: { scopes: ['orders:read'] } }))
  .meta(policyMeta({ cache: 'force-cache' }))
  .errors(orderErrors.definitions)
  .input(z.object({ id: z.string() }))
  .output(z.object({ id: z.string(), totalMinor: z.number().int() }));
```

*(Transitional opt-in at `0.1.0`: server-only packages that temporarily wish to keep `.route(...)` syntax may import `'@orpc/openapi/extensions/route'` directly in their own runtime entrypoint, noting that `dist/extensions/route.js:3` imports `@orpc/server` at runtime and requires side-effect evaluation before any `.route()` call.)*

### Client error handling & TanStack Query v2 names

```ts
// Import error helpers from `@netscript/sdk/client` (never re-exporting raw ORPCError class per RFC 0001).
// Note: `getErrorHttpStatus(err)` reads `ResponseError` (and `MalformedResponseError`) on HTTP;
// returns `undefined` on MessagePort & router-client!
import { getErrorHttpStatus, safe } from '@netscript/sdk/client';

const res = await safe(client.getOrder({ id }));
if (!res.isSuccess && res.isDefined) {
  console.log(res.error.code, getErrorHttpStatus(res.error));
}

// TanStack Query v2 names (verified in `@orpc/tanstack-query@2.0.0-beta.53/dist/procedure-utils.d.ts`):
// `streamedKey`, `streamedOptions`, `liveKey`, `liveOptions`, `fnOptions`.
const streamed = queryUtils.watchOrders.streamedOptions({
  input: { tenantId },
  fnOptions: { refetchMode: 'append', maxChunks: 200 },
});

// Replacing v1 `refetchMode: 'replace'` (do NOT blindly switch to `'reset'`, which clears data immediately!):
// Use a custom `queryFn` that buffers incoming chunks and resolves the replacement array on completion.
```

#### 4.2 Blocker B1 + N1 decision: Mixed v1/v2 RPC protocol guard, CORS-wrapped `426` wire contract, real-link decoding & blue-green preflight path (**measured** Probe B1)

- **Middleware / plugin ordering — CORS ALWAYS wraps the protocol guard (and non-RPC routes stay untouched):**
  - **Inside `createService` (`withCors()`):** `createServiceCorsMiddleware` (`packages/service/src/middleware/service-cors.ts:59-94`) runs as outer Hono middleware around `wireRpc()`. Do **not** silently mutate `resolveServiceCorsOptions()` (`service-cors.ts:23`) globally for non-RPC routes (`/raw`, `/health`, `/api/*` OpenAPI): keep explicit `allowHeaders` exact on non-RPC routes, and append `'X-NetScript-RPC-Protocol'` (case-insensitively deduplicated) **strictly on RPC-path `OPTIONS` preflights** (`rpcPath` / `rpcAliases`, default `/api/rpc/*`). On RPC requests, `createServiceCorsMiddleware` handles `OPTIONS` → `204` and restores all 6 `Access-Control-*` headers + `unionVary` onto BOTH `200` and `426` responses returned by `rpcHandler`.
  - **Standalone `createRPCHandler` (outside `createService`):** Never reject `426` in a wrapper *before* standalone CORS! Instead mount the protocol guard as an oRPC handler plugin running **inside** CORS (strictly on `RPCHandler`, never on `OpenAPIHandler`):
    - On **v2 (`0.1.0`)**: `ProtocolGuardHandlerPlugin` declares `name: 'netscript-rpc-protocol-guard'` and **`before: ['~cors']`** so `CORSHandlerPlugin` (`name: '~cors'`) prepends its `corsHeadersInterceptor` and `preflightInterceptor` *outside* the protocol guard's `routingInterceptor` (while keeping `if (request.method === 'OPTIONS') return next()` inside the guard as defense-in-depth when `CORSHandlerPlugin` is absent).
    - On **v1 (`0.0.10`)**: `ProtocolGuardPluginV1` registers at **`order: 0`** (below v1 `CORSPlugin.order = 9e6`) so `CORSPlugin` unshifts its CORS headers & preflight interceptors *outside* the guard.
  - Result (verified in Probe B1): cross-origin browsers receive `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials` (when enabled), and merged `Vary: X-NetScript-RPC-Protocol, Origin` on RPC **`204` preflights, `200` responses, AND `426` rejections** — never an opaque CORS network error, and never mutating non-RPC routes!
- **Wire-compatible `426` error envelopes & defined stale-client behavior:**
  - `@orpc/client@1.16.6` `isORPCErrorJson` requires `{ defined, code, status, message, data }` inside `{ json: ... }` (decoding bare JSON `426` as `MALFORMED_ORPC_ERROR_RESPONSE`), whereas `@orpc/client@2.0.0-beta.53` `isORPCErrorJson` strictly forbids `"status"` and requires `{ defined, code, message, data }` inside `{ json: ... }` (throwing `MalformedResponseError` on bare JSON or on objects containing `"status"`).
  - Because the server sees the incoming `X-NetScript-RPC-Protocol` header, the protocol guard emits the exact oRPC error envelope expected by the rejected caller's protocol generation (always with HTTP `426` and `defined: false`, since protocol mismatch is a transport error outside procedure `.errors()` maps):
    - **Stale v1 / headerless caller (`proto === undefined || proto === 'orpc-v1'`) hitting v2 server:** returns HTTP `426` + `{ json: { defined: false, code: 'CLIENT_UPGRADE_REQUIRED', status: 426, message: 'Client RPC protocol is outdated; reload or upgrade.', data: { expectedProtocol: 'orpc-v2', receivedProtocol } } }`. Real `@orpc/client@1.16.6` `RPCLink` decodes a genuine v1 **`ORPCError`** with `err.code === 'CLIENT_UPGRADE_REQUIRED'`, `err.status === 426`, `err.defined === false`, and `err.data` intact — allowing stale browser tabs, cached Fresh islands, and installed desktop apps to detect `err.code === 'CLIENT_UPGRADE_REQUIRED'` (or `getErrorHttpStatus(err) === 426`) across origins and prompt/trigger reload or update!
    - **v2 caller (`proto === 'orpc-v2'`) hitting Phase 0a v1 server (or non-v1 mismatched caller such as `orpc-v3` hitting v2 server):** returns HTTP `426` + `{ json: { defined: false, code: 'CLIENT_PROTOCOL_UNSUPPORTED' | 'CLIENT_UPGRADE_REQUIRED', message: '...', data: { expectedProtocol, receivedProtocol } } }` (omitting `"status"`). Real `@orpc/client@2.0.0-beta.53` `RPCLink` decodes a genuine v2 **`ORPCError`** with `err.code`, `err.defined === false`, `err.data`, and `err.cause instanceof ResponseError` (`getErrorHttpStatus(err) === 426`), NOT `MalformedResponseError`! (As defense-in-depth against non-oRPC proxy `426` responses, `getErrorHttpStatus(err)` also reads `MalformedResponseError.response.status`.)
- **Two-step CORS-safe rollout & blue-green preflight path (`X-NetScript-RPC-Protocol`):**
  - **Phase 0a (`0.0.10`, server-only RPC-scoped — zero breaking CORS preflights!):**
    1. On mounted RPC paths (`rpcPath` / `rpcAliases`, default `/api/rpc/*`), `withCors()` automatically appends `'X-NetScript-RPC-Protocol'` (case-insensitively deduplicated) to explicit `allowHeaders` preflights while leaving non-RPC routes (`/raw`, `/health`, `/api/*` OpenAPI) untouched (explicitly documented in `packages/service/README.md:167-169` and updating only the `/api/rpc/ping` preflight expectation at `packages/service/tests/cors-response-authority_test.ts:267`, leaving `/api/status`, `/raw`, `/health` and line `432` unchanged). Standalone v1 `CORSPlugin` echoes `access-control-request-headers` by default (or auto-includes the header when `allowHeaders` is explicit).
    2. v1 `RPCHandler` mounts the reverse `ProtocolGuardPluginV1` inside CORS rejecting `orpc-v2` with HTTP `426` (`CLIENT_PROTOCOL_UNSUPPORTED`, v2 envelope), **exempting `OPTIONS`**, and appending `Vary: X-NetScript-RPC-Protocol` on BOTH RPC `200` and `426` responses (updating only the `/api/rpc/ping` `assertVary` assertions at `packages/service/tests/cors-response-authority_test.ts:197,304,476` to `['origin', 'x-netscript-rpc-protocol']` while leaving `/api/status`, `/raw`, and `/health` unchanged).
    3. **SDK `RPCLink` does NOT emit `X-NetScript-RPC-Protocol: orpc-v1` by default in `0.0.10`** — preserving zero-preflight cross-origin `GET` simple requests on v1, avoiding breakage against external gateways / un-upgraded services with explicit `allowHeaders`, and keeping `OMITTED_CONTRIBUTION_BASELINE` (`packages/sdk/tests/integration/client-contribution-adapter_test.ts:25-30,389-406`) unchanged in `0.0.10`.
  - **Phase 2 (`0.1.0`, breaking wire & CORS shift):**
    1. v2 SDK `RPCLink` unconditionally emits `X-NetScript-RPC-Protocol: orpc-v2` (explicitly documented as a `0.1.0` breaking change: cross-origin browser `GET` RPC queries now trigger a CORS `OPTIONS` preflight, external reverse proxies/gateways with explicit `Access-Control-Allow-Headers` must allow `X-NetScript-RPC-Protocol`, and `OMITTED_CONTRIBUTION_BASELINE` in `client-contribution-adapter_test.ts` is updated at `0.1.0`).
    2. Both RPC-path `withCors()` preflights and opt-in `RPCHandlerConfig.cors` (`CORSHandlerPlugin` on RPC mounts) automatically include `'X-NetScript-RPC-Protocol'` whenever explicit `allowHeaders` is configured.
    3. v2 `RPCHandler` mounts `ProtocolGuardHandlerPlugin` (`before: ['~cors']`), rejecting `'orpc-v1'` or missing headers with CORS-wrapped `426 CLIENT_UPGRADE_REQUIRED` and emitting `Vary: X-NetScript-RPC-Protocol` on BOTH RPC `200` and `426`.
  - **Multi-service, installed-client & blue-green preflight rollout order:**
    1. Deploy **Phase 0a (`0.0.10`)** on services first so `withCors()` / v1 CORS allows `X-NetScript-RPC-Protocol` and v1 handlers reject `orpc-v2` cleanly with CORS-wrapped `426`.
    2. For single-workspace / lockstep deployments: deploy `0.1.0` servers and web bundles together; stale cross-origin browser tabs (sending no header) receive readable CORS-wrapped `426` decoded as `ORPCError('CLIENT_UPGRADE_REQUIRED', { status: 426 })` and reload cleanly.
    3. For multi-service or installed desktop/mobile deployments that cannot upgrade all callers simultaneously: **drop** the unworkable dual-major `/api/rpc/v2` in-process mount. Instead use either: (a) **blue-green gateway header routing** (`X-NetScript-RPC-Protocol: orpc-v2` → v2 green pool; absent/`orpc-v1` → Phase 0a v1 blue pool until v1 traffic drains to zero). Crucially, browser CORS `OPTIONS` preflights **never** carry the custom `X-NetScript-RPC-Protocol` header (only `Access-Control-Request-Headers: x-netscript-rpc-protocol`), so a header-routed gateway sends v2 preflights to the **Phase 0a v1 blue pool** (unless the gateway also routes `Access-Control-Request-Headers` matches to v2 green); because the Phase 0a v1 blue pool already allows `X-NetScript-RPC-Protocol` in `Access-Control-Allow-Headers` and answers `204`, the browser immediately proceeds to send the actual `X-NetScript-RPC-Protocol: orpc-v2` request to the v2 green pool (`200`, verified end-to-end in Probe B1!), or (b) the empirically verified **`OpenAPILink` v1.16.6 → `OpenAPIHandler` v2 bridge** (proven in Probe B1 for JSON-safe procedures—strictly limited to JSON-representable types, no `BigInt` or RPC-only event metadata).

#### 4.3 Blocker B2 + N3 decision: Contract-declared `GET` allow-list, full HTTP-verb parity & paired `allowGetRpc: false` client contract (**measured** Probe B2)

- **Server `allowMethods` preserving `PUT`/`PATCH`/`DELETE`/`HEAD→GET` (N3):** Keep `GET`-first RPC queries for procedures explicitly declaring `method: 'GET'` or `method: 'HEAD'` in contract OpenAPI/route metadata **while preserving v2's `RPC_DEFAULT_ALLOW_METHODS` (`POST`, `PUT`, `PATCH`, `DELETE`)** so CRUD `PATCH` (`update`) and `DELETE` (`delete`) (`packages/contracts/crud/create-crud-contract.ts:367-378`, `workers.contract-definition.ts:534`) continue working identically:
  ```ts
  const DEFAULT_WRITE_METHODS = new Set(['POST', 'PUT', 'PATCH', 'DELETE']);
  allowMethods: (method, proc) => {
    if (DEFAULT_WRITE_METHODS.has(method)) return true;
    if (method === 'GET') {
      const declared = getOpenAPIMeta(proc)?.method;
      return declared === 'GET' || declared === 'HEAD';
    }
    return false;
  }
  ```
  Paired with `GetMethodCsrfProtectionHandlerPlugin`, this preserves all 52 first-party `GET` procedures, CRUD `PATCH`/`DELETE`, `HEAD→GET`, `DedupeRequestsPlugin`, `force-cache` / `default` cache groups, and HTTP/CDN caching.
- **Exact v1-parity replacement for `inferRPCMethodFromContractRouter` (N3):** Replace with a small NetScript helper in `packages/sdk/src/internal/transport-policy.ts` reading `getOpenAPIMeta(procedureNode)?.method`: maps `'HEAD' → 'GET'` (preserving `packages/sdk/tests/transport-policy_test.ts:35`), preserves `'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'`, and defaults omitted/other methods to `'POST'` (verified in Probe B2).
- **Measured CSRF matrix (Probe B2):**
  - `GET` on a `POST` mutation → `matched: false` (404).
  - `PUT` / `PATCH` / `DELETE` and `HEAD→GET` on matching procedures → `200`.
  - Server-to-server `GET` (no `Sec-Fetch-Site`) → `200`.
  - Same-origin / same-site browser `GET` → `200`.
  - Cross-site browser `fetch()` with full Fetch Metadata (`Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: cors`, `Sec-Fetch-Dest: empty`) → **`200`** (governed by `withCors()` allowlist).
  - Cross-site `GET` with **missing `Sec-Fetch-Mode` or `Sec-Fetch-Dest`** OR top-level navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) → **`403 FORBIDDEN`**.
- **Mandatory security prerequisite & paired client opt-out (N3):** GET-enabled RPC endpoints require session cookies marked `SameSite=Lax` or `SameSite=Strict`. Services that must accept cross-site `SameSite=None` cookies MUST set `allowGetRpc: false` (`POST`/`PUT`/`PATCH`/`DELETE` only) on `createService` / `RPCHandlerConfig` **AND pair every SDK client calling `GET`-declared procedures on that service with `createServiceClient({ ..., transportPolicy: { method: () => 'POST' } })`** (or use a `POST`-only RPC contract without `method: 'GET'`), because without the paired client override the SDK infers `GET` from the contract and hits `404` (`matched: false`, verified in Probe B2!).

#### 4.4 Blocker B3 decision: Preserving v1 CORS boundary in Phase 0a; breaking tightening at `0.1.0`

- **Phase 0a (`0.0.10`):** Keep `new CORSPlugin()` in `packages/service/src/primitives/handlers.ts:112` untouched on v1 so existing v1 origin-reflection behavior for services omitting `withCors()` and standalone `createRPCHandler`/`createOpenAPIHandler` mounts is preserved without breaking cross-origin callers. Non-RPC routes (`/raw`, `/health`, `/api/*` OpenAPI) keep their exact configured `withCors({ allowHeaders })` and `Vary` headers untouched (`packages/service/tests/cors-response-authority_test.ts:432` and all non-RPC cases at lines `197`, `267`, `304`, `476` remain unchanged). On mounted RPC routes (`rpcPath` / `rpcAliases`, default `/api/rpc/*`), Phase 0a's RPC-scoped protocol readiness (§4.2) appends `X-NetScript-RPC-Protocol` to explicit `allowHeaders` preflights and `ProtocolGuardPluginV1` (`order: 0 < 9e6` inside `CORSPlugin`) appends `Vary: X-NetScript-RPC-Protocol` on RPC `200`/`426` responses; Phase 0a explicitly updates `packages/service/README.md:167-169` to document that RPC-route contract and updates only the `/api/rpc/ping` assertions in `packages/service/tests/cors-response-authority_test.ts` (line `267` for RPC preflight `allowHeaders`, and lines `197`, `304`, `476` for RPC `200` `Vary: ['origin', 'x-netscript-rpc-protocol']`).
- **Phase 2 (`0.1.0`, breaking security tightening):** Remove implicit handler-level CORS from `createRPCPlugins()` by default (never relying on v2's deprecated `CORSPlugin` alias, which silently answers `*` with no `Vary: Origin`). Services built with `createService` configure `withCors()` (`NETSCRIPT_CORS_ORIGINS`); standalone `createRPCHandler()` / `createOpenAPIHandler()` callers needing CORS pass explicit `cors: { origin: [...], allowHeaders?: [...] }` on `RPCHandlerConfig` (automatically including `X-NetScript-RPC-Protocol` on RPC mounts when explicit `allowHeaders` is provided, and wrapping `ProtocolGuardHandlerPlugin` via `before: ['~cors']` so `426` rejections carry CORS headers).

#### 4.5 Blocker B7 decision: `redirect: 'error'` enforced after spread (**measured** Probe B7)

- **Decision:** Enforce **`redirect: 'error'`** (NOT `'manual'`, which silently resolves with `undefined`) applied **after** spreading `...init` at the single HTTP link fetch call in `packages/sdk/src/client/http-client-link.ts:192`:
  ```ts
  return await transportFetch(request, {
    ...init,
    headers,
    cache: context?.cache as RequestCache,
    signal: context?.signal,
    redirect: 'error',
  });
  ```
- **Contract & parity:** Misrouted 3xx responses reject with a network `TypeError` (consistent with PR #2659's explicit redirect refusal), and foreign 307 targets receive **zero requests** (preventing leakage of custom headers such as `x-api-key`, `traceparent`, and request bodies, as well as cross-origin response spoofing—noting Deno's Fetch already strips `Authorization` and `Cookie` on cross-origin hops).

#### 4.6 `release/orpc-v1` version scheme, `0.0.x` semver rules & rollback (B8)

- **Version scheme under `0.0.x`:** Phase 0a ships as **`0.0.10`**, Phase 0b ships as **`0.0.11`**, and Phase 2 cuts over to **`0.1.0`** (new semver minor line on JSR), leaving `release/orpc-v1` on the **`0.0.x`** line (**`0.0.12+`**) for **90 days** after `0.1.0` GA.
- **Exact `0.0.x` semver consumer update rules (verified via `@std/semver`):** Under SemVer `0.0.x`, caret ranges pin **both** minor and patch (`^0.0.10` resolves strictly `>=0.0.10 <0.0.11`, **excluding** `0.0.11` and `0.0.12`; similarly `^0.0.11` excludes `0.0.12`). Downstream applications pinned to `^0.0.10` or `^0.0.11` therefore do **not** automatically resolve `0.0.12+` backports: to receive `release/orpc-v1` maintenance patches while remaining on oRPC v1, consumers must either:
  1. **Update their pin explicitly** when taking a backport release (e.g., `^0.0.10` / `^0.0.11` → `^0.0.12`, or exact `0.0.12`), **OR**
  2. **Opt into a bounded `0.0.x` range** such as **`~0.0.10`** / **`~0.0.11`** (equivalent to `>=0.0.10 <0.1.0` / `>=0.0.11 <0.1.0`), which resolves `0.0.12+` backports automatically while never pulling `0.1.0`!
- **Rollback:** Before publishing `0.1.0`, revert the cut-over merge (single atomic revert via `catalog:`). After publishing `0.1.0`, backport critical fixes to `release/orpc-v1` (`0.0.12+`) during the 90-day overlap window.

### 5. Interaction with companion RFC A (PR #2673 / issue #2671)

- **RFC A Stage 1a (`0.0.10`, head `bd8d51c0`):** Independent of v2; unblocks PR #2659 and ships unified `requestId`, per-leaf + context-symbol idempotent router wrapping, and declarative `withProcedureRateLimit` (with `ResponseHeadersPlugin`), while **also keeping `CORSPlugin` untouched on v1** (fully aligned with RFC B §4.4!).
- **RFC A Stage 1b (`0.0.11`, gated on RFC A acceptance):** Retains `contract-procedure-index.ts` at the HTTP edge on v1 to preserve 401/403-before-413 and 404/410 parity, and migrates at **Phase 2 (`0.1.0`)** onto oRPC v2's native `RPCMatcher` (`@orpc/server/standard`) + `OpenAPIMatcher` (`@orpc/openapi/standard`) + `getOpenAPIMeta` (eliminating the 4 removed v1 helpers without weakening HTTP edge guards).
- **RFC A Stage 2 (`0.1.0`)** ships with RFC B Phase 2 so downstream applications adopt `createRouterClientTransport` and oRPC v2 in one release, with the per-leaf `WRAPPED_PROCEDURE_SERVICE` + per-invocation `PIPELINE_EXECUTED_SYMBOL` guards protecting against v2's middleware-dedup removal.

### Security implications

1. **CORS boundary & preflight/rejection safety (B3 + N1):** Permissive origin reflection already exists on v1 for services omitting `withCors()` and standalone handlers (`cors-response-authority_test.ts:442-480`). On v2 the deprecated `CORSPlugin` alias silently degrades to `*` with no `Vary: Origin`. Removing implicit handler CORS in `0.1.0` tightens security explicitly while giving standalone mounts an explicit `cors` option, auto-including `X-NetScript-RPC-Protocol` strictly on RPC-path explicit `allowHeaders` preflights (leaving non-RPC routes untouched), exempting `OPTIONS` from the `426` guard, and running CORS *outside* the protocol guard (`withCors()` / `before: ['~cors']` / `order: 0 < 9e6`) so cross-origin browsers can read `426` upgrade errors cleanly.
2. **Redirect SSRF & header/body leakage (B7):** Enforcing `redirect: 'error'` after `...init` spread in `http-client-link.ts` prevents v2's default redirect-following from leaking custom headers (`x-api-key`), `traceparent`, and request bodies to foreign 307 targets or accepting spoofed responses.
3. **GET RPC CSRF policy (B2 + N3):** Contract-declared `GET`/`HEAD` allow-list + `GetMethodCsrfProtectionHandlerPlugin` blocks cross-site top-level navigations and partial Fetch Metadata headers while keeping `POST`/`PUT`/`PATCH`/`DELETE` mutations non-GET; requires `SameSite=Lax|Strict` cookies (or `allowGetRpc: false` paired with client `transportPolicy: { method: () => 'POST' }` for `SameSite=None`).
4. **Protocol mismatch protection (B1 + N1):** Fail-closed CORS-wrapped `426` on `X-NetScript-RPC-Protocol` mismatch (`OPTIONS` exempt, `Vary` on `200` and `426`, wire-compatible `ORPCError` JSON envelopes decoded cleanly by real v1.16.6 and v2 links) prevents silent `bigint`/error corruption across mixed-version clients and servers without forcing CORS preflights in `0.0.10`.

## Breaking changes and migration

Labeled `breaking` because `0.1.0` (Phase 2) upgrades to `@orpc/*@^2.0.0`, removes implicit handler `CORSPlugin`, changes RPC wire protocol (v2 client emits `X-NetScript-RPC-Protocol: orpc-v2` triggering cross-origin `GET` preflights; v2 handlers fail closed with CORS-wrapped `426 CLIENT_UPGRADE_REQUIRED` exempting `OPTIONS`), and drops v1-only contract/error/query/package surfaces. Phase 0a (`0.0.10`) is backward-compatible except refusing misrouted 3xx RPC redirects (`redirect: 'error'`). Under `0.0.x` semver, `^0.0.10` / `^0.0.11` exclude `0.0.12+`; consumers staying on `release/orpc-v1` (`0.0.12+`) during the 90-day overlap update their pin explicitly (`^0.0.12`) or opt into `~0.0.10` / `>=0.0.10 <0.1.0`. See `## Downstream consumers` and §4 for the full split plan, codemod limits, and rollout sequence.

## Prior art

- **oRPC v1→v2 migration guide:** <https://orpc.dev/docs/migrations/from-v1> (read in full, covering up to `2.0.0-beta.53`).

- **Draft PR #2659** (`rfcs/0000-in-process-service-link.md`, head `f8c8d8fd`) — in-process fetch-link sharing the `redirect: 'error'` and v2 `fetch(url, init)` alignment.

## Unresolved questions

1. **Contract metadata `~openapi` key stability across oRPC v2 beta → GA:** `deno publish --dry-run` (`--isolatedDeclarations`) has already been verified passing on `2.0.0-beta.53` with explicit `defineMeta` / `BaseContractRoute` annotations, and `routeMeta` via `defineMeta('~openapi', ...)` keeps `@netscript/contracts` free of `@orpc/server`. Verify in Phase 1 (`chore/orpc-v2-shadow`) that oRPC `2.0.0` GA preserves `'~openapi'` as the public `openapi` meta key (or adopt an official browser-safe `@orpc/openapi/meta` subpath if upstream splits it out before GA).
2. **Scalar UI compatibility with OpenAPI `3.2.0`:** Verify in Phase 1 whether NetScript's bundled `/api/docs/scalar.js` renders OpenAPI `3.2.0` documents cleanly or requires pinning `3.1.0` in `OpenAPIGenerator` options.
3. **`@netscript/sdk/client` `safe()` tuple index 2 at `0.1.0`:** Decide whether `@netscript/sdk/client`'s `safe()` retains `isDefined: boolean` permanently alongside adding `definedError`, or aligns tuple index 2 with upstream oRPC v2 (`definedError | null`) at `0.1.0`.
