
### [SEVERITY: major] Production-exclusion "mechanism A" is specified two incompatible ways, and §10's version describes a mount H-1 abolished
**Anchor:** §10 D-7 lines 2588-2594 (*"The app-side mount import sits behind a constant… `import.meta.env.MODE !== 'development'` folds to a dead branch"*; mechanism B as *"The middleware serving the DevTools mount… returns 404"*) vs §5 H-4 lines 726-742 (mechanism 1: *"Nothing under `.netscript/devtools/` is reachable from any of those roots"*; mechanism 2: generated `main.ts` first-statement refusal that *exits*) and H-1/H-2 lines 622-681 (*"never mounted into the application's `routes/` tree"*).
**Finding:** Under H-1 there is no app-side DevTools import at all — structural absence is a graph fact, not a dead branch — so §10 D-7's mechanism A ("the app-side mount import… folds to a dead branch") describes the app-mounted design T1 rejected. Its mechanism B ("middleware serving the DevTools mount… 404") likewise differs from H-4's mechanism 2 (startup refusal in `main.ts`, process exit). INV-4's requirement that "the two mechanisms MUST NOT share a signal" therefore cannot even be evaluated: the two sections do not agree on what the two mechanisms *are*, and where §10's pair both derive from the mode/NODE_ENV family, the independence claim is strained on its own terms.
**Why it matters:** "Stricter than every system surveyed" is the RFC's headline trust claim, and G-5 is its proving gate. A gate written against §10's stale mechanics tests a mount that doesn't exist; written against H-4, §10's prose is unfalsifiable. This is also the defect class the RFC accuses `/design` of — an ungated surface described inconsistently.
**Proposed direction:** Rewrite §10 D-7 mechanisms A/B to H-4's definitions (build-graph edge absence; `main.ts` startup refusal), delete the `define`-fold and middleware descriptions, and restate INV-4's two signals as (a) graph reachability, (b) runtime env — then name what "share a signal" means for that pair.

### [SEVERITY: major] DT0's claimed browser-boundary defense is vacuous in v1, and DT1's token-transport rule contradicts its own link grammar
**Anchor:** §9 line 2133 (DT0: *"What DT0 still defends is the **browser** boundary (INV-5)"*) vs INV-5/G-4 line 2246 (*"Every non-GET DevTools endpoint… requires a per-process token… GET never requires the token, so read paths stay friction-free"*); §9 line 2134 (*"If a token ever travels in a URL it uses the **fragment**"*) vs H-5 line 768 and §11.6 line 2928 (*`{PublicUrl}/login?t={token}`*).
**Finding:** Two exposure defenses do not hold as written. (a) INV-5 gates only non-GET endpoints, and v1 is read-only — L8 plus INV-3 ("no declared actions ⇒ no mutating endpoint generated at all") means v1 has zero non-GET endpoints, so the token protects nothing and the entire diagnostic surface (plugin inventory, endpoint directory, telemetry, contract coverage) is readable by any local web page that can reach 127.0.0.1:5199 — DNS-rebinding being the named T-4 class, which INV-5's Origin/Host check does not cover for GET. The RFC also never pins the HTTP method of oRPC read procedures: if reads are POST, INV-5 makes every read token-gated and G-4's "friction-free reads" sentence is false instead. Either reading breaks a stated property. (b) DT1 normatively requires fragment transport for URL-borne tokens (fragments don't reach servers/logs/Referer) while H-5 and the §11.6 helper specify Aspire's `login?t=` *query* form, which does all three.
**Why it matters:** The declines in D-5 are defensible only if the boundaries that remain are real. "DT0 defends the browser boundary" is the RFC's own justification for spending no trust budget on contributors; an invariant that is vacuous for the only release it describes is exactly the decorative-gate failure mode the RFC elsewhere condemns (L13).
**Proposed direction:** Specify read-procedure method and make INV-5 method-independent for the Host check: verify `Host`/`Origin` against the bound address on *every* request (Vite `allowedHosts` posture), token only for non-GET; state the loopback DNS-rebinding residual explicitly if Host-checking is declined. For DT1, pick one: keep `login?t=` and delete the fragment sentence (accepting log exposure, as Aspire does), or transport the token via fragment and document the Aspire divergence.

### [SEVERITY: minor] Identity residues survive the unification: an undefined type, a retired id form in a doc comment, and a package-keyed example
**Anchor:** §8 lines 1787-1790 (doc comment *"`<pluginId>/<panel>/v<major>` — version-suffixed ids"* over `DevToolsPanelRef`) with lines 1807 and 1830 (`readonly panelId: DevToolsPanelId;`); §12 line 3412 (A-6: *"`@netscript/workers/panel/v1`"*).
**Finding:** `DevToolsPanelId` is referenced by both server and client context contracts but never defined — the defined type two lines above is `DevToolsPanelRef`. Its doc comment still describes the retired string-template identity (`<pluginId>/…`, plugin-keyed) that §6's mountId law replaced, and §12's adopt table likewise examples a package-name-keyed id. These are the same variant class PLAN-EVAL cycle 2 failed the corpus over, surviving in the final normative text at smaller scale.
**Why it matters:** These are the types a panel author implements against; an undefined type name plus a contradicting doc comment is precisely how two implementers produce two identity schemes.
**Proposed direction:** Rename both uses to `DevToolsPanelRef`, rewrite the comment as "`<mountId>/<id>/v<apiMajor>` — host-derived, never authored", and fix the A-6 example to a mountId-keyed form.

### [SEVERITY: minor] The zone contract is unreconciled across §6, §7, and §11.3
**Anchor:** §6 lines 1141-1144 (zone ids *"Version-suffixed… 'devtools.capability.panel/v1'"*) vs §7 lines 1447-1453 (`DevToolsZone` = `'workers.console' | …`, no suffix); §6 line 1134 (`navGroups`) vs §7 line 1392 (`nav` kind **REJECT**ed, host derives nav); §11.3 line 2787 (*"contributed home cards sit BELOW the feed"*) vs §7 line 1398 (`home` zone **STAGE**d until "a first-party card issue is actually filed").
**Finding:** Three unreconciled seams: (1) the targeting law (line 1008) requires contributions to name target ids "drawn from the host's descriptor vocabulary," but descriptor zone ids are version-suffixed while the `zone` field's union is bare — as specified, no panel matches any zone; (2) the descriptor carries `navGroups` though the only kind that consumed nav groups was rejected; (3) §11.3 lays out Home around contributed home cards that §7 explicitly stages out of existence.
**Why it matters:** Each piece is small; together they mean the zone vocabulary — the closed-vocabulary decision the whole collision story rests on — has no single consistent statement a generator could implement.
**Proposed direction:** Decide whether zone ids carry `/v1` (and update `DevToolsZone` to match, plus the quarantine-state mapping between §6's five states and §11.7's seven `PanelState` arms, which is also never stated); drop `navGroups` or cite its consumer; strike "contributed home cards" from §11.3 or un-stage the `home` zone.

### [SEVERITY: minor] The trust antecedent overstates "no third parties," and generate-time in-process import is an unmodelled execution surface
**Anchor:** §9 lines 2122-2125 (*"A DevTools contribution is a workspace package whose server code the developer already runs with full permissions… A panel cannot gain what its own package already has"*) vs §10 lines 2490-2497 (install resolves `source = {kind:'jsr', specifier: 'jsr:<pkg>@<version>'}`) and §6 lines 1066-1067 (*"the generator imports the plugin's pointed-to export in-process"*).
**Finding:** The decline table's antecedent — "untrusted third-party code… absent" — is weaker than the RFC's own install path warrants: JSR-installed plugins are third-party code, and the devtools family imports their envelope modules *in-process inside the CLI* at `plugin install`/generate time. The honest load-bearing argument is the capability-subset one ("a panel cannot gain what its package already has"), but that argument covers the app runtime, not CLI-process execution at install time — a surface where plugin code did not previously run, with the CLI's permissions, before the app ever starts. No threat row covers it: T-2/INV-2 govern the subprocess model the devtools family deliberately does not use, and advisory-install ("never fails the install") specifies validation failure but not import-time side effects or crashes.
**Why it matters:** The declines themselves may well be right — this is not a sandboxing argument — but a threat model that names ten threats and omits the one execution surface its own pipeline creates is the kind of scoped-away gap the RFC's citation discipline exists to prevent.
**Proposed direction:** Restate D-1's antecedent around capability subset rather than contributor trust; add a threat row for "envelope module executes in the CLI process at generate time" with the advisory-install behavior for throw/side-effect cases, and a normative line that envelope modules must be import-safe (the AP-11 rule the RFC imposes on itself, extended to contributors).

## Strongest part

The single best decision is the **closed, host-owned zone vocabulary — Medusa's actual model, corrected from the Strapi-shaped "plugin-minted zones" that circulated in the board's prior art — with the design budget consciously moved off collision and onto ordering** (§2.3, §6 Collision, research F22/R5). It is the decision that makes the entire contribution model small: no open namespace, no two-phase register/bootstrap lifecycle, no caller-side `if (plugin)` guards, deterministic capacity overflow, and "adding a zone is a data change, not a contract change." It converts the one problem every surveyed system failed at (ordering) into the one place the RFC invests net-new design, and it is what lets quarantine be product surface instead of machinery. Everything fixed above must not break it: the anchor-format fix must keep curation host-owned and mountId-keyed (never reopen zone minting or key order by package name), and the `DevToolsUiNode` widening must stay a host-release vocabulary growth, not a plugin renderer seam.
