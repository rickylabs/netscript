## Recommendation

NetScript DevTools is a **separate first-party host process** — a NetScript-owned Fresh app whose
thin, CLI-generated root lives at `.netscript/devtools/` in the user's workspace, launched on
demand by the CLI on its own port (loopback-bound, default `NETSCRIPT_DEVTOOLS_PORT` → `5199`),
with its **own** route tree and its **own** Vite dev process — composed with the scaffolded app
strictly by HTTP reads and typed deep-links, never by mounting into the app's `routes/` tree. The
fat host runtime and panels live in `packages/plugin-devtools-core` (**Archetype 2**, per the
ratified dashboard precedent), with a thin `plugins/devtools` (**Archetype 5**) as the
installable glue; **no `@netscript/fresh` subpath is taken**, so the A3-vs-A4 dispute over
`fresh` is defused rather than inherited. Deployed production gets DevTools **absent by
construction** (nothing in the app's build graph references it) **and** refused at runtime
(fail-safe mode check), two independent mechanisms per the TanStack precedent — stricter than
upstream, which ships devtools into prod builds with auth disabled. A Vite-8 migration is neither
a prerequisite nor a scheduled follow-up: the design is Vite-version-independent because open
question 1 is now **closed from source** — Fresh, not Vite, renders the app HTML, so the entire
`transformIndexHtml`-shaped design space was never available.

## Normative decisions

Each is committal and citable; "the host" means the DevTools host process.

1. **Identity.** DevTools is a separate first-party host process composed with the app by HTTP
   reads and deep-links — not an app-mounted mode, not a `fresh` subpath. This matches #1446 P-6's
   two-hosts decision sentence (`p2` F3 via research.md F3), the ratified dashboard precedent's
   shape (fat core + thin plugin + CLI auto-launch, `.llm/runs/plan-roadmap-expansion--seed/design/A-dashboard/proposal.md:9-12`
   via `b2` F1; issues #423/#424 in `b2` F11), and Aspire's own trajectory (fixed separate
   dashboard host; in-dashboard agent UI removed in 13.3, `m4` F15 via S-19).
2. **Local development behavior.** The CLI generates a thin host root at
   `<projectRoot>/.netscript/devtools/` (`main.ts`, `client.ts`, `vite.config.ts`, `routes/`,
   `islands/` — sibling of the existing `.netscript/generated/`, `r1` F10) and launches it with
   the same task shape as the app (`deno run -A npm:vite --configLoader native`, `r1` F15,
   `generate-app-deno-json.ts:112-119`). Port: `NETSCRIPT_DEVTOOLS_PORT`, default **5199**
   (distinct from the app's 5173 default, `vite.config.ts.template:36-39`). Bind: `127.0.0.1`.
   Route tree: **the host's own** `routes/` under `.netscript/devtools/` — the user app's
   `routes/` gains zero DevTools entries, so `r1` F7 (full-reload state reset on app route edits)
   and F8 (page-module rewriting) do not touch DevTools, and DevTools edits do not reload the
   user's app. URLs are un-prefixed on the host's own origin (`http://127.0.0.1:5199/`,
   `/traces`, …) — no `/__devtools` prefix is needed because the origin is the namespace.
3. **Deployed-production behavior: absent by default, via two independent mechanisms**
   (TanStack precedent: distrust any single signal, `m2` F6-F7 via research.md F24; upstream
   ships devtools into prod builds with client auth disabled, `m1` D4/F10-F11 — we are stricter):
   - **Mechanism 1 — structural absence.** The app's build graph is rooted at `client.ts`, the
     `routes/` walk, and `main.ts` (`r1` F4 `manifest.ts:289,407`; F15 `vite build` →
     `_fresh/server.js`); nothing under `.netscript/devtools/` is referenced by any of them, so
     the deploy artifact **cannot contain** DevTools code. No `import.meta.env.DEV`-guarded
     in-app injection exists to fail open.
   - **Mechanism 2 — fail-safe runtime refusal.** The generated `main.ts`'s first statement
     refuses to serve unless mode is **literally** `'development'` (polarity per TanStack's
     `!== 'development'` no-op: anything not-dev refuses, `m2` F6 via F24) and exits with a named
     error. A copied artifact that somehow reaches a production environment still refuses.
   - **No build-mode/static-dump target in v1.** The `__rpc-dump` shape (`m1` F10, C8) is
     recorded prior art, not scope.
4. **Remote-exposure behavior.** Default is loopback-only; the host is never reachable
   off-localhost unless the operator passes an explicit `--host` flag **and** the host has
   minted a session browser token, with links built as `{publicUrl}/login?t={token}` — the
   sanctioned Aspire automation pattern (`m4` F12/F17-18 via S-19). #890's T0 posture is not
   inherited: #890 itself parks T1/T2 tiers "in the dashboard epic", i.e. hands them here
   (`p1` F10, C9). Token/auth mechanics are T6's scope; T1 fixes the gate: **no token ⇒ no
   non-loopback bind**, and deployed production is excluded upstream of this question by
   decision 3.
5. **Archetype and packages.** `packages/plugin-devtools-core` takes **Archetype 2**
   (integration: package-owned ports over Aspire/OTLP/telemetry-query + a UI-serving
   application layer; no background processor, no owned DB) exactly as the dashboard precedent
   ratified (`A-dashboard/proposal.md:9-12,77-95` via `b2` F1); `plugins/devtools` is the thin
   **Archetype 5** glue under the thinness law (`06-archetypes.md:161-214` via `b2` F2). The
   v1 host **owns no long-running supervised state**: live views are request-scoped reads or
   request-lifetime streams, and live tails deep-link to Aspire per #400's non-duplication
   acceptance line (`b1` F3 via research.md F8). If a later streaming contract (the S-21 gap)
   gives the host supervised subscriptions with lifecycle, the archetype **must be re-evaluated
   to A3** under "pick the larger" (`06-archetypes.md:348-367`), which adds gate **F-13**
   (`stop()` + `AbortSignal`, `archetype-gate-matrix.md:19-38` via `b2` F3).
6. **`@netscript/fresh` is treated as A4 for this RFC's purposes** — the doctrine's own
   assignment table is the authority (`06-archetypes.md:376`), and the merged #890 record's A3
   label is recorded drift (`b2` D3), not a ratified reassignment. The question is additionally
   **moot for the host** because decision 1 takes no `fresh` subpath — which also honors the
   stop-conditions constraint against deepening `fresh`'s Restructure verdict (`b2` F6).
7. **Gate-set consequence** (naming it, per S-10 "not self-executing"): the core takes the A2
   column — F-1…F-12, F-14…F-19 required, **no F-13 in v1**; the plugin takes the A5 column
   (F-13 `subtype`). Browser gates come from the **`SCOPE-frontend` overlay**, which the RFC
   must name explicitly because no archetype column requires browser validation for A2/A3
   (`archetype-gate-matrix.md:65-72`, `SCOPE-frontend.md:22-36` via `b2` F3). Adding
   `--root packages/plugin-devtools-core --root plugins/devtools` to `deno.json:156` is a
   **named slice**, or the gate claim is decorative (`b2` F7).
8. **Vite 8 is avoidable** — neither a prerequisite nor a follow-up RFC this design depends on.
   The host mounts nothing through Vite's HTML pipeline (decision 9 closes why that pipeline was
   never available), and adoption of `@vitejs/devtools-kit` is already resolved impossible at
   this baseline (R4; `m1` F28/D2). Recorded as an explicit non-goal with a re-entry condition:
   *if* kit adoption is ever wanted, a Vite-8 migration RFC precedes it as separate work.
9. **Open question 1 — CLOSED: Fresh renders the app HTML; Vite never serves it.** Read from
   the pinned plugin's source (`jsr:@fresh/plugin-vite@^1.1.2`, pinned at
   `packages/cli/src/kernel/constants/scaffold/scaffold-app-catalog.ts:10`; cached source
   enumerated via `deno info --json jsr:@fresh/plugin-vite@^1.1.2`):
   - `https://jsr.io/@fresh/plugin-vite/1.1.2/src/plugins/dev_server.ts` — the `fresh:dev_server`
     plugin's `configureServer` installs a catch-all Connect middleware
     (`server.middlewares.use(...)`) that, for every URL that is not a Vite-internal URL
     (`/@vite|/@fs|/@id|/.vite`), module-graph hit, or static file, runs
     `await server.ssrLoadModule("fresh:server_entry")` and
     `const res = await mod.default.fetch(req)` — **Fresh's own `App.fetch` produces the HTML
     `Response`**, post-processed only by the plugin's manual CSS collection
     (`html.replace("</head>", styles + "</head>")`) and sent via `sendResponse`.
   - `grep transformIndexHtml|index.html|appType` across all 18 files of the package → the only
     `index.html` handling is *static-dir* `index.html` served verbatim with
     `nodeRes.end(content)` — **zero `transformIndexHtml` uses** anywhere in the package.
   - The scaffold ships no `index.html`: `packages/cli/src/kernel/assets/app/` contains only
     `client.ts`/`main.ts`/`router.ts`/`vite.config.ts` templates + `routes/`/`components/`/
     `assets/` (directory listing, this session).
   **Consequence:** NetScript is squarely in Vite DevTools' documented silent-no-op bucket for
   `transformIndexHtml` injection (`m1` F9). Every mounting decision in this RFC is
   NetScript-owned by necessity, not preference.
10. **Package-shipped panel islands ride the upstream seam, not a bespoke one.**
    `FreshViteConfig.islandSpecifiers?: string[]` — "Treat these specifiers as island files.
    This is used to declare islands from remote packages"
    (`https://jsr.io/@fresh/plugin-vite/1.1.2/src/utils.ts:59-63`; consumed in `src/mod.ts:234-237`).
    The generated `.netscript/devtools/vite.config.ts` passes first-party (and later contributed)
    island specifiers through `fresh({ islandSpecifiers })`. This is AGENTS.md rule 3 ("wrap, do
    not reinvent") applied to the one place the design previously had an unverified dependency.
11. **The user app's tree stays clean.** No `routes/_devtools/` or `routes/(_devtools)/` trees
    ever (both are invisible helper conventions, `r1` F4 `manifest.ts:53-55` — a trap, not an
    option), and no visible DevTools group either (decision 1). Any future *in-app* affordance
    is bounded to the already-planned `/_netscript/*` JSON introspection endpoint (#423, `b2`
    F11) — data, not UI — and is out of this RFC's v1.

## Rejected, with reasons

- **App-mounted route group (`/design` shape).** Ships into production by default — the
  precedent's own gating omission is documented and unfixed (`r1` F13, OQ5); panel client state
  is reset by any app route edit (`r1` F7); the tree inherits page-module rewriting (`r1` F8);
  and it is user-owned, so DevTools updates become app-migration events.
- **`@netscript/fresh` subpath host.** Imports the unresolved A3/A4 label and gate ambiguity
  (`b2` D3) and deepens a Restructure-verdict package against the doctrine's stop conditions
  (`b2` F6). #890's own choice of this shape is merged **design text with zero implementation**
  (`p1` F1) — there is no shipped surface to stay compatible with.
- **Prebuilt package host with runtime-loaded contributions.** Runtime module federation is
  declined with the admin-console evidence (S-21/`m3`): its costs answer an antecedent
  (untrusted third-party code in a production surface) DevTools does not have.
- **`@vitejs/devtools-kit` adoption / embedded overlay.** Vite-8 floor (`m1` F28); injection
  bucket closed from source (decision 9); user-owned prod guard is fail-open (`m1` F9).
  Contract *shapes* (dock descriptor as data, named prefixed RPC, handle-update, launcher tier,
  json-render tier) remain the imitation targets (`m1` applicability verdict) — T2/T3's input.
- **Static/offline dump mode in v1.** Upstream's build mode disables client auth by
  construction (`m1` F11, `DTK0008`); nothing in the charter needs it.

## Open questions for the owner

1. **Auto-launch policy.** Does the app dev flow auto-start the DevTools host (the #424
   precedent), or is `netscript devtools` always explicit? Recommend: explicit in v1, launcher
   affordance later (`m1` F15).
2. **Distribution.** Is `plugins/devtools` installed by default at scaffold time, or opt-in via
   `netscript plugin add devtools`? Recommend opt-in (keeps scaffold minimal; doctor can
   advertise it).
3. **Ratify the Vite-8 non-goal** (stage-C owner fork 17) and the **production posture**
   (fork 18: no build-mode target, two exclusion mechanisms) as stated in decisions 3 and 8.
4. **`/design` ships ungated today** (`r1` F13/OQ5). Fixing it is out of this RFC's scope but is
   the same defect class decision 3 prevents — file it as its own issue?
5. **Port default** `5199` is a proposal; any collision policy preference (fail vs increment)?

| Risk | Basis | Mitigation |

| Generated-root drift / stale regeneration | registry writes today are non-transactional and leak on remove (`r4` F3/F10 via S-16) | Transactional staged→check→swap for `.netscript/devtools/` regeneration; provenance headers |
| A2 label flips to A3 late if T5's streaming contract gives the host supervised subscriptions | `06-archetypes.md:348-367` pick-the-larger; F-13 delta (`b2` F3) | Decision 5 pre-declares the trigger and the consequence; T5 must keep live-view lifetimes request-scoped or accept F-13 |
| Auth gate must cover the Vite dev-server's own endpoints (HMR WS, `/@fs`) when non-loopback, not only the Fresh routes | the dev middleware passes Vite URLs through untouched (`dev_server.ts` `IGNORE_URLS`) | T6 scope; T1's loopback default keeps the risk out of the default path |
