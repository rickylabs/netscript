# Research — #1371 aspire-service-reference-verification

Verify-first. The wave-6 claim under test: `BackgroundProcessors.<name>.ServiceReferences` is
parsed from appsettings but **never injected** into the background resource.

## Repro vehicle

Installed-consumer surface per closed #1343: a clean root outside the framework checkout,
`deno run -A --minimum-dependency-age=0 jsr:@netscript/cli@0.0.7-canary.1`, no local-source
fallback. Root `/home/codex/repos/ns-verify-1371`. Canary presence confirmed against the JSR meta

## Finding 1 — the default scaffold emits no `ServiceReferences` at all

Generated `appsettings.json` `NetScript.BackgroundProcessors`:

| Processor | `ServiceReferences` | `PluginReferences` |
| --- | --- | --- |
| `sagas` | **absent** | `sagas-api`, `streams`, `workers-api` |
| `triggers` | **absent** | `streams`, `triggers-api`, `workers-api` |
| `workers` | **absent** | `streams`, `workers-api` |

`Services` = `users`; `Plugins` = `sagas-api`, `streams`, `triggers-api`, `workers-api`.

This matches the issue's hypothesis (c) — a path where `serviceReferences` is never written onto
the background entry — but as **configuration shape, not a defect**: the official plugins declare
peer *plugin* references, not service references, and
`appsettings-entry-builders.ts:77-79` only writes the key when the option is non-empty. The literal
wave-6 claim therefore cannot even be exercised by an unmodified scaffold, which is likely part of
why it went unreproduced for so long.

## Finding 2 — injection exists for both reference kinds (claim refuted at the generator)

`aspire/.helpers/register-background.mts`, generated by the published canary, emits under
`// Plugin references — wired via endpoint env vars`:

```ts
const sagas_apiEndpoint = await _plugins.get('sagas-api')?.getEndpoint('http');
if (sagas_apiEndpoint) {
  await sagas.withEnvironment('services__sagas-api__http__0', sagas_apiEndpoint);
}
```

To exercise the `ServiceReferences` path specifically, `workers.ServiceReferences = ["users"]` was
added to appsettings and `generate aspire --project-root .` re-run (note: `generate plugins` does
**not** regenerate AppHost helpers — only `generate aspire` does). The helper then emits:

```ts
// Service references — wired via endpoint env vars
const usersEndpoint = await _services.get('users')?.getEndpoint('http');
if (usersEndpoint) {
  await workers.withEnvironment('services__users__http__0', usersEndpoint);
}
```

**The claim "parsed but never injected" is refuted at the generator level on the published canary.**

## Finding 3 — emitted key uses the raw resource name

Every emitted key uses the resource name verbatim, including hyphens:
`services__sagas-api__http__0`, `services__workers-api__http__0`,
`services__triggers-api__http__0`. This is the hypothesized mismatch surface; whether it is an
actual defect depends on what Aspire itself exports for a hyphenated resource, which the runtime
phase measures.

## Finding 4 — the unresolvable reference is silent (candidate defect)

`triggers.ServiceReferences = ["ghost-service"]` (no such service) regenerates to:

```ts
const ghost_serviceEndpoint = await _services.get('ghost-service')?.getEndpoint('http');
if (ghost_serviceEndpoint) {
  await triggers.withEnvironment('services__ghost-service__http__0', ghost_serviceEndpoint);
}
```

`_services.get(...)` returns `undefined`, the guard is false, **nothing is emitted, nothing is
logged, and the AppHost does not fail**. The child starts with the env var simply absent. Acceptance
box 6 requires the opposite: an unresolvable declared reference must fail or degrade *visibly*
rather than start with a missing env var. Runtime confirmation pending.
