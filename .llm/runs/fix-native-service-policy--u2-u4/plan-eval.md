D-U4-7 (plan §B owner 5; decisions §C) specifies `installHealth()` only as "guarded by healthInstalled, like installAuth/installDeferredRoutes". This leaves two load-bearing questions unflagged: (a) whether registration is conditional on captured `healthConfigured` (without it, EVERY built service gains health routes — silent opt-in breakage); (b) the flag order — installAuth's mark-before-work shape is exactly what root's atomicity section condemns as fail-open for auth, so "like installAuth" is now ambiguous between the condemned shape and the mandated prepare-then-mark shape. A faithful naive implementation (`if (healthInstalled) return; healthInstalled = true; if (!healthConfigured) return; register…`) additionally drops late `withHealth()`-after-build silently (works today via immediate registration). No planned proof row distinguishes any of these cases: the matrix has no "no withHealth ⇒ /health not registered" row and no late-config row, so the defect would pass planned tests and be caught only by whole-suite luck (unverifiable from packet) or in production. Required fixes 1–2 lock the predicate and the proofs. Minimal, mechanical, no architecture change.
