## Decisions

1. **Lifecycle and intake.** Core-owned named WorkerLifecycleState is idle/running/paused/draining/stopped. Worker exposes pause()/resume(), isPaused, and its health snapshot lifecycle. Pause requests intake cancellation synchronously, leaves all admitted jobs/tasks/trigger jobs and lease renewal running, and keeps start() pending. Each listener supervisor owns a separate attempt AbortController and a pause barrier. Its long-lived run loop parks after the old queue.listen generation drains; resume starts the next generation only after that barrier, preserving concurrency and queue reuse. A committed claim racing pause/drain is handed back without running a new user handler. A claim already committed before pause is handed back as an ordinary charged requeue; only draining/shutdown handback preserves its attempt, pinned by an S4 raced-claim test. Pause is intentional healthy idleness, not a crash/restart: preserve restart counters and failure history; failed supervisors cannot be revived by resume. Worker.stop is idempotent, concurrent callers share completion, stop is terminal for that Worker instance; replacement uses a new instance as the runner is already terminal on current main. Pause before start/after stop and resume while draining/stopped are harmless no-ops; repeated pause/resume are idempotent. No queue closes and no runner shutdown during pause.

2. **Two-phase bounded stop.** drainTimeoutMs is the TOTAL Worker.stop budget, default25,000ms. abortGracePeriodMs defaults min(5,000ms, floor(drainTimeoutMs/5)), therefore5,000ms for the default total; standalone core runner uses that same default5s. Validate finite safe integer milliseconds, total1..2,147,483,647, grace0..total. Reserve min(1,000ms, max(1ms, floor(total/25))) for queue/listener settlement and close. Work may finish without cancellation until total minus grace minus that reserve (default19s); abort leftovers only then, await runner cleanup/listener generation barriers within the remaining grace, then stop owned queues within the reserve. Use one monotonic deadline, never restart each timeout. Work that completes in the first phase follows normal success/idempotency/ack. Task listeners are included through their generation barriers, including executor and registry/state work before any activeJobs entry. Cancellation/individual deadlines remain immediate with the configured grace. Core runner standalone default5s is documented against this25s worker total and the queue's30s listener drain; the process-level parent budget has at least5s headroom. Larger configured worker budgets require a correspondingly larger process drain budget and are documented. A hung executor/storage/close makes stop reject TimeoutError within the total bound; in-process JavaScript cannot be physically killed and late results cannot mark success after abort. Existing executable parent shutdown owns eventual process termination.

3. **Clock contract.** The core-owned WorkerDrainClock port has monotonic now() and disposable schedule(delayMs,callback), structurally reusing the scheduler method from JobRunnerClock without changing that port's epoch-time meaning. Web Platform default uses performance.now and owned/cleared setTimeout. Worker accepts this clock as an optional direct-composition seam; standard config stays data-only. Core owns the duration/default resolver and bounded drain lifecycle primitives; the plugin wires listeners, runner and queues. Use the existing core ./shutdown public subpath for the new lifecycle/budget primitives and types, avoiding extra runtime/root barrel growth. The existing generic ShutdownManager lacks the two-phase work/abort/settlement contract and is left unchanged. No generic lifecycle registry or dependency added. Tests use manual advancement for boundary/race cases, plus real-time cleanup>1s and actual broker oracles.

4. **Configuration and runtime.** Add drainTimeoutMs/abortGracePeriodMs to WorkersConfigData, authoring input, shared schema and direct WorkerOptions. Defaults come from the same core policy. Load the authored workers section through the existing loadConfig plus WorkersConfigSchema path before runtime dependencies. Move the existing CLI loadWorkersConfig implementation into src/runtime/workers-config.ts and retain the CLI file as an identity forwarding shim; bin/runtime.ts must not import a CLI implementation. startWorkerProcess and startCombinedProcess both accept explicit budget overrides, otherwise use validated project config, otherwise defaults. Forward grace through Worker into the actual WorkerPool/InProcessJobRunner even when no static registry exists. Explicit direct WorkerOptions.abortGracePeriodMs wins over the legacy workerPoolOptions value; legacy pool-only customization remains supported when the top-level value is absent and is validated against total budget. Generated glue delegates to the same startCombinedProcess and requires no second resolver. A subprocess using a real project config and real handler proves standard startup/forwarding, not a string search or fake runner.

5. **Queue handback contract.** Add optional NackOptions.preserveDeliveryCount, false by default and effective only for requeue:true. It refunds exactly this live delivery, never arbitrary historical attempts; next delivery sees the same count. It bypasses max-deliveries exhaustion and failure backoff for this handback only, retaining message identity, original enqueue time, payload, headers, queue and ordering/delay metadata. requeue:false ignores preservation and retains terminal policy. Existing ordinary explicit/implicit failures and crash/expiry reclaim still charge. Duplicate and stale settlement must not refund a newer claim or enqueue duplicate copies. Worker requests preservation only for its controlled shutdown cause (first cause ShutdownError), never merely because a stop happened concurrently with a business error, timeout, lease loss, duplicate claim, state/DLQ outage or operator cancel. Preserve existing error propagation/retry behavior for those paths.

6. **Adapters.** Redis/Garnet: existing atomic receipt Lua transition fences ownership/expiry, selects refunded encoded envelope only for explicit handback, removes the receipt once, and never changes expiry/reclaim/DLQ/outbox behavior. No new commands; declare all existing script keys. Postgres: one fenced UPDATE decrements the current delivery and unlocks it atomically before any max-retry decision. Generate an opaque per-claim locked_by receipt (existing column) and carry it through context settlement; guard against expired/replaced receipt and repeated local calls. Normal requeue remains counted. KV polling: extract internal message/key and settlement concerns into _kv-polling/message.ts and settlement.ts, keeping the currently811-line adapter below800 and not deepening the warning unnecessarily. CAS checks the stored processing entry and a fresh per-claim identity, then atomically moves to pending with attempts minus1 for handback; preserve failure delay/count/DLQ behavior. Successful explicit settlement must suppress the existing unconditional automatic ack/nack. Recovery retains its charged attempt and must not settle a replacement. Prefer existing kv.atomic; retain and document the existing single-consumer best-effort fallback when a caller supplies a KV without atomic support (no stronger concurrency guarantee is claimed there). Memory: per-delivery settlement guard, refund once, pending identity stable. Deno KV: explicit requeue and a thrown handler failure must actually enqueue the same addressed envelope before returning so the native dispatcher can acknowledge the old delivery; count is previous/current according to preservation. An explicit settlement prevents another automatic settlement; propagate failed persistence to the native retry path without acknowledging. Current nack is a no-op, so remove the worker's extendVisibility requirement only once portable handback works. A transport failure before the retry metadata can be committed retains the native unacknowledged recovery path; ordinary user-handler failures use the counted enqueue-before-ack path. Document crash/outage limitations honestly. AMQP: existing wrapper leaves Fedify native retry disabled (upstream double-acks Promise handlers) and does not pass queueName. Set native retry and queue name for publishing, and consume through the existing upstream amqplib channel so intake cancellation uses basic.cancel while admitted handlers settle before channel close. Use native prefetch for concurrency and one terminal ack/nack path, with same-envelope explicit requeue/count preservation. On handler failure publish counted retry before acknowledgement; a publish failure retains native unacked/redelivery behavior. No new transport abstraction or dependency; stop closes only the adapter-owned channel/connection. This is necessary for portable worker pause/handback, not a new AMQP feature set. Durability remains at-least-once. The pinned Fedify publisher does not wait for broker confirmation, so handback/counting retries use the already installed amqplib createConfirmChannel/sendToQueue callback and acknowledge the old delivery only after broker confirmation. Publish failure nacks the old live delivery; disconnect closes/requeues the unacked claim. Keep the existing public delayed-enqueue path; no new publisher abstraction.

## Risk register and mitigations

- Queue stop can wait on handlers while pause must return: attempt pause barrier is separate from supervisor lifetime; public pause requests cancellation without joining admitted handlers. Resume waits old generation before listening again. Test no over-admission and start lifetime.
- Task dispatch lacks activeJobs bookkeeping: generation barriers include whole task callback, so work drain covers tasks without introducing a fake job map entry.
- Concurrent initial startup/stop/pause: own controllers/state before awaits, drain allocations exactly once; tests stop during initialization and queued last claim. Start errors must release owned resources; no swallowed fatal listener errors.
- Shutdown attribution race: first cause and typed reason gate preservation; negative business failure/deadline/cancel/lease-loss controls. Idempotency key remains stable because refunded delivery count stays stable; release interrupted claim before replacement processing.
- Atomic refund abuse/races: opt-in only, fenced receipt/claim token, local settlement once, atomic count+move, duplicates/stale receipts no effect; preserve terminal nacks. CAS/publish failures must leave durable ownership/retry, not report successful handback.
- AMQP baseline is broken before oracle: native upstream channel lifecycle and publisher confirmation inspected/tested with owned RabbitMQ, include failure/deadline/disconnect/pause cases; no claim that raw main passes accounting. Keep change within handback/intake prerequisite.
- Default inner/outer timing:25s total leaves5s within main child30s work; future combined runtime PR35total/30work keeps same headroom. Work19s, cleanup5s, settle1s. One monotonic bound. Customization docs require parentbudget >= worker total + external cleanup.
- F-1/F-16: baseline Worker463, KV polling811, Postgres581. Extract affected polling settlement (no new module at adapters root except one cohesive _kv-polling directory); reduce big touched files, no broad unrelated refactor or numeric exemption. Existing adapters cardinality debt records the one new concern directory with rationale and closing gate. Test files<480. Existing public type closure debt not deepened.
- JSR/slow types: explicit owned interface/data types and return annotations; no exported Zod implementation, broad any/casts, new dependency, lock change, or root/sub-barrel mirrors. Runtime/core additions exported only from appropriate existing subpath, no new package export. Run doc-lint all affected subpaths and compare existing baseline diagnoses, publish dry-run/audit and consumer type contracts; any new diagnostic is a failure. Core/plugin flat surface baseline recorded as debt if encountered, no waiver by analogy.
- Expensive runtime resources: full scaffold smoke only at end; local remote Docker is unsupported by native Aspire guard, so use supported runner rather than bypass/bridge. Positive ownership IDs for backend containers, read-only leak report and teardown preview before cleanup; foreign resources untouched.
