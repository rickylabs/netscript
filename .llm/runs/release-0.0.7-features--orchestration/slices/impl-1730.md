## What this issue is, and what it is not

#1730 is a **regression-net** issue, not a product defect. `#1694` shipped correct code and is merged
at `21d516224`. At the merged head `agent/loop.ts` has exactly two consumers of `input.context` —
`:162` the `context:` field and `:250` tool options — and touches no message or system text. **Do not
"fix" the loop.** If you find yourself changing product behaviour, stop and re-read this paragraph.

The gap is that a promise has no tripwire. `RequestContext` exists to reach TanStack
`chat({ context, metadata })` and tool handlers and **nothing that reaches a provider**. That negative
invariant is guarded at the *adapter* boundary but not above it in the loop. The #1696 IMPL-EVAL
proved it by mutation in a throwaway worktree at `414a52ba8`:

| Mutation | Result |
| --- | --- |
| **A** — bridge folds `request.context` into `modelOptions` (`tanstack-chat-client.ts:180`) | 2 named tests FAIL |
| **B** — **loop** appends `JSON.stringify(input.context)` to `system` (`loop.ts:158`) | **none — 9/9 still pass** |
| **C** — loop stops passing `context` to tool dispatch (`loop.ts:250`) | 2 named tests FAIL |

**Mutation B is the gap you are closing.** The loop test `threads the run context into every
ChatClientRequest` (`packages/ai/tests/request_context_test.ts:302-321`) asserts
`request.context === CONTEXT` but never asserts the sentinel is **absent** from the other four fields
of `provider.requests[*]`.

There is a second, narrower gap in the same area: the `never reaches the Anthropic provider wire
request` test **cannot detect mutation A**, because the Anthropic adapter drops unknown `modelOptions`
keys itself — so it passes whether or not the bridge leaked. It is weaker than its name claims.
