## Carried obligations from the S2 review — close both

- **S2-N1 — a field whose non-empty case can never occur.** `PluginCliCapabilityGrant` (RFC 275–279)
  declares `requested`, `granted`, and `denied`, and that grant reaches plugin code through
  `PluginCliInvocationContext.grant` (562) and `PluginCliGenerationContext.grant` (757). But line 594
  makes denial fatal *before* the handler or planner is imported, so in any grant a plugin can
  observe, `denied` is always empty and `granted` always equals `requested`. Three fields carry one
  field's information and the RFC never says where a non-empty `denied` is seen. This is the defect
  class `milestone-run.md` § Gate integrity calls the signature failure of this kind of work — a
  guard whose predicate can never fire, which looks correct while doing nothing. Resolve it exactly
  one of three ways and say which: (a) the grant type is shared with a host-side diagnostic path
  where `denied` is non-empty — then state where; (b) narrow the plugin-facing context to `granted`
  alone; or (c) record that in contract major 1 a plugin-visible grant always has `denied === []` and
  `granted === requested`, with the forward-compatibility reason for keeping the shape.
- **S2-N2 — text-only generation.** `PluginCliGenerationOperation.content` is a `string` and plan
  contents are fixed as UTF-8 text, so a contributed generator cannot emit a binary asset. Defensible,
  but name it in `## Drawbacks` alongside the other accepted costs rather than leaving it to be
  discovered.
