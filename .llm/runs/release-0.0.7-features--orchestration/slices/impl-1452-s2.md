## The ruling — this is the design, do not re-open it

**`@netscript/plugin` must NOT gain a concrete dependency on `@netscript/kv`.** The host boundary is
preserved. Instead:

- **`@netscript/plugin` publishes a structural, injected factory.** It owns the generic parts: lazy
  memoisation and composition over **caller-supplied async DB and KV resolvers**, plus contracts,
  logger, and env assembly.
- **The CLI host supplies the adapters.** The scaffolded template imports `@netscript/kv` itself and
  passes `getKv`; it also passes its project-relative `getDatabaseClient`.

The resolvers are typed **structurally** — a function returning a promise of the thing — never by
importing the adapter package. That is what satisfies "reusable lazy DB/KV" without coupling the
plugin contract package to an adapter.

## What Slice 1 already did — do not redo it

`createLazyKv()` is published from `@netscript/kv` and the template dropped 123 → **43 lines**. What
remains in `packages/cli/src/kernel/assets/plugins/service-context.ts.template` is exactly the
injectable part:

- `getDatabaseClient()` — a **project-relative** `await import('../../database/mod.ts')`, which no
  published package can resolve. It must stay in the template and be **passed in**.
- `createPluginServiceContext(pluginName)` — assembles `{ db, contracts, kv, logger, env }`. This
  assembly is the generic part that moves into `@netscript/plugin`.

## What to build

already lives — `@netscript/plugin/sdk` — unless doctrine says otherwise; justify the placement).

It takes caller-supplied resolvers and returns the assembled context, memoising each resolver so
repeated access resolves **once**. Prove laziness **by observation**, exactly as Slice 1 did for
`createLazyKv`: zero resolutions at construction, exactly one after repeated use — not merely that
values come back correct.

Then reduce the template to importing the factory and supplying its two resolvers plus the plugin
name, and regenerate the `embedded.generated.ts` carrier from tooling.
