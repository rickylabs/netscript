## Scope

`createOpenAPISpec` (`packages/service/src/primitives/openapi.ts`) currently delegates straight to
`OpenAPIGenerator.generate()` and supplies only `info`/`servers` — it never reads procedure access
metadata (research finding 11). This slice **post-processes the generated spec**: for each operation,
look up its originating procedure's `~orpc.meta.access` (from #1466/Slice 1's vocabulary) and inject
the corresponding OpenAPI `security` entry, adding a bearer security-scheme component only when at
least one operation needs it. **Preserve every existing user-supplied OpenAPI field** — this is
additive post-processing, not a rewrite of the generator's output.

**The exact mapping, locked by LD-9 — do not improvise a different one:**

- `authentication: 'none'` → operation `security: []`.
- `authentication: 'required'` → a default bearer security-scheme requirement on the operation;
  declared `authorization.scopes` go inside that requirement; declared `authorization.roles` — which
  OpenAPI security schemes cannot express portably — go in a documented `x-netscript-roles` extension,
  not inside `security`.
- `authentication: 'optional'` → `security: [{}, { bearerAuth: [] }]` — **even though the runtime
  authorizer rejects `optional` at construction (LD-8).** This is deliberate: the contract's
  declaration must be visible in the generated docs regardless of runtime support. Do not suppress it,
  and do not make this slice enforce LD-8's rejection — that already happens elsewhere.
- No metadata on a procedure → no `security` field added; leave the operation exactly as the
  generator produced it.

**Matching operations back to procedures.** oRPC exposes a public traversal API for exactly this —
research finding 10 points at `deno doc --filter traverseContractProcedures jsr:@orpc/server`. Inspect
it yourself before writing a traversal; do not reinvent one that duplicates
`contract-authorizer.ts`'s private router-walk (that file is **not** on this slice's ceiling and must
not be imported from or copied).
