## Scope — this is genuinely partial, state it honestly

`KvExecutionState`'s `queue`/`start`/`complete` methods all follow one pattern:
`#transition(executionId, updates) → #save() → persist to KV + invoke the mutation hook`. That
mutation hook is already wired (via `createStreamMutationHook`) to publish to the durable workers
execution stream. **Add a `progress()` method following the identical pattern** — this makes
progress persistence and publication possible using machinery that already exists, with zero new
plumbing. **This slice does not wire `ctx.reportProgress()` (called from inside a running job) to
this new method** — that runtime message-passing path was searched for during research and not
found; see `research.md`'s LD-4 for the narrow exception if you find it's trivially simple, and stop
+ report in `drift.md` if it's not.

**Exact locked decisions — see `plan.md` LD-1 through LD-4, do not deviate:**

1. Add `progressPercent: number | null` and `progressMessage: string | null` to
   `ExecutionRecordShape`/`ExecutionRecordSchema`/`ExecutionRecord`
   (`packages/plugin-workers-core/src/domain/job-definition.ts`) — **nullable, not optional**,
   matching this file's own convention for `startedAt`/`error`/`result`.
2. Add `KvExecutionState.progress(executionId: string, percent: number, message?: string):
   Promise<ExecutionRecord | null>` calling `#transition(executionId, { progressPercent: percent,
   progressMessage: message ?? null })` — identical shape to `queue`/`start`.
3. Thread both fields through `streams/schema.ts`'s `WorkerExecution` type + Zod schema and
   `streams/producer.ts`'s `WorkerExecutionRecord` type + `toExecutionStreamEntity()`.
4. Do not touch `runtime/messages.ts`, `job-dispatcher.ts`, `in-process-job-runner.ts`,
   `job-context.ts`, `runtime-types.ts`, or `public/root.ts` unless you find a genuinely trivial,
   already-existing one-line wiring path (LD-4's narrow exception) — not a new subsystem.
