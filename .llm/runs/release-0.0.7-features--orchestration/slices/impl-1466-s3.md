## The two documentation defects this slice carries

### G-4 (IMPL-EVAL cycle 2, low) — docs point at a symbol that is no longer public

`commonErrorMap`'s **value** export was withdrawn in slice 1 by ruling R-2/F-1. Two places still
describe things by reference to it, so a reader of the public reference is sent to a symbol they
cannot find:

1. `docs/site/reference/contracts/index.md` — the `CommonErrorMap` row describes the type as the
   "public shape of `commonErrorMap`".
2. `packages/contracts/src/application/contract-primitives.ts` — a `{@link commonErrorMap}` in
   **public** JSDoc.

Fix both by describing the type **on its own terms** — e.g. "the standard NetScript error map carried
by every base route, whose codes, HTTP statuses, message literals and data schemas are the stable
compatibility contract" — and drop the `{@link}` to the private value. Do **not** re-export the value
to make the link valid; that would reopen F-1, which is a doctrine-04 violation, not a docs choice.
`deno doc --lint` does not flag this, which is exactly why it needs a human-written fix.

### AF-1 (supervisor Tier-A on slice 2, low) — the G-1 anchor is brittle on correct code

The declaration-anchored pin in `packages/contracts/tests/assertion-budget_test.ts` spans
`baseContract`'s type annotation with `[^=;]+?`. It works today, but it goes **red on correct code**
the moment that annotation contains a `=` or `;` — a default type parameter (`<T = X>`) anywhere in
the `ContractBuilder` generics would do it.

The hazard is not the false positive; it is the **repair someone will reach for**: loosening the
regex back toward the file-wide form that G-1 was raised to remove. Add a comment in that test naming
the trap and stating the correct response (widen the annotation span, never drop the
`export const baseContract` anchor). **A comment only — do not change the pattern**, and re-run the
contracts suite to prove the pin still passes and still goes red under the decoy forgery.
