## Scope

Add a typed generation-options mapper for the OpenAI **Responses** API request shape, alongside the
four existing sibling mappers in `packages/ai/src/adapters/openai-compatible.adapter.ts`
(`anthropicGenerationModelOptions` lives elsewhere; the direct siblings in *this* file are
`openAiCompatibleGenerationModelOptions`). This is **request-shape mapping only** — see "explicitly
out of scope" below.

**The exact mapping — verified against the official OpenAI Responses `create` reference, do not
improvise a different one:**

```ts
export function openAiResponsesGenerationModelOptions(
  options: GenerationOptions,
): Readonly<Record<string, unknown>> | undefined {
  const modelOptions: Record<string, unknown> = {};
  const effort = options.reasoningEffort;
  if (effort !== undefined && effort !== 'off') {
    modelOptions.reasoning = { effort };
  }
  if (options.maxOutputTokens !== undefined) {
    modelOptions.max_output_tokens = options.maxOutputTokens;
  }
  return Object.keys(modelOptions).length > 0 ? modelOptions : undefined;
}
```

(This is a sketch to anchor the exact field names — `reasoning: { effort }` nested,
`max_output_tokens` — not necessarily the exact code layout; follow the file's existing style and
doc-comment conventions, matching `openAiCompatibleGenerationModelOptions`'s own JSDoc shape.)

`'off'` omits the `reasoning` key entirely, exactly like every existing mapper's convention (no
provider has a wire "disable" value, so the field is simply absent and the model default applies).

**Wire the selection.** `OpenAiCompatibleModelProvider.createChatClient` currently passes
`mapModelOptions: openAiCompatibleGenerationModelOptions` unconditionally to `toTanstackChatClient`.
Change this to select `openAiResponsesGenerationModelOptions` when `this.#config.api === 'responses'`,
and keep `openAiCompatibleGenerationModelOptions` for `undefined` or `'chat-completions'` — the
existing default behavior for every current caller must not change.

## Explicitly out of scope — do not widen this

The OpenAI Responses API's **response**/streaming shape is a discriminated-union item array
(`message` items with `content` parts, `function_call` items carrying `call_id`/`name`/`arguments`,
etc.) and a distinct set of streaming events (`response.output_item.added/done`,
`response.output_text.delta/done`, ...) — structurally different from Chat Completions' streaming
deltas. **This slice does not touch response parsing, streaming event handling, or
`toTanstackChatClient` at all.** Whether the underlying `@tanstack/ai-openai/compatible` package
already handles that correctly when `api: 'responses'` is configured is unverified and explicitly not
this slice's concern — see `research.md`'s "Response-side complexity" section. If you find evidence
it does NOT handle it correctly, **stop, record it in `drift.md` as a finding, and report** — do not
attempt to fix it here.
