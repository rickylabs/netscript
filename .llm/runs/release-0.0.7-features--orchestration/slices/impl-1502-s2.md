## Scope — the S2 normative sections

Complete these in `rfcs/0000-plugin-cli-contribution.md` without changing the S1 ownership boundary:

1. **Discovery and generated-registry lifecycle** — explicit pointers over ambient scanning (the RFC
   already rejects `node_modules` scanning; make the accepted mechanism normative). When the registry
   is generated, what invalidates it, how staleness is detected, and what happens when it is missing
   or older than the manifest.
2. **Selected-handler async bootstrap** — when a handler module is imported, what may run at import
   time, cancellation and deadline ownership, and the `bootstrap-timeout` path. Only the *selected*
   handler is imported; help, completion, and validation must remain import-free, as S1 requires.
3. **Isolation and plugin-absent UX** — the failure boundary around plugin code, what
   `handler-unavailable` and `plugin-absent` mean concretely, and how an optional command that is not
   installed presents to the user. Keep the S1 rule that thrown values are not public contract.
4. **Capabilities** — the concrete `PluginCliCapability` union whose placement S1 fixed and whose
   values S1 deliberately did not improvise. Declare it now, with grant semantics and the
   `capability-denied` path.
5. **Host-owned generation transaction** — staging, validation, atomic commit and rollback,
   preview/no-write, and the `plan-invalid` / `commit-failed` codes. Mutation stays host-owned; a
   plugin contributes a plan, never a write.
6. **Doctor integration and manifest/pointer ownership** — what doctor checks, what it reports, and
   who owns the manifest pointer.

Reuse the S1 vocabulary and the reserved diagnostic codes rather than minting parallel ones. Where a
decision belongs to S3 (compatibility, deploy supersession, duplicate audit, epic roadmap), say so
explicitly the way S1 declared its gaps — an explicit gap, never implementation discretion.
