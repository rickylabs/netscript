### Locked decision 1 — Bounded retry policy (`KvWriteRetryPolicy` / `SettlementRetryPolicy`)
Applies **only** to `known_uncommitted_transient` local SQLite write contention failures:
- `maxAttempts: 6` (1 initial attempt + at most 5 retries)
- `maxTotalTimeMs: 2_000` (monotonic **retry-start deadline** checked both before and after backoff; no retry begins at or after `start + maxTotalTimeMs`, returning/throwing the last failure on expiry; an already-started backing write runs to completion unless the operation itself supports cancellation)
- `baseDelayMs: 15` (exponential ceiling: `15, 30, 60, 120, 240` ms)
- `maxDelayMs: 250` (per-wait cap)
- Jitter: equal jitter in `[ceiling / 2, ceiling]` (at least `1` ms); if `jittered >= remainingMs` before sleep or `now() >= deadline` after sleep, stop immediately without retrying
- Abort-aware: checks `AbortSignal` before every attempt and after sleep, uses abortable sleep (`delay(ms, { signal })`), and aborts immediately without another attempt if cancelled.

### Locked decision 2 — Commit-outcome classification (`WRITE_FAILURE_CLASS` / `SETTLEMENT_FAILURE_CLASS`)
Every storage write outcome classifies into a closed vocabulary before deciding retry vs verify vs fail:
1. `committed`: write fulfilled (`void` or `{ ok: true }`). Proceed normally.
2. `cas_conflict`: atomic check refused (`{ ok: false }`) or CAS/claim-loss conflict error (`Worker idempotency claim lost`, `CasConflictError`, `CAS_CONFLICT`, `ATOMIC_CHECK_FAILED`, atomic check / versionstamp conflict). **Never retried as transient.** Preserved as a conflict immediately; never causes blind replay or false dead letter.
3. `known_uncommitted_transient`: local SQLite lock/busy error before commit — walking `error` and `error.cause` (depth <= 8, cycle-safe) for SQLite busy/locked codes (`SQLITE_BUSY*`, `SQLITE_LOCKED*`) or messages (`database is locked`, `database table is locked`, `database schema is locked`), explicitly giving precedence to CAS conflicts, abort/shutdown/timeout/lease-loss, **any explicit non-busy SQLite error code** in `error.code` or message tokens (e.g., `SQLITE_IOERR_WRITE`, `SQLITE_IOERR_FSYNC`, `SQLITE_CORRUPT`, `SQLITE_FULL`), closed-handle errors (`BadResource`, `KvClosedError`), and ambiguous markers (`ambiguous`, `uncertain`, `commit outcome`, `outcome unknown`, `after commit`). Retried only within the locked bounded retry policy.
4. `aborted`: `AbortError`, `ShutdownError`, `TimeoutError`, `QueueLeaseLostError`, or aborted `AbortSignal`. Never retried; surfaces immediately to preserve #2645 cancellation and shutdown handback semantics.
5. `unknown_commit_outcome`: default for every other failure where commit status is unknown (explicit non-busy SQLite codes, I/O error, interrupted write, generic outage). **Never triggers a blind write replay or blind effect replay.**
   - `DenoKvAdapter` / `KvQueueDispatcher` writes (`enqueue`, `nack({ requeue: true })`, routing hops, parking, cancellation handbacks): never blindly retry `unknown_commit_outcome`, and `DenoKvAdapter.createContext` retains any attempted `settlement` promise so a failed explicit `nack` never issues a second counted `nack`. Unsettled callbacks reject so Deno KV's native recovery retains the unacknowledged source receipt (at-least-once transport; enveloped deliveries retain `messageId` for consumer deduplication; distinct raw non-envelope legacy payloads always receive fresh unique UUIDs).
   - `KvDeadLetterStore.append`: O(1) read-only `identityKey` verification confirming it points to `recordKey`.
   - Worker `idempotency.markApplied`: read-only owner-token commit verification inside `KvWorkerIdempotencyStore.markApplied` (`kv.get(appliedKey)` checking `applied.value.token === token`, zero extra mutations, keeping CAS `{ ok: false }` as a conflict).
   - Worker `executionState.start` / `executionState.complete`: read-only lookup via internal `ReadableExecutionState.get?` checking `row?.status === expectedStatus`.
   - Post-success latch (`executionSucceeded === true`) + best-effort diagnostics: completion span events (`addJobStepEvent`), metrics (`recordSharedWorkerMetrics`), task completion logging, secondary diagnostic reporting (`logPostEffectSettlementFailure`), and queue consumer tracing (`TracedQueue` span completion/end) are best-effort after success so no diagnostic fault overwrites a completed row, dead-letters, releases the claim, or triggers a counted `nack` (direct worker callers without `queueContext` still reject with the original primary error).

### Locked decision 3 — Local Deno KV whole-delivery concurrency, cancellation & drain
- `KvQueueRegistration` (`packages/queue/adapters/_kv-queue/routes.ts`) bounds concurrent deliveries to `concurrency` (default `1`) across the entire `DenoKvAdapter.deliver()` promise (handler + `ack`/`nack`).
- Excess deliveries arriving from `Deno.Kv.listenQueue` queue FIFO in `#waiters` while holding their native `listenQueue` delivery unacknowledged.
- Slot handoff on delivery completion is atomic: `#releaseSlot()` starts the next waiter synchronously and adds it to `#activeDeliveries` before the finishing delivery is removed, so `#active` never exceeds `concurrency` and `settle()` never observes an empty gap.
- `KvQueueRouteTable.next(queueName)` prefers a registration with `hasCapacity` in round-robin order before falling back to round-robin across saturated registrations.
- On cancellation (`signal.abort()`, `stop()`, `close()`, or loop failure), `registration.close()` immediately rejects future/queued admissions (resolving queued waiters with `admitted = false`) without cancelling already-admitted deliveries; `registration.settle()` drains only admitted deliveries.
- Unadmitted deliveries (`admitted === false`) re-enter `KvQueueDispatcher.#route`:
  - If another registration for the same queue name exists, deliver immediately.
  - Else if other queue names remain registered, `#reroute` as before.
  - Else (`#routes.isEmpty`):
    - On non-dedicated loops (`:memory:` / caller-owned `Deno.Kv`), park with `policy.parkDelayMs` as before.
    - On dedicated file-backed loops (`dedicatedListener === true`), wait until either a new listener registers (0 ms handoff) or all admitted deliveries finish draining, then durably re-enqueue the unchanged envelope (`messageId`, `deliveryCount`, `headers`, `routingHops` preserved) with a short handback delay (`min(25 ms, policy.parkDelayMs)`) **before** resolving the native `listenQueue` callback (crash-safe publish-before-ack; avoids the 5 s park stall on pause/resume while keeping the closing loop from reclaiming the handback).

## Acceptance Box 3 — Owner Decision Analysis (Fix round 4)

IMPL-EVAL round 4 confirmed Acceptance boxes 1 and 2 are satisfied and surfaced an irreducible tension in box 3 ("Recovery from that persistence error avoids a false dead letter and a repeated successful external effect. Preserve the existing pause, acknowledgement and redelivery semantics from #2645") when post-effect persistence fails permanently or with an unconfirmed `unknown_commit_outcome`. No new post-effect recovery contract was implemented in round 4; both failure classes are documented below for owner disposition.

### Case (a) — `idempotency.markApplied` IS durable; `executionState.complete` is unconfirmed
- **Reproduced sequence:** File-backed KV, one queued job with stable `idempotencyKey`, live `DenoKvAdapter` listener (`concurrency: 1`). `idempotency.claim()` commits active marker; `executionState.create()` & `start()` set row to `running`; external provider executes once (`providerEffects: 1`); `idempotency.markApplied()` commits durably (active marker removed, applied marker with owner token persisted); `executionState.complete({ status: 'completed' })` fails pre-commit (`SQLITE_IOERR_WRITE` or exhausted retries) and read-only `executionState.get()` confirms row is still `running`.
- **Observed state at `0b4a6e978`:** `job-dispatcher.ts` enters `if (executionSucceeded)` catch, reports best-effort, and returns `undefined` to `DenoKvAdapter.deliver()`, which auto-acknowledges the native receipt. Final durable state: `providerEffects: 1`, `writeAttempts: 1` (`SQLITE_IOERR_WRITE`), `deliveries: 1`, `execution row: running` (`0` completed, `0` failed), `active marker: 0`, `applied marker: 1`, native ready/running tables empty, `DLQ: 0`.
- **Recovery feasibility:** Because the applied marker IS durable, **completion-only recovery is possible without re-calling the provider**: a redelivered message or completion reconciler can observe `{ claimed: false, alreadyApplied: true }` and finalize the `running` execution row to `completed` without invoking the provider again.

### Case (b) — `idempotency.markApplied` is unconfirmed (NO durable proof of provider outcome)
- **Reproduced sequence:** Same file-backed KV fixture. Provider executes once (`providerEffects: 1`); `idempotency.markApplied()` fails pre-commit with `SQLITE_IOERR_WRITE` (1 write attempt) or exhausts all 6 SQLite busy retries; read-only verification inside `KvWorkerIdempotencyStore.markApplied` reads `null` (no matching applied marker).
- **Observed state at `0b4a6e978`:** `job-dispatcher.ts` enters `if (executionSucceeded)` catch, reports best-effort, and returns `undefined` to `DenoKvAdapter.deliver()`, which auto-acknowledges the native receipt. Final durable state: `providerEffects: 1`, `writeAttempts: 1` (or `6` on exhausted busy), `deliveries: 1`, `execution row: running` (`0` completed, `0` failed), `active marker: 1` (until 15 m active TTL), `applied marker: 0`, native ready/running tables empty, `DLQ: 0`.
- **Fundamental impossibility without external idempotency/atomic boundary:** Without a durable applied marker, no local state proves the provider succeeded. Acknowledging drops the native receipt and strands the row in `running` with no redelivery/DLQ; keeping the receipt unacknowledged / redelivering allows a later delivery (after active TTL or lease takeover) to invoke the provider a second time unless the provider honors a stable idempotency key or shares an atomic boundary.

### `#2645` semantics tension
`#2645` acknowledges a queue receipt only after durable settlement and preserves recovery (unacknowledged receipt / redelivery / bounded DLQ) when settlement cannot complete safely. Silently acknowledging an unsettled delivery drops receipt recoverability (`running` row stranded), whereas preserving redelivery in Case (b) risks repeating the provider call.

### Candidate options for Owner decision
1. **Option 1 (Split Case (a) and Case (b)):**
   - **Case (a):** Implement completion-only recovery (e.g., reject/redeliver or record completion repair while `applied` is durable, so `alreadyApplied: true` finishes `executionState.complete('completed')` without re-calling the provider — zero duplicate effect AND zero stranded row).
   - **Case (b):** Choose either **(1i)** explicit operator-visible quarantine/reconciliation (never auto-replay the provider; surface an explicit `unconfirmed_settlement` record/status rather than silent `running`, acknowledging local storage outage can still prevent that write) or **(1ii)** accept the current no-replay latch for unconfirmed `markApplied` and scope box 3 to recoverable known-uncommitted contention + Case (a) completion recovery (retaining the documented provider-side idempotency key requirement for unconfirmed `markApplied` and crashes).
2. **Option 2 (Strict `#2645` at-least-once across both (a) and (b)):** Never acknowledge a delivery until both `markApplied` and `executionState.complete` are durable (reject / leave unacknowledged on unconfirmed settlement). Eliminates stranded `running` rows completely and preserves `#2645` strictly, at the cost of allowing duplicate provider calls in Case (b) unless the provider honors a stable idempotency key.
3. **Option 3 (Accept current `0b4a6e978` behavior for `#2651`, defer Case (a) repair):** Keep the current latch for both (a) and (b) and track Case (a) completion-only repair in a follow-up issue. Zero additional code complexity now, at the cost of leaving even Case (a) stranded in `running` when `executionState.complete` fails permanently.
