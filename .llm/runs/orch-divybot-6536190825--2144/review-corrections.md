**1. Dead-letter identity for direct dispatch: fixed.** When there is no queue message id, the record id now comes from `resolveWorkerIdempotencyKey`, which has the form `job:<jobId>:<key>`. Two different jobs that share a caller key no longer collide, and when there's no caller key the execution id keeps records distinct. The remaining shared case, a failure before any execution exists with no caller key, falls back to a hash of the payload. Two such failures of the same job with the same payload are then treated as the same message and stored once. That is consistent with how the claim treats them, and reprocessing frees the id again, so it isn't a blocker.

**2. Replay while the original claim is still active: fixed.**
- **Behaviour:** a duplicate whose claim is still active but not yet applied now throws. It goes through the requeue path without releasing the owner's claim, because `release` only runs when this delivery holds the claim. A duplicate of an already-applied claim is still acknowledged. The window between the dead-letter write and the claim release can no longer quietly drop a replay.
- **Advisory:** if a job runs longer than the transport's visibility timeout, the recovered duplicates are now put back on the queue repeatedly. They used to be acknowledged. On KV polling, which `create-queue.ts` uses only for KV Connect, they can end up in the queue's own dead-letter store while the original attempt still succeeds. The docs already say the time budget must stay below the visibility timeout. Also, `recordIdempotentSkip` now records a "skip" for an attempt that will be retried, which makes that metric slightly misleading.

**3. Fatal shutdown blocked by a health read: fixed.**
- **Fatal path:** `failed()` is now synchronous. It sets the final state from the last good snapshot and starts the 1-second stop timer straight away. A fresher snapshot can still fill in details, but only in the background: its errors are handled and it can't hold up shutdown.
- **HTTP reads:** a read now races the snapshot against an interrupt that fires on failure or stop, and its abort listener is removed afterwards. Abandoned snapshot promises are still handled by the race, so they don't surface as unhandled rejections. Once the process has failed, health answers with the stored final state without touching storage.
