### Required fixes

**1. The restored variant can fail for a non-defect reason — no bounded retry on the Activity projection.** `activity()` calls `probeAppHome(projectRoot, 'dashboard', appHost)` with **no options**, so it waits only for the app to serve, never for the streams capability; it then does a **single** `fetch` and demands `data-capability-state="ready"` plus the exact caught-up description. The generated app explicitly models three transitional projection states — `state: snapshot.items.length ? 'ready' : 'empty'`, `'Catching up with stream history…'` and `'Events observed since the preview skipped earlier history.'` — over a per-URL cached snapshot with bounded catch-up. The gate's own test (line 130) proves `state="empty"` throws. So a first render that has not yet read the event fails the restored variant with a generic `Error`, and because this gate is `critical: true` and runs first, that flake fails the entire merge-readiness suite after paying for three scaffolds. Fix: retry the HTML read with a bounded budget (the existing 30×1s convention), treating `StreamLinkAcceptanceError` as terminal so the drop-link control still short-circuits instead of burning the budget:
```ts
for (let attempt = 1; ; attempt++) {
  const html = await fetchHome();
  try { assertLinkedActivityHtml(html); return await finish(html); }
  catch (error) {
    if (error instanceof StreamLinkAcceptanceError || attempt === ATTEMPTS) throw error;
    await delay(1_000);
  }
}
```
Do **not** instead pass `readyCapabilities: ['streams']` to `probeAppHome` — for drop-link that never becomes ready, and the probe's generic failure would replace the typed symptom the control requires.

**2. The gate will likely time out on a cold runner, and it does not raise Aspire's own start timeout.** `timeoutMs: 1_200_000` (20 min) covers three full Postgres-backed walkthroughs: init + two plugin installs + restore + start (Postgres, Redis, five processes) + db init/generate/seed + doctor + probes + teardown, with `skip-seed-handoff` additionally burning its whole 30×1s execution-probe budget. At the aspire skill's own observed figures that is plausibly 12–21 minutes, i.e. at or over the ceiling on first-run image pulls. Separately, every existing gate that starts Aspire sets `ASPIRE_CLI_START_TIMEOUT` (`garnet-coexistence-fixture.ts:311-312` defaults it; `verify-typed-db-phase-b.ts:137` injects it), while the new `command()` helper passes no `env` at all, so its three `aspire start` calls use Aspire's default. Fix: raise `timeoutMs` to ~2,400,000 (or justify the ceiling with a measured figure) and pass `ASPIRE_CLI_START_TIMEOUT` on the `aspire start` invocations, matching the established pattern.
