# Auth prerequisites verified against current source

The supported generated sign-in path is **kv-oauth**, the normal plugin default. After the parent's two automatic stream integration steps and existing AI/UI setup, supplying the following auth/model configuration requires no further application source wiring. Real external-provider acceptance still needs a browser login and valid provider/model credentials; stub tests do not attest those external systems.

Sources: `plugins/auth/services/src/backend-registry.ts`, `plugins/auth/services/src/kv-oauth-subject.ts`, `packages/cli/src/kernel/assets/auth/bff.ts.template`, `packages/auth-kv-oauth/src/backend.ts`, `packages/auth-better-auth/src/better-auth-backend.ts`, and `docs/site/identity-access/how-to/add-authentication.md`.

## Default kv-oauth

- Install `netscript plugin install auth --name auth --app portal` using the actual app name. Default backend is kv-oauth; installation provisions KV, not auth SQL tables. Keep `auth/bff.ts`, app `/auth/[action]`, `/sign-in`, and auth service discovery from the normal installer. Bootstrap the AppHost with the provider environment already present, and restart after changes.
- Set `NETSCRIPT_AUTH_BACKEND=kv-oauth` in the auth service environment (or retain the default). Provide working persistent KV and **`NETSCRIPT_AUTH_KV_OAUTH_KEY`**, a stable base64/base64url encoding of exactly 32 random bytes. Missing/invalid key is a startup error. Keep this separate from the streams secret and retain it across restarts so existing sessions remain decryptable.
- Register a real OAuth/OIDC application. Supply **`NETSCRIPT_AUTH_CLIENT_ID`**, **`NETSCRIPT_AUTH_CLIENT_SECRET`** where required by the registered provider, and **`NETSCRIPT_AUTH_REDIRECT_URI=<portal-origin>/auth/callback`**. Register that exact app-origin URL with the provider. The app BFF owns the GET callback and forwards its state/code/transaction cookie as a POST to auth; registering the auth service's POST API URL is incorrect for this browser flow.
- Configure the provider's issuer/endpoints and scopes. For GitHub specifically: `NETSCRIPT_AUTH_PROVIDER_ID=github`, authorization endpoint `https://github.com/login/oauth/authorize`, token endpoint `https://github.com/login/oauth/access_token`, userinfo endpoint `https://api.github.com/user`, `NETSCRIPT_AUTH_SCOPES=read:user user:email`. Do not set a GitHub OIDC issuer. Set the corresponding `NETSCRIPT_AUTH_AUTHORIZATION_ENDPOINT`, `NETSCRIPT_AUTH_TOKEN_ENDPOINT`, `NETSCRIPT_AUTH_USERINFO_ENDPOINT` variables explicitly when injecting environment; the boot fallback endpoints are intentionally nonfunctional. The named GitHub preset derives a stable `github:<id>` subject from userinfo. OIDC providers instead need their real `NETSCRIPT_AUTH_ISSUER`/discovery and `openid` scope, with stable ID-token `sub`; custom userinfo providers need a stable `NETSCRIPT_AUTH_SUBJECT_SOURCE` / `NETSCRIPT_AUTH_SUBJECT_CLAIM`.
- Use HTTPS for the app, preserving `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no Domain and the default `__Host-ns_session` cookie. Behind a trusted TLS-terminating proxy, set `NETSCRIPT_AUTH_TRUST_PROXY_HEADERS=true` **only** when that proxy replaces inbound protocol headers and blocks direct access to auth. The generated BFF supplies the forwarded protocol. Direct auth TLS requires the existing `NETSCRIPT_AUTH_COOKIE_SECURE=true` setting.
- For local HTTP development, use **`localhost`** for the app (the BFF refuses non-localhost plain HTTP). Auth needs its explicit local transport opt-in `NETSCRIPT_AUTH_ALLOW_INSECURE_HTTP_REQUESTS=true`. When retaining `__Host-ns_session` with a browser that accepts secure cookies on localhost, keep `NETSCRIPT_AUTH_COOKIE_SECURE=true`; an insecure prefixed cookie is invalid. The framework's alternative local-only configuration uses an unprefixed `NETSCRIPT_AUTH_COOKIE_NAME=ns_session_dev` consistently in app and auth with `NETSCRIPT_AUTH_COOKIE_SECURE=false` and the explicit development opt-in; the BFF forwards that backend-issued app-origin cookie. Never apply those development overrides to a production/non-loopback deployment. Arbitrary plain HTTP app hosts are unsupported. Leave outbound-provider HTTP opt-in off for real HTTPS identity providers.
- The app and auth service must agree on `NETSCRIPT_AUTH_COOKIE_NAME`. Keep their normal discovery/reference wiring. The app sends only the cookie credential through the existing bearer client to `/api/rpc/v1/auth/session`; it uses only the verified subject in the response. Our runtime now converts chat/MCP POST into a server-owned GET for this GET-only BFF action. Missing/rejected/broken auth fails closed; browser-supplied subjects are ignored.

Supply provider secrets and the KV key through the deployment environment backed by `~/.secrets` or an external secret manager. Do not put secret values in appsettings or project files. The normal `netscript plugin auth provider set` command can write credential bindings into project `.env`; it is not needed for this environment-injected recipe. Do not print generated keys or pass them in visible CLI arguments. Non-secret provider settings may be managed by the existing configuration path.

After starting the configured services, open `/sign-in`, complete the external provider login, and confirm `/auth/session` returns `authenticated: true` with a stable subject and no bearer/session ID. Then `/ai` permits a private conversation and `/api/showcase/mcp` verifies that same browser cookie. `ANTHROPIC_API_KEY` (or the supported OpenAI-compatible configuration from integration.md) enables real model generation. An installed but unconfigured auth service is not evidence of a working login.

## Better-auth alternative: existing-session validation only

Select `NETSCRIPT_AUTH_BACKEND=better-auth` **before** installing/reinstalling auth so the normal installer contributes auth Prisma tables and database references. Supply **`BETTER_AUTH_SECRET`**, a long random stable signing secret; `DB_PROVIDER` must match the real SQL adapter (`sqlite`, `postgres`/`postgresql`, etc.). Use the parent's normal database init/generate/migration commands to create `authUser`, `authSession`, `authAccount` and `authVerification` tables. Switching backends requires reinstalling with `netscript plugin install auth --name auth --app portal --force` to reconcile schema/runtime wiring.

The current official plugin constructs `createNetscriptBetterAuth` for session validation. Its `createBetterAuthBackend` has no `InteractiveFlowPort`; generated `signin`/`callback` return `AUTH_PROVIDER_ERROR` (502). Setting `BETTER_AUTH_SECRET` or OAuth credentials does **not** create a login page, expose the better-auth issuer handler, configure social providers, or issue an app-origin session cookie.

A deployment choosing this alternative must already provide a supported better-auth issuer/login flow, shared database/signing configuration, and its secure browser-session bridge to the existing BFF/auth verifier. The backend's token lookup uses the better-auth session cookie format; an arbitrary user ID or unsigned cookie is not acceptable. That is separate authored authentication integration and cannot be achieved by this slice's allowed stream/setup changes. Keep the existing sign-in surface; select kv-oauth for the promised no-extra-source-wiring path. No demo identity, shared user, or trusted subject header is supplied as a substitute.
