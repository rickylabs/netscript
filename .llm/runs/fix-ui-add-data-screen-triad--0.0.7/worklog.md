## Design

This checkpoint was recorded before any implementation file was created. S1 contains harness
artifacts only.

### Public Surface

- `netscript ui:add page <path> --island [--route <id>] [--app <name>] [--force] [--dry-run]` —
  emits/plans page + loader + island + route registration when exactly one bindable generated query
  client exists.
- `netscript ui:add page <path> [--route <id>] [--app <name>] [--force] [--dry-run]` — the plain
  non-island path emits/plans its static page plus the same `router.ts`/`appRoutes` registration; it
  does not require a query binding and does not emit loader/island roles.
- `netscript ui:add island <Name> --query [--app <name>] [--force] [--dry-run]` — emits/plans one
  route-tree query island bound to that client.
- `UiAddCommandInput` — retains current optional `projectRoot`, `app`, `registryRoot`, `theme`,
  `force`, `route`, `island`, and `query`; adds `dryRun?: boolean`.
- No `packages/cli/mod.ts` export changes. Application types/functions remain CLI-internal.

### Domain Vocabulary

- `UiGeneratedFileRole` — semantic role of a planned write: page, query-loader, island, or
  route-registration (plus the existing static-island/page cases as needed).
- `UI_DATA_SCREEN_FILE_ROLES` — the single advertised four-role contract used by help and tests.
- `UiGeneratedFile` — absolute path, rendered content, and semantic role.
- `UiScaffoldResult` — exact planned/generated file collection and dry-run/write reporting.
- `UiQueryBinding` — one recognized generated query module, service/export name, canonical `list`
  factory seam, input dialect, and source kind (`explicit-client` or `init-example`).
- `UiPageScaffoldInput` / island input — gain `force` and `dryRun`; app-root resolution stays above
  them in the public command.
- `UiScaffoldPreconditionError` (name may be adjusted within the same concept) — non-zero,
  actionable validation failure raised before mutation.

### Vocabulary and behavior contract

- **Bindable contract** means one recognizable `...Queries.list` factory with a canonical input
  dialect. Selection first considers `lib/<service>.ts` files generated by
  `netscript service add --name <service> --with-client` (one binds; peers are ambiguous), then—if
  none exist—one canonical `init --service` route-local `(_lib)/service-query.ts` teaching module.
- **Data screen** means a page layer whose loader performs a cache-first factory query and hands
  `input`, real `initialData`, and `cachedAt` to a hydrating island.
- **Query island** means `QueryIsland` + `useIslandQuery` with the factory's `clientKey(input)`,
  seeded data, and `initialDataUpdatedAt: cachedAt`.
- **Plan** means all rendered file contents—including the updated `router.ts`—are validated before
  any write. Dry-run exposes this same plan without mutation.
- **Force** means overwrite web-scaffold-owned target content after successful full preflight; it
  does not introduce #1354's content-comparison/idempotency reporting.

### Ports

- `FileSystemPort` — consumed for binding discovery, router/target reads, existence checks,
  directories, and writes. Existing methods suffice; no port change.
- Command execution/process, HTTP, prompt, output-renderer, and template ports — unchanged and not
  consumed by product implementation. E2E command execution remains in the existing E2E harness.

### Constants

- `UI_DATA_SCREEN_FILE_ROLES` — `page`, `query-loader`, `island`, `route-registration`.
- `UI_QUERY_PREREQUISITE` — exact diagnostic verb
  `netscript service add --name <service> --with-client`.
- Supported input-dialect constants — persistent CRUD (`limit`, `page`, `sortBy`, `sortOrder`) and
  memory (`limit`, `offset`; optional search omitted for initial load).
- Route helper directory — `(_islands)` under `routes/**`; no top-level `islands/` output from
  future `ui:add island` runs.
- Literal names are provisional implementation spellings; changing spelling without changing the
  locked concepts is minor. Adding a new concept/axis is a rescope.

### Composition Axes

- Existing registries: `DbEngineRegistry`, `DeployTargetRegistry`, `OutputRendererRegistry`,
  `PluginKindRegistry`, `PresetRegistry`, `TemplateRegistry`, `CliCommandRegistry`.
- New axes: none. Query binding is deliberate closed convention recognition, not a registry.
- Composition roots: unchanged (`PublicCli` and its existing command dependencies).
- Layering direction: public UI/add command → kernel application UI scaffolder → `FileSystemPort`;
  the application layer never imports public presentation code.

### Spine and layer-2 abstracts

- Existing spine observed: `CliCommand<TDefinition>`, `CliRoot<TDefinition>`,
  `UseCase<TInput,TResult>`, `Registry<TKey,TValue>`. Archetype-6's ideal `CliCommand<Input,Result>`
  and `CliCommandGroup` are not the current package surface.
- Existing layer-2: `DeployStepCommand` (three command concretes), `Pipeline`/`PipelineStep` (three
  deploy flows), `Manifest` (`TemplateRegistry`), and `ScaffoldCommand` (one existing `AddDbCommand`
  concrete).
- This leaf introduces/modifies none of these and creates no new abstraction debt.

### Island convention and compatibility

- New page island: `routes/<segment>/(_islands)/<Page>Island.tsx`.
- New standalone island: `routes/(_islands)/<Name>.tsx` because its current syntax carries no route.
- These are one convention: route-tree helper directories excluded from route discovery.
- Existing top-level `islands/` files continue to work and are not moved. Already-scaffolded apps
  see no automatic migration; only future command output changes. Real command help states this;
  generated-corpus how-tos are deferred under D17.

### No-write precondition sequence

1. Resolve the app root through the existing #1356 resolver.
2. Validate path/name/route identifiers.
3. Discover and fully validate the prioritized conventional query binding and supported list dialect
   for data-bound modes; otherwise throw with the prerequisite verb/candidates.
4. Render every target in memory, including a uniquely validated router registration.
5. Inspect all target collisions and force eligibility.
6. If dry-run, return/print the plan and stop. Otherwise create directories/write the already
   validated plan.

No cleanup path is part of this contract because validation errors cannot cross step 5.

### #1360 boundary

`initialDataUpdatedAt?: number` is already available as an optional field in `IslandQueryOptions`;
therefore #1357 can and, by its generator contract, must emit it whenever it seeds `initialData`.
#1360 is still real: it owns correcting the two existing canonical showcase variants, the invariant
test for those shipped assets, and the beta migration note. This leaf does not edit those paths and
does not drop the timestamp from its own contract.

### Golden and help seam

- Planned files carry semantic roles. Help derives its advertised role list from
  `UI_DATA_SCREEN_FILE_ROLES`, but the test expectation is not derived from that same constant.
- Positive semantic golden: generate into an in-memory canonical app and assert roles plus
  `appRoutes`, cache-first `fetchQuery`, factory `clientKey`, `QueryIsland`, `useIslandQuery`,
  `initialData`, `initialDataUpdatedAt`, real rendering, and the absence of old placeholders.
- Negative semantic golden: pass a fixture matching the old lone-`useSignal` island and empty loader
  object to the validator; it must reject both independently.
- Help coupling: invoke/render the real Cliffy `ui:add` command help, extract every advertised role,
  and compare it with the independently observed actual planned role set. A constant-to-constant
  assertion is insufficient; a changed description or emission set must break this surface test.
- No giant byte snapshot; assertions are semantic and focused (AP-18).
