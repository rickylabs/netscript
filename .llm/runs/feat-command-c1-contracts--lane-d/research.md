## Load-bearing findings

1. RFC 0003 is Accepted. Its placement table assigns commands to service, transport schemas/errors to contracts, raw transaction/relay storage to database and bounded attributes to telemetry. The service -> database direct dependency is currently absent from packages/service/deno.json. There are no commands exports in the current service/contracts/database export maps.
2. packages/contracts/src/application/contract-primitives.ts now exposes exact CommonErrorMap, BaseContractErrors and BaseContractMeta. The current base builder initializes metadata and preserves that metadata generic, unlike the older RFC example's empty fourth generic. The command builder must extend this current form, preserving six base codes plus three command codes without widening metadata or errors.
3. packages/plugin-sagas-core/src/runtime/saga-engine.ts calls save, saveCorrelation and appendTransition separately in its transition persistence path. SagaStorePort has no atomic transition capability. The KV adapter CAS checks its state write alone; Prisma opens a private transaction in save while other writes are separate. This cannot be presented as an atomic command producer.
4. packages/plugin-workers-core/src/domain/job-definition.ts JobDefinition carries optional payloadSchema; src/domain/public-schema.ts supplies the existing structural Standard Schema contract. TaskDefinition in src/domain/task.ts has a payload generic and handler but no payloadSchema. Job payload continuity is available, but a durable task effect needs a schema-bound extension in workers core and task builder. No separate saga payload map will be introduced.
5. SagaHandler currently returns CascadedMessage[]. Its send tag is a saga-message cascade. Existing integration/workers helpers are imperative and SagaWorkersClientPort permits an independently inferred payload generic. Durable constructors must be distinct, bind a concrete schema-bearing definition, and never call those helpers from the handler.
6. The RFC sink returns Promise<void> and markPublished currently takes no acceptance receipt. #1932 requires persisted receipt identity/time after checked worker acceptance. C5 must therefore provide a narrow acknowledged-receipt settlement extension usable by the producer; adding receipt persistence only in #1932 after sink publication would create a new crash window. This is a planned additive C5 contract decision.
7. PostgreSQL receipt claims require ON CONFLICT DO NOTHING RETURNING plus indexed select, bounded transaction-local lock_timeout, and whole-callback rollback after busy. At ReadCommitted a committed leader is replayable; stronger isolation may produce serialization failure. There is no automatic callback retry.
8. Deno is available; the running tool reports 2.9.7. rg and rtk are absent, so focused native tools substitute. MCP find_guidance and search_docs were consulted; they provided general runtime/plugin guidance rather than command-kit specifics. No framework implementation was hand-rolled before this query.
