## D-1452-RUNTIME — the plan forbade the runtime gate the change class required

**Severity: significant.** `plan.md:53` locked *"Runtime/Aspire/Docker/browser and `e2e:cli` gates are
explicitly forbidden for this lane"*, and `context-pack.md` recorded Runtime as
`N/A — forbidden/no runtime lease`. That was wrong at the contract level, not merely unlucky: this
slice changes a **scaffold template** and its **generated carrier**, which is precisely the change
class `scaffold.runtime` exists to cover. The plan's blanket prohibition — written for a lane holding
no local Aspire lease — was silently applied to a change that needed the gate.

The error was masked twice over. The PR was a **draft**, and `ci.yml` gates every heavy lane on
`pull_request.draft == false`, so `scaffold-runtime` did not merely go unrun — it reported `skipping`
and looked like a satisfied gate. An external audit caught it, not this lane's own evidence set.

**Resolution:** the prohibition was correct only about *how*, not *whether*. Local Aspire is
topology-parked, so the gate was taken in CI instead by opting the non-draft PR into `e2e-cli-gate`.
Result at immutable head `b87fd92faf86bb2a616effc6c340568f7ddeaf96`, run `33358058235`:
`scaffold-runtime (aspire + docker + postgres)` **success**, `scaffold-runtime-sqlite (aspire + sqlite
+ garnet)` **success**, `scaffold-static (deno-only)` **success**.

**Lesson for the next leaf:** "no runtime lease" justifies choosing a CI lane over a local one. It
never justifies declaring a required gate `N/A`.

## D-1452-CARRIER — tool-forced carrier changes outside the hand-written ceiling, and two integrations

**Severity: minor, but it must be on the record** because the diff is wider than the plan's ceiling
and a reader comparing them would otherwise find an unexplained gap.

The plan's hand-written ceiling is five files. The shipped diff also carries two **generated**
carriers that no human edited:

- `packages/cli/src/kernel/assets/embedded.generated.ts` — regenerated by `gen:assets-barrel` because
  the slice changes an embedded template.
- `packages/mcp/src/infrastructure/export-surfaces/export-surface-corpus.generated.ts` — regenerated by
  `gen:mcp-export-corpus`; +1 symbol, exactly the new `createLazyKv` export.

The corpus additionally moved **twice for integration reasons unrelated to this slice's content**:

1. Integrating `main` `584caa03f` — corpus was the sole conflict; resolved by taking `main`'s file and
   regenerating.
2. Integrating `main` `eaea940be` at the final seam `8ab11ddee` — same single conflict, same
   mechanical resolution. Its blob therefore moved `1dd90409… → 6e84e995…` between the evaluated head
   `3130fb52b` and `b87fd92f`.

**Byte-identity does not and should not hold for a regenerated derivative.** The correct invariant is
that the carrier is genuine tool output, proven by `check:mcp-export-corpus` and
`check:assets-barrel` exiting 0 at the head — not by blob comparison. The five hand-written product
files *are* byte-identical to the evaluated head, and that is the claim the evaluator verdict rests on.

Neither carrier was ever hand-merged; both were regenerated from tooling at every step.
