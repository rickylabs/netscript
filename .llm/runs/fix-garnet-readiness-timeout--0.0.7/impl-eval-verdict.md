### Non-blocking observations

- **R1 — verifier treats `EPROTO` as terminal (sharpest edge).** `isTerminalListenerFailure` fails the whole gate immediately on `data.code === 'NOAUTH' || 'EPROTO'`. NOAUTH is genuinely deterministic. But my adversarial case 8 shows a **transient** accept-then-close (Docker/DCP port proxy accepting before Garnet binds, 0 bytes, `'end'`) also yields `EPROTO` — under the old code `aspire wait` (300 s) rode through such a window; under the new code one Unhealthy-EPROTO observation kills `runtime.wait.garnet` instantly. The window is millisecond-scale against a 5 s-scale health cadence, so likelihood is low, but the asymmetry (accept-then-hang → retryable ETIMEDOUT; accept-then-close → instant fail) is real. Recommendation: restrict terminal classification to `NOAUTH`, or reclassify a 0-byte close as retryable.
- **R2 — 30 s "never published" budget.** Cold ghcr pull or cold NuGet tool restore landing inside the garnet wait can exceed 30 s and now hard-fails. Mitigated by gate ordering (Postgres wait at 300 s precedes garnet) and 16–30× headroom over observed readiness. Recommendation: consider retaining a longer budget only for the "resource/key never published" state (cold-start) while keeping 30 s for "published but unhealthy" (stability), or pre-warming the image/tool in an earlier gate. This is a deliberate, worklog-documented trade; it does not block.
