## 4. Contract honesty — captured-but-not-listed worker run

**Contract of record** (`packages/mcp/tests/fixtures/telemetry/README.md` at `85bd49673`, "Pending
Aspire 13.5.3 capture (phase B)", steps 1–5): (1) start the exact 13.5.3 AppHost and wait for the
required resources; (2) trigger the scaffolded `health-check` worker job; (3) `GET …/api/telemetry/
resources` + `…/spans`; (4) save raw envelopes + `aspire-13.5.3-fixture.ts` + 13.5.3 case beside the
13.4.6 case; (5) promote parity `pending-lease → required`; record date / CLI 13.5.3 / AppHost
identity / URL redaction / lease evidence; never fabricate, copy forward, or hand-edit. Issue #1715
acceptance: every compat-fixture row has a 13.5.3 case beside its 13.4.6 case; fixture READMEs state
command + date + CLI version; scoped tests green.

**Finding.** Every literal step is satisfied by real, unedited output (§1–§3). But the 13.5.3
envelope is a *degraded* capture and the tree does not say so:

- The 13.4.6 case proves the adapter's consumer path (`queue.dequeue` consumer span → `job.execute`
  → `list_runs` = 2 → `get_run` schema-valid → `get_last_job_result found:true`). The 13.5.3 case
  asserts `workerSpanKind: 'producer'`, `listedRunCount: 0`, `jobFound: false`, and the `get_run`
  block is skipped (`if (runs[0])`). At 13.5.3 the run/job aggregation paths are therefore exercised
  only on the empty branch.
- Cause is environmental, not a 13.5.3 shape change: the brief-scoped scratch had no `streams`
  plugin, so the published workers runtime never consumed (`workers` `hasTraces:false`), and no
  `database.codegen` step, so web `/health` is 500 ×12 (supervisor D-75 O-1/O-2). Only the receipt
  (`09-phase-b-attempt-3-capture.md`) and supervisor `drift.md` D-75 record this.
- In the committed product text nothing names it: README "Current capture" describes the same
  "trigger … then capture" sequence as 13.4.6 with no outcome; `aspire-13.5.3-fixture.ts` header
  mirrors the 13.4.6 header; the 13.5.3 test case has no comment. A reader would conclude that a
  13.5.3 dashboard does not surface completed worker runs — a false product signal.

**Decision.** The #1715/README contract is **satisfied as written** (no fabrication; the trigger was
real; a job that is triggered but never dequeued is what the dashboard truthfully returned), so this
is **not** `FAIL_RESCOPE` and does not require a fourth lease: consumer-run coverage at 13.5.3 is
already routed by D-75 to the hosted `scaffold.runtime` proof and S8's local phase B. It **is** a
scope gap that must be named in the tree, not accepted by omission — the harness bar for fixtures
is "honestly labelled" (cycle-1 M-1 was failed on exactly this ground). Hence `FAIL_FIX`, bounded to
provenance text and run-artifact bookkeeping; no envelope, adapter, or parity change.

Note (not a finding): the `spans.some(service.name === 'workers')` assertion passes via the
`@hono/otel` spans of the **workers-api** resource, which carry span attribute
`service.name: workers` / `netscript.http.service: workers`; there is no `workers` resource span
in the 13.5.3 envelope. Worth a word in the F-2 comment so nobody reads it as worker-runtime tracing.
