## Revised load-bearing seam (PLAN-EVAL cycle two)

First implementation probes show native closed can resolve immediately when enqueueing a final response, before subscribeJson parses or invokes its callback. This invalidates using closed to await batch commit or subscriber failure. Do not ship that implementation. Revised public seam uses each native StreamResponse.json() (completion promise with direct parse rejection), live:false to prevent prefetch beyond catch-up, and public StreamOptions.params live=long-poll on subsequent finite reads. stream-api.ts appends those params to the first request after offset; no private SDK access or handwritten transport parser. json() consumes every catch-up response until upToDate; reads resume final returned metadata after completion, then one upstream dispatcher callback commits all items. Native closed rejection is observed only to prevent unhandled rejection, never to choose resume. Once caught up, subsequent long-poll response is naturally pending for new data; empty upToDate responses preserve cursor/offset and reset outage budget. Stop cancels finite native session, pending request and clock. Direct json() parsing error and subscriber exceptions remain terminal. Existing public handle/status/reconnect, finite retry policy, genuine killed-server and mutation gates unchanged. No owner choice or upstream patch needed if this public seam passes independent review.
