The cookie propagation code works and the tests fail without it, but the cookie-jar recipe the docs now give for local testing does not work over plain HTTP with the default cookie name.

### Findings

1. **major**: `docs/site/identity-access/how-to/add-authentication.md:309-346` and `docs/site/tutorials/workspace/02-auth.md:232-251`. The documented local round trip fails as written.
   - **Why it fails:** The recipe runs against `http://localhost:8094` and tells the reader that plain HTTP needs `NETSCRIPT_AUTH_ALLOW_INSECURE_REQUESTS=true`. With that setting, `buildCookieHeader` emits `__Host-ns_session=…; Path=/; SameSite=Lax; HttpOnly` with no `Secure`, because `deriveHttps` is false. Clients reject a `__Host-` cookie that lacks `Secure`. I reproduced this with curl 7.88: a jar fed `__Host-ns_session` without `Secure` stays empty. The same cookie with `Secure`, or an unprefixed name, is stored.
   - **Result:** The `-c cookies.txt` signin never saves the transaction cookie, so the documented callback fails with `oauth_cookie_missing`. Browsers reject it for the same reason. "`__Host-` browser cookie rules still apply" warns about this but does not tell the reader what to do.
   - **Fix (docs only):** Make the local recipe work. Options:
     - add `-H 'X-Forwarded-Proto: https'` to each curl call (curl keeps `Secure` cookies for `localhost`);
     - tell readers to set an unprefixed `NETSCRIPT_AUTH_COOKIE_NAME` for plain-HTTP testing;
     - show the cookie-less `txn` callback path.
   - **Optional follow-up:** consider making issuance refuse an insecure `__Host-` cookie outright, since no client will accept it.
2. **minor**: `plugins/auth/services/src/main.ts:64-69` resolves the cookie name a second time.
   - **What:** `init.ts:28` and `backend-registry.ts:100-158` already resolve the name, with precedence ctx.env > Deno.env > appsettings. main.ts repeats that logic, and its appsettings guard differs: it uses `hasAuthAppsettings` where init uses `isAuthServiceAppsettings` validation. Only `toAuthnRequest` is unit-tested; nothing tests the bootstrap path with a custom name end to end.
   - **Fix:** Get the name from the same merged env the backend uses, for example by returning it from `initializeAuthService` or exporting one resolver.
3. **minor**: `packages/auth-kv-oauth/src/cookies.ts:30,74-79`. The public option `KvOAuthCookieOptions.httpOnly?: boolean` still accepts `false`, but `false` now always throws.
   - **Fix:** Document that in the JSDoc, or narrow the type in this breaking release.
4. **nit**: `cookies.ts:122-124`. The `__Host-` HTTPS branch in `assertCookiePolicy` can no longer be reached, because the new general check at :77 runs first. Remove it or fold the two checks together.
5. **nit**: `plugins/auth/services/src/routers/v1-handlers.ts:175`. `captureAuthResponseCookies` runs before `audit.setOutcome`. If a later step throws, the session cookie is attached to an error response. Capture just before the handler returns.
