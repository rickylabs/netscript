The normalizer itself is solid and well tested (asks 1–3 pass), but the scaffolded `prisma.config.ts` can no longer be loaded by the Prisma CLI. Every `db:*` task that passes `--config prisma.config.ts` breaks, so ask 4 is not delivered and `Closes #2104` is not supported.

### Findings

1. **blocker** — `packages/cli/src/kernel/assets/database/connection-helpers.ts.template:8` (rendered into both `prisma.config.ts` and `database/postgres/mod.ts`). The new bare import `@netscript/database/adapters/postgres` works for `mod.ts`, which runs natively under Deno. It does not work for `prisma.config.ts`. Prisma 7 loads its config through c12/jiti, which resolves modules the Node way via `node_modules`. JSR packages and Deno workspace members are never there.
   - **Reproduced** at this head: a maintainer local-source scaffold with `init … --db postgres`, then `deno run -A npm:prisma@^7.4.2 generate --generator client --config prisma.config.ts` in `database/postgres`. Result: `Failed to load config file ".../prisma.config.ts" as a TypeScript/JavaScript module. Error: Cannot find module '@netscript/database/adapters/postgres'`.
   - **Control:** the same steps on `origin/main` (`861de0270`) print `Loaded Prisma config from prisma.config.ts.`
   - `deno check prisma.config.ts` passes, because Deno's resolver differs from the one Prisma uses. That is why the type-check gate missed it.
   - **Impact:** `db:generate`, `db:migrate:deploy`, `db:push`, `db:status`, `db:reset`, `db:introspect`, `db:studio` and `migrate resolve` all fail for every new Postgres scaffold, in both local and JSR import modes. The `scaffold.runtime` tiers have not run at this head (they show as skipping) and would hit this at `db init`/`db generate`.
   - **Fix:** don't import a JSR/workspace module from `prisma.config.ts`. One option: run the Prisma tasks through a small Deno entry script that resolves the URL with `normalizePostgresConnectionString` and passes the normalized `DATABASE_URL` to the Prisma subprocess. `prisma.config.ts` then only reads an already-normalized env value. Any other design that the real Prisma loader can resolve also works.
   - **Test:** add a test that loads the generated config through the actual Prisma loader (or run the `scaffold.runtime` postgres tier) as the negative control.

2. **major** — `packages/cli/src/kernel/templates/database/postgres-normalizer_test.ts:16-33`. The ask-4 proof only checks that the generated text contains the import and call. It cannot catch finding 1. The PR body's statement that the four asks are "proven" is not true for ask 4. The same unproven claim appears in `packages/database/README.md:109` ("The scaffolded Postgres module and Prisma config use this same helper").
   - **Fix:** back ask 4 with a test that actually loads the generated config, or keep `Refs #2104` until the runtime tier proves it.

3. **minor** — `connection-helpers.ts.template:8`. The old template called `value.trim()` before normalizing; the new alias passes `rawValue` through untrimmed. Measured at this head:
   - `' postgres://a:b@h/d'` now throws `invalid-format`; it worked before.
   - `'postgres://a:b@h/d\n'` passes through with the newline still attached.
   - Env values from secret files or `.env` often carry such whitespace. **Fix:** keep a `.trim()` in the scaffold wrapper, or trim inside the normalizer and document it.

4. **minor** — `packages/database/adapters/mssql.adapter.ts:120`. The public function `parseAdoNetConnectionString` now throws the internal, unexported `AdoNetConnectionStringSyntaxError` for input it used to tolerate: segments with no `=`, and unterminated or trailing-garbage quoted values. Quoted values are now unquoted, which is a behaviour fix. This is a public behaviour change with no `@throws` in the JSDoc and no `packages/database/CHANGELOG.md` `Unreleased` entry; the package keeps per-PR entries.
   - **Fix:** add `@throws` to the JSDoc and a changelog line. Also add the Postgres normalizer to the changelog.

5. **minor** — `packages/database/adapters/postgres.adapter.ts:10`. Re-exporting from the adapter module means a caller that only wants string normalization also loads `@prisma/adapter-pg`. The issue allowed either export location. The root `.` entry already carries "connection-string helpers" (`parseConnectionString`, `buildPostgresConnectionString`), so it would be the more idiomatic, lighter home. Worth reconsidering together with the fix for finding 1.

6. **nit** — `connection-helpers.ts.template:8`. The import is emitted mid-file, after `resolveDatabaseUrl` / `resolveConnectionString` (line 33 of `prisma.config.ts`, line 80 of `mod.ts`). It is legal ESM, but unidiomatic in generated code that users will read.

7. **nit** — `postgres-connection-string.ts:7-19`. Some Npgsql aliases are missing: `User Name`, `UserId`, `DB`, `PSW`, and a bare IPv6 `Host=::1`. These cases fail closed with `unsupported-key` / `unsupported-value`, so security holds, but valid Aspire/Npgsql strings that use them are refused.

8. **nit** — `packages/database/README.md`. Unrelated paragraphs and table columns in the command-store sections were reflowed by Markdown formatting, which inflates the diff.
