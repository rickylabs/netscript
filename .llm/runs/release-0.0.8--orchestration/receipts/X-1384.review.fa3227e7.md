The #1384 signout hardening holds and the latest cookie-cleanup commit is sound. One defect blocks merge: on better-auth and WorkOS, the new operator `revokeSession` route answers "not found" for a live session and leaves it active.

### Findings

1. **major — `plugins/auth/services/src/routers/v1-handlers.ts:270` (with `packages/auth-better-auth/src/better-auth-backend.ts:170`, `packages/auth-workos/src/workos-backend.ts:82`, `packages/cli/src/public/features/plugins/auth/auth-session-client.ts:66`): operator revocation reports an existing session as not found on 2 of the 3 shipped backends.**
   - **Cause:** `revokeSession` checks first with `backend.sessions.getSession({ sessionId })`. Neither the better-auth nor the WorkOS session store can look a session up by id alone. better-auth's `headersFromSessionLookup` needs a request or token, and WorkOS reads `lookup.token ?? cookie`. Both return `undefined` for every id.
   - **Result:** the handler returns 200 `{ revoked: false }` and records a `SUCCESS` audit outcome. The CLI prints `Auth session <id> was not found.` The target session stays active.
   - **Reproduced** against a real `betterAuth` instance with the memory adapter, calling the handler with a principal that holds `auth:sessions:revoke`:
     ```text
     operator revokeSession -> {"revoked":false,"sessionId":"<live id>"}
     victim session still active -> true   sessions in store: 1
     ```
   - **Regression:** on `main`, `plugin auth session revoke` against these backends failed loudly, because `revokeSession` threw `AuthBackendOperationUnsupportedError`. This PR swaps that for a false "not found" on a security operation. An operator responding to an incident would believe the id was wrong while the session stays live.
   - **Fix:** do not treat "lookup by id unsupported" as "unknown id":
     - Call `backend.sessions.revokeSession(id)` directly.
     - Map only a definite not-found (for example kv-oauth `session_not_found`) to `{ revoked: false }`.
     - Let `AuthBackendOperationUnsupportedError` surface as `AUTH_PROVIDER_ERROR`.
     - Add a better-auth (and WorkOS) operator-route test asserting the call does not report `revoked: false` for a live session.
   - The PR body's "Operator route, unknown id" drift note should also say that better-auth and WorkOS cannot revoke by id.
2. **minor — `plugins/auth/services/src/routers/v1-session-ownership.ts:131`: the same root cause makes the same-subject `sessionId` selector unusable on better-auth and WorkOS.**
   - `requireOwnedSession` always fails there, so `signout { sessionId: <own id> }` returns 401 "No session of the authenticated principal matches…". This also happens with `everywhere: true`, and for plain signout when the principal carries `claims.sessionId`.
   - Single-session signout did not work on these backends on `main` either, so this is not a regression of the security property. Only the diagnosis changes: an unsupported operation now reads like an ownership refusal.
   - Document it, or surface the unsupported error once the session is proven to be the caller's.
3. **minor — PR body, Golden rule 5 paragraph: "A worker or saga can call `revokeSession` with a service identity that holds `auth:sessions:revoke`" is unproven.**
   - `createInProcessAuthenticator` (`plugins/auth/services/src/auth-guard.ts:42`) accepts only backend sessions (bearer or cookie). It does not accept the internal service credential merged from #2166, so a worker cannot authenticate with a service identity.
   - Nothing in this PR needs background work, so this is not a golden-rule-5 violation. Correct the claim, or record composing the internal-credential authenticator as a follow-up.
4. **nit — `docs/site/orchestration-runtime/how-to/deploy.md:130`:** the text still says "exposing five endpoints" but now lists six. `auth-model.md` was updated to "six".
