Verdict: REVISE at d37654079b57807032c4fd232473b8771ad38132

The bounded KV cancellation is built well and its gates reproduce. It is blocked by two problems. A scheduled message whose originating saga ends is now silently dropped, even when the message is addressed to a different saga. And the default runner can no longer start when a host injects its own engine or runtime factory.

### Findings

1. **major** — `plugins/sagas/src/runtime/saga-delivery.ts:277` and `:215`. **Silent loss of scheduled messages.** Once the originating instance is terminal, a `schedule()` cascade is dropped, both when it is enqueued and when it falls due. This happens whatever the wrapped message's destination is.
   - The bus bridge only schedules after the transition is saved. So `[sagaComplete(), schedule(msg, '1d')]` is persisted as terminal first, and then its schedule is suppressed. A completing saga can therefore never schedule a follow-up for another saga.
   - I confirmed this with a throwaway probe outside the checkout. The probe used the PR's own runtime wiring (`createDurableSagaRuntime` + `SagaQueueScheduler` over a real KV polling queue). The definition was `.on('Finish', () => [sagaComplete(), schedule({ type: 'ReviewRequest', correlationKey: 'review-1', … }, '1d')])`. Result: **0** pending scheduled keys, where 1 was expected.
   - The drop writes no log, and the cascade span still finishes as `SUCCESS`.
   - The PR's own integration test codifies the same thing: its timer is addressed to `correlationKey: 'destination'`, yet it is cancelled when origin `order-1` completes.
   - #2109 asks that scheduled messages "expire or are deleted **within their window**" (retention). It does not ask for delivery to be cancelled at the terminal transition. This changes the public `schedule()` contract ("Deliver a wrapped message after a delay").
   - **Fix:** never suppress cascades emitted by the terminal transition itself. Then either:
     - limit cancellation to timers whose destination resolves to the originating instance (self-timers), or
     - cancel only once the originator's retention deadline (`completedAt + completedRetentionDays`) has passed.

   Whichever you choose, log or count every drop, document it on `schedule()`, and add a test showing a cross-saga schedule emitted alongside `sagaComplete()` is still delivered.

2. **major** — `plugins/sagas/src/runtime/saga-runner.ts:104-108` with `saga-delivery.ts:207-212`. **Startup regression for supported runner configurations** (found by reading the code; I did not run this one).
   - Without a `deliveryQueue`, the runner now always builds a cancellable `scheduledQueue` (KV polling).
   - `SagaQueueScheduler.start()` throws unless `bindRetentionStore` was called first. Only `createDurableSagaRuntime` calls it.
   - The supervisor's other public paths never bind it:
     - `runtimeOptions.native.engine` injected: `createDefaultRuntime` takes the `hasInjectedNativeEngine` branch, then `createSagaRuntime`.
     - `supervisor.createRuntime` supplied as a custom factory.
   - In both cases `SagaBusBridge.start()` reaches `scheduler.start()`, and startup fails with "Cancellable scheduling requires canonical state and queue cancellation." On main these configurations started.
   - **Fix:** if no store is bound at `start()`, fall back to the old native-delay path and log a warning, instead of throwing. Or only create the default `scheduledQueue` when the durable runtime path will bind it. Add a regression test for the injected-engine and custom-factory cases.

3. **minor** — `packages/plugin-sagas-core/src/runtime/saga-scheduler.ts:36,161`. **Speculative public API in core.** `SagaSchedulerStorePort.cancelCorrelation?` and `SagaScheduler.cancelCorrelation()` are new public API with no store implementation and no caller. The method only throws `notImplemented`.
   - The core `SagaScheduler` now records `instanceId` but has no `bindRetentionStore`/`cleanupRetention`. So the scheduler file named in the brief gets no retention; all of the behaviour lives in the plugin's `SagaQueueScheduler`.
   - **Fix:** either implement this for a real core store, or drop the speculative API and state the core-scheduler gap under remaining scope.

4. **minor** — `plugins/sagas/src/runtime/saga-delivery.ts:247,251`. `cancelPending!` and `this.#store!` are non-null assertions. They are only safe because `start()` validated both values earlier. `cleanupRetention()` can be called before `start()` (it is a public method), and then it throws a `TypeError`. **Fix:** narrow explicitly and return `false`, or throw a typed `SagasError`.

5. **nit** — `saga-delivery.ts` `start()`. It does not guard against a second call, so calling it twice starts a second scheduled-queue listener. Add a guard like the one in `SagaQueueDelivery.start`.

6. **nit** — The PR body says "No expensive-gate label was added", but `e2e-cli-gate` is on the PR (applied after `status:impl-eval`). If the coordinator applied it, reword the body so it stays accurate. No local paths, hostnames or token data appear in the body.

Not issues:
- The cursor and CAS design in `_pending-retention.ts` is sound: the exclusive cursor, per-key CAS, and the cursor CAS result folded into `more`.
- The visibility-recovery bound (`[...key, '']` as an exclusive start, reset when a pass reads fewer than 100) is correct, and it improves on the old unbounded scan.
