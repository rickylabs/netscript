The override is wired correctly and well tested, but the regenerated helper now crashes in existing workspaces that never set the variable. Every helper-regenerating command (`generate aspire`, `plugin install`/`remove`, `services add`/`remove`) rewrites the helper, so these workspaces pick it up silently.

### Findings

1. **major** — `packages/cli/src/kernel/templates/workspace/aspire-cli-task.ts:20` (generated `const aspireCli = Deno.env.get('NETSCRIPT_ASPIRE_CLI') || 'aspire';`)
   - **What:** The regenerated helper reads the env var at top level without checking that it has env permission. Existing workspaces still have the old grant `deno run --allow-run=aspire --allow-read …` in their workspace-owned root `deno.json`, which nothing rewrites. Regeneration is not limited to `netscript generate aspire`: `regenerateAspireHelpers` is also called by `plugin install` (public and local), `plugin remove`, `services add` and `services remove`. Any of these routine commands now silently replaces `.netscript/aspire-cli.ts`.
   - **Effect:** After that, `deno task aspire:otel` and `deno task aspire:export` fail in non-interactive runs (agents, CI) with `NotCapable: Requires env access to "NETSCRIPT_ASPIRE_CLI"`, exit 1. In a terminal they prompt instead. This hits the **default path**, where the user never set the override.
   - **Repro:** I generated the helper from this head and ran it with the old grant, env unset and stdin redirected: exit 1 with the error above.
   - **Docs and PR body understate it:** the PR body says the `deno.json` update is needed "when adopting the override". The docs say "For an existing workspace, update its two telemetry task grants once". In practice the update is needed by every existing workspace, as soon as any of those commands runs.
   - **Fix:** In the generated helper, read the variable only when permission is granted, for example `Deno.permissions.querySync({ name: 'env', variable: 'NETSCRIPT_ASPIRE_CLI' }).state === 'granted'`, otherwise fall back to `'aspire'`. Catching `Deno.errors.NotCapable` also works. Add a real-task test that runs the regenerated helper under the old grant `--allow-run=aspire --allow-read` with the env var unset, and assert it still calls `aspire`. That test should fail at this head. Then correct the docs and PR-body wording: old grants keep the default working, and only the override needs the new grant.

2. **minor** — `aspire-command-executor.ts:29,53`, `deno-aspire-agent-initializer.ts:30`, `aspire-cli-task.ts:20`, `deno-json.ts:100,102`
   - **What:** The literal `NETSCRIPT_ASPIRE_CLI` and the `|| 'aspire'` fallback appear in five places, and the executor duplicates the resolution expression between `output` and `spawn`.
   - **Fix:** Move the name into one constant (for example next to the existing scaffold constants) and add a small `resolveAspireExecutable(env?)` helper used by both CLI adapters. Interpolate the constant into the template and into the `deno.json` task strings so the name cannot drift.

   - **Fix:** Mention it in that row, or say it once in the new section.
