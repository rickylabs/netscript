### Findings

1. **major — `packages/queue/adapters/_kv-queue-dispatcher.ts:328`** — Shutdown discards the loop before draining it. Unregistering the last route clears `#loop`, so the subsequent `close()` cannot await `loop.done`; registration promises also resolve immediately. Reproduced: both `stop()` and `listen()` return while a handler remains blocked. With a short asynchronous handler, `handlerCompletedWhenStopReturns` is **false at this head**, versus **true with main’s adapter**. This violates the queue port’s graceful-stop contract and lets callers tear down handler dependencies prematurely. **Fix:** retain and await stopping loops, track in-flight work per registration, and settle shutdown only after that work completes. Add coverage for stopping both the last listener and one listener among several names.

2. **major — `packages/queue/adapters/_kv-queue-dispatcher.ts:105`** — Listener cancellation closes a database still leased by producers. `SingleKvConnection` supplies the same KV handle for writes and listening; Fedify closes that handle on abort, and `listenerStopped()` clears it. Reproduced with separate consumer/producer adapters sharing `path: ':memory:'`: enqueue a delayed message, abort the only listener while retaining the producer lease, then restart listening. The pending message disappears because reopening creates a fresh database. A caller-owned `withKv()` handle also becomes unusable after listener shutdown. **Fix:** separate listener-registration cancellation from shared database lifetime; preserve the database while leases remain and respect caller ownership. Add pending-message retention and ownership tests.

3. **minor — `packages/queue/adapters/_kv-queue-dispatcher.ts:182`** — Round-robin selection uses one counter across every queue name. Alternating messages for two names with two consumers each consistently selects one consumer per name. Reproduced consumer counts: `a=[0,4]`, `b=[4,0]`. **Fix:** maintain a cursor per queue name and test interleaved traffic.
