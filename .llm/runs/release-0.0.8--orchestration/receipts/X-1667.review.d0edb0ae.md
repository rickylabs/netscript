2. **major** — The new identity index loses a dead-letter record when a reprocessed message fails again. This is a regression.
   - **Where:** `packages/queue/adapters/kv-dead-letter-store.ts:118-135` and `packages/queue/testing/memory-queue.ts:85-89`.
   - **What:** `reprocess` re-enqueues first and only then deletes the row and its identity key. `KvPollingQueueAdapter.reprocessDlq` (`kv-polling.adapter.ts:758-782`) re-enqueues with the **same** `messageId`. If a poller claims the message and it fails again before `reprocess` commits the delete (which is likely for validation failures, since they repeat), this happens:
     - The new `append` fails its CAS on the still-present identity and returns without error, so the new record is dropped.
     - `reprocess` then deletes the old row and the identity key.
     - The message ends up in neither the DLQ nor the pending queue.
   - **Proof:** I wrote a test in a temp directory, importing the head sources. It does `append(r1)` then `reprocess(r => append({...r, failedAt: later}))` and asserts `depth() === 1`.
     - At the head, kv and memory both FAIL with Actual 0 / Expected 1.
     - On `origin/main`, both pass.
   - **Fix:** release the identity before or atomically with the re-enqueue. For example, CAS-delete the row and identity first, then re-enqueue, and restore both if `reenqueue` throws. Alternatively, have `append` take over an identity whose row is being reprocessed. Add this scenario as a regression test.
   - **Note:** the existing "failed reprocessing retains identity" test assumes re-enqueue happens before delete and will need adjusting. Postgres `reprocess` has the same ordering already, but it has no same-id requeue caller today. Fixing the port contract consistently is better than copying the pattern.

3. **minor** — Each record in KV `reprocess` now costs an extra `kv.get(identityKey)` plus an atomic commit. That is bounded by `limit`, so it's acceptable. A failed CAS `continue`s after `reenqueue` has already run, so concurrent reprocessors can each re-enqueue the same record. That is the same as before the PR, but it's worth a comment.

4. **nit** — `kv-dead-letter-store.ts:124` compares keys with `JSON.stringify(identity.value) === JSON.stringify(entry.key)`. This is correct for string keys, but bigint/Uint8Array key parts would throw or collide. The keys today are strings only.
