### Findings
1. **minor**: `packages/cli/e2e/src/application/gates/scaffold/runtime/evidence/describe-follow.ts:1-2` ↔ `describe-capture.ts:5-10` import each other. `describe-follow.ts` re-exports the capture functions, and `describe-capture.ts` imports the parser and evaluator back from `describe-follow.ts`. It works today only because neither module uses the other's bindings at top level. This is a layering smell, and a future top-level use would break it. **Fix:** move the parser and evaluator (`parseDescribeFollow`, `evaluateDescribeFollow`, `isPendingConvergence`) into their own module. Keep `describe-follow.ts` as the CLI entry and re-export.
2. **minor**: `describe-capture.ts:58-67`. `aspire start` used to have no bound. Deno now aborts it at `max(ASPIRE_CLI_START_TIMEOUT, listener ceiling)`, which is 300 s for both tiers. The Aspire CLI applies its own budget from that same knob, and the Deno timer starts before the process spawns. So the outer SIGTERM can fire first and replace Aspire's own timeout message, leaving only partial stderr. This also changes local behaviour slightly. **Fix:** set the outer abort to the knob plus a grace period (for example +30 s), so Aspire's own diagnostic wins.
3. **minor**: `describe-capture.ts:217`. `pullDetails()` always reads the fixed, cwd-relative path `.llm/tmp/e2e-image-pulls.json`. In a local run, a stale report from an earlier CI-style preparation would be reported as the current failure's pull time. **Fix:** pass the path through an argument or env var that only CI sets, or skip a report older than the gate's start.
4. **minor**: `.llm/tools/e2e/prepull-runtime-images.ts:81-118`. The SDK image inspection (`dotnet run` plus NuGet restore, 180 s timeout, no retry) is a hard failure before the suite starts. That adds a new way for the tier to fail before any product assertion runs. The NuGet cache restore limits the risk. **Fix:** give the inspection the same bounded retry, or fall back to letting Aspire pull the image.
5. **nit**: `prepull-runtime-images.ts:36-38` pulls the whole cache catalog for each tier. That includes Redis, which the runtime tiers do not use; they expect Garnet. It also ignores any per-entry `ImageTag` override. The list is derived from the catalog, but it is not exact for each tier. The author recorded the Redis/Garnet mismatch as drift.
6. **nit**: `prepull-runtime-images.ts:1` uses an inline `jsr:@std/async@1/delay` specifier, while the next line uses the import map for `@std/path`. Prefer a mapped `@std/async` entry so it stays consistent.
7. **nit**: The `prepull-runtime-images_test.ts` test "both CI tiers prepare images…" checks the workflow by searching the YAML as text. That is brittle, but acceptable as a test of how the workflow is wired.

The PR body has no hygiene leaks: no local paths, hostnames, session IDs or usage numbers. The `.llm/tmp/...` config paths it mentions are relative to the repo.
