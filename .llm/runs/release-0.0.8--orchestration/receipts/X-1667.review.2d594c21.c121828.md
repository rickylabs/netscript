Both earlier findings are fixed. But the new claim-before-requeue order turns DLQ reprocessing from at-least-once into at-most-once: a KV record is lost whenever its restore write fails, and main keeps it.

### Findings

1. **major** — KV `reprocess` can now permanently lose a dead-letter record. This is a new regression.
   - **Where:** `packages/queue/adapters/kv-dead-letter-store.ts:135-160`.
   - **What:**
     - The record and its identity are now deleted (CAS) **before** `reenqueue` runs.
     - If `reenqueue` rejects, the record is restored by a second write (`this.append(...)` or `kv.atomic(...)`). For `KvPollingQueueAdapter.reprocessDlq`, the requeue and the DLQ share one KV, so whatever made the requeue fail (KV unavailable, timeout) is likely to make the restore fail too. The restore error then replaces the original, and the record is in neither the DLQ nor the pending queue.
     - A process exit between the claim commit and the end of `reenqueue` loses it the same way. The PR body (Drift) admits there is no crash atomicity, but not that this is a step back from main, which never deletes before a successful requeue.
     - A DLQ exists so poison messages are not lost; a duplicate requeue is the cheaper failure.
   - **Proof:** I wrote a test in a temp directory, outside the checkout. It patches `DenoKvAdapter.atomic` to reject once the `reenqueue` callback has run, and the callback rejects. It then asserts `depth() === 1`.
     - At the head: FAIL, Actual 0 / Expected 1.
     - On `origin/main`: pass.
   - **Fix:** claim only the identity, never the row. That keeps the old at-least-once behaviour and the same-id re-failure fix:
     1. CAS-delete the identity key, if this row owns it.
     2. Run `reenqueue`.
     3. CAS-delete the row, using its versionstamp.

     A same-id failure during the requeue appends a fresh row with a new identity. If the callback rejects, try to re-set the identity (`versionstamp: null`); if that write fails, the row still exists and is reprocessable as a legacy row, so nothing is lost. Concurrent reprocessors may both requeue, which is the at-least-once behaviour main already has.

     Add the transient-failure case above as a regression test. The memory store's claim-first order is fine as it is: its restore cannot fail, and a crash loses the whole in-process store anyway.

2. **minor** — `reprocess` now does one extra reverse `list` per call plus a `get` and an atomic commit per row. That is bounded by `limit`, so it's acceptable.
