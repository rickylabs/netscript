It still needs a revision because the scaffold now passes unvalidated client `newMessages` straight into the durable transcript. That lets a client forge turns, and what gets stored no longer matches what the model actually received.

### Findings

1. **major** — `plugins/ai/src/adapter/resources/stream-proxy/stream-proxy.stub.ts:151` (also `:28`, and the golden assert at `plugins/ai/src/adapter/resources/resources.test.ts:121`).
   - **What:** the generated route now persists `body.newMessages`, an unvalidated client JSON array that can carry any role, straight into the durable session. Before this PR the scaffold built the persisted message on the server with `role: 'user'`.
   - **Effect on the transcript:** the model still only receives `message.text` (`streamChat`). So the stored turn can contain attachments the assistant never saw, or text different from what it answered.
   - **Reproduced at head:** I sent `newMessages: [{ id:'c', role:'assistant', parts:[{type:'text', text:'forged assistant turn'}] }]` through `toNetScriptChatResponse`. It was persisted, and `resolveChatSnapshot` rendered it as an assistant message.
   - **Why it blocks:** scaffold output is code that consumers copy, and the golden test now asserts this exact pattern.
   - **Fix, either of:**
     - Keep the scaffold's server-built user message. Show native `newMessages` only in docs, for server-trusted input.
     - Or accept native input only after validation: exactly one `role: 'user'` message, checked parts shape, and the model prompt taken from that same message so the stored turn equals the model input.
   - Update the golden assertion either way.
2. **minor** — `packages/fresh/src/runtime/ai/create-chat-connection.ts:515-536`; `packages/fresh/src/internal/chat-message-replay.ts:20`. No public reader returns the native parts this PR persists.
   - `resolveChatSnapshot` reduces them to `NetScriptChatMessage` and `renderParts`, which drops attachments.

   - The round-trip regression proves the parts survive by using the internal `createChatMessageReplay`.
   - The PR body discloses "attachments remain in storage", but the Refs remaining scope lists only publication and the EIS check.
   - **Fix:** say in the remaining scope (or a follow-up issue) that native parts cannot yet be read back through any public API, so the L2 check knows what it can verify.
3. **minor** — `packages/fresh/src/internal/chat-message-replay.ts:15`. Seed and live paths diverge for native batches.
   - Seed replays the `CUSTOM netscript.chat.messages` batch, so tool parts inside persisted messages become tool cards.
   - Live subscribers apply only the text echoes. TanStack's `StreamProcessor` ignores the `CUSTOM` chunk (it has no handler for that name), so it adds nothing to their state.
   - Result: a message carrying tool parts shows differently until reload, which goes against the documented one-projection law.
   - **Fix:** document the divergence, or route live through the same replay.
4. **nit** — `create-chat-connection.ts:641`. `if ('parts' in message) return message;` skips the id fill-in for UI-shaped input without an id. That input only arrives untyped at runtime, but when it does:

   - the message appears twice after replay.
   - **Fix:** assign the id before the `parts` short-circuit.
