### Findings

1. **major** — `packages/service/src/rate-limit/middleware/client-address.ts:59-73`, called from `rate-limit-middleware.ts`
   - **What:** `rateLimitAddressKey` treats IPv4-mapped IPv6 addresses (`::ffff:a.b.c.d`) as ordinary IPv6 and masks them to the prefix. At the default `/64` the IPv4 part sits entirely in the masked-off low 64 bits, so every mapped address gets the same key. Probe at this head:
     - `::ffff:192.0.2.1`, `::ffff:198.51.100.7` and `::ffff:10.0.0.1` all map to `0:0:0:0:0:0:0:0/64`.
     - A `Deno.serve({ hostname: '::' })` listener reports an IPv4 client as `::ffff:127.0.0.1`.
   - **Impact:** On any dual-stack bind, or behind a trusted proxy that writes mapped forms into XFF, all IPv4 clients share a single quota. One client using up `limit` gets every IPv4 user rejected with 429 for the rest of the window, which turns the anonymous-route protection into a denial-of-service lever.
   - **Tests and docs:** The new test only covers mapped forms at `ipv6Prefix: 128`, which hides the problem. The docs ("IPv4-mapped IPv6 addresses follow the IPv6 prefix policy", README:654, how-to:95) describe the behaviour without its consequence.
   - **Fix:**
     - Detect `::ffff:0:0/96` after canonicalization, convert it back to dotted IPv4, and key it as the native IPv4 address. This matches common rate-limiter practice.
     - Add a default-`/64` test where two distinct mapped addresses get independent quotas, ideally on a real `::` listener.
     - Correct the docs.
