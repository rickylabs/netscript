### Findings

1. **minor**: `packages/cli/src/kernel/adapters/secrets/installation-secret-file.ts:178-181` (`assertOwnerOnly`).
   - **What:** on POSIX, provisioning hard-fails if the directory or file has any group/world bit set. On filesystems that don't keep POSIX modes, every file reports 0777 and `chmod` does nothing. The common case is a WSL project on a `/mnt/c` drvfs mount without `metadata`. There, any project with a backend would fail at AppHost start.
   - The remedy message ("mode 0700/0600") can't be followed on such a mount. The `NETSCRIPT_INSTALLATION_SECRET_FILE` override also goes through the same parent-directory check, so there is no workaround.
   - `ensureDatabasePassword`, which this PR now matches, does not check modes, so this is a new failure mode for the same directory.
   - **Fix:** no change needed in this leaf. Record the limitation in the L4 recipe, or add it to the Windows/ACL item already deferred to the coordinator. The runtime pass should include a drvfs case if WSL is a supported dev setup.
2. **minor**: `packages/cli/src/kernel/assets/generated/aspire/helpers/generate-index-1.ts.template:56`. The comment says "Apps and tools never receive this identity". That is true of delivery: apps and tools get no environment variable or permission grant. But the file now sits inside the workspace, so any app or tool process with workspace-wide `--allow-read` can read it, the same as the DB password files beside it. This is the trade-off the coordinator chose. **Fix:** state it once in the L4 docs so the isolation claim isn't read as filesystem isolation.
