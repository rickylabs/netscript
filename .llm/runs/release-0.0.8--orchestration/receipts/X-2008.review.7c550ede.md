The L1 changes work and are well tested: one bridge file, an idempotent `CLAUDE.md` import, and Aspire using only the standard location. But on Claude Code, the default host, the generated guidance now contradicts itself about how skills are loaded, and the docs changed by this PR keep that contradiction.

### Findings

1. **major** — `packages/cli/src/kernel/assets/agent/guidance.md.template:31-38` (unchanged, but this PR makes it wrong for Claude), together with `packages/cli/src/kernel/assets/agent/repo-skills.md.template:10-12`.
   - **What:** The `AGENTS.md` section, which Claude now imports through `@AGENTS.md`, says: *"Skills are addressed by their registered name. Call the skill by name … do not read its file directly"*, then names `netscript-build`, `aspire`, `deno`, and so on.
   - After this PR, Claude Code registers only `repo-skills`. Claude Code discovers project skills from `.claude/skills/`, not `.agents/skills/`, and this repo's own Claude session lists only `repo-skills`. So a skill call such as `netscript-build` finds nothing.
   - The bridge then says the opposite: *"read `.agents/skills/<name>/SKILL.md` completely"*. A Claude agent that follows `AGENTS.md` literally has no permitted way to load any NetScript skill.
   - Before this PR the mirror registered every name, so `AGENTS.md` was accurate. This is a functional regression in skill routing on the default host.
   - The docs repeat the conflict:
     - `docs/site/ai/agent-tooling.md:122-124`: *"hosts load them through their skill tool instead of reading `SKILL.md` files directly"*. This contradicts the paragraph the PR added at :112 on the same page.
     - `docs/site/reference/ai/skills.md:33-34`: *"so the host loads it through its skill tool"*.
   - **Fix:** Make Claude's route coherent without breaking the #2007 rule that skills are addressed by name. For example:
     - Have `claude.md.template` add one Claude-specific line after `@AGENTS.md` stating that NetScript skills are reached through the `repo-skills` bridge.
     - Optionally, list the installed skill names in the bridge `description` so Claude's skill matching sends those names to it.
     - Change the "registered name / skill tool" sentences in both doc pages to cover Claude's bridge.
     - Add a test asserting that the Claude-host output (merged `CLAUDE.md` + `AGENTS.md` + bridge) gives a route a Claude agent is allowed to take.

2. **minor** — `init-agent.ts:174-195` (no longer refreshes `.claude/skills/<skill>`).
   - **What:** On existing 0.0.7 projects, `agent init` used to rewrite the mirror on every run. Now it updates `.agents/skills/` and leaves the legacy `.claude/skills/<skill>` copies untouched. Claude Code still prefers those copies, so they are now guaranteed to go stale. That is the issue's failure mode 1, made deterministic until L2 lands.
   - The PR body and docs mention that legacy mirrors are preserved, but not that they go stale.
   - **Fix:** Either ship L2 in the same release as L1, or emit a non-destructive message when legacy mirror directories are detected (for example, "legacy `.claude/skills/<name>` is no longer refreshed"). Say which in the PR body.

3. **minor** — `repo-skills.md.template:12`
   - **What:** The bridge says *"this bridge is the only Claude-local repository skill"*. That is false in any upgraded project where L1 preserves the legacy mirrors or custom skills.
   - **Fix:** Soften the wording until L2 lands, or accept it explicitly as interim debt in the PR body.
