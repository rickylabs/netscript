Verdict: REVISE at 4b318014fee8c84602d094764b7b9de9be91f6c1

The users REST/RPC gates and the gate registration are solid. But the four auth-route gates run against an auth listener the harness assembles itself, with a guard the harness picks. If someone removes authorization from the real auth service, these gates stay green. That is the exact failure #1388 was filed to catch.

### Findings

1. **major**: `packages/cli/e2e/src/application/gates/scaffold/guarded-service-probe-source.ts:61`, used by `generated-auth-checks.ts:49-60, 68-89`.
   - **What:** `behavior.auth-signout-unauthenticated`, `behavior.auth-rpc-unauthenticated`, `behavior.auth-signout-foreign-session` and `behavior.auth-session-authenticated` all probe a listener the harness builds from `plugins/auth/services/src/router.ts`. The probe attaches the guard itself: `auth: createAuthServiceGuard(registry)`. Neither the real auth service entrypoint (`plugins/auth/services/src/main.ts:75`) nor the scaffold.runtime AppHost's auth resource is ever exercised by these refusal checks.
   - **Effect:** delete `auth: createAuthServiceGuard(registry)` from `main.ts`, and signout becomes unguarded in every generated project, yet all eight new gates stay green. Nothing else catches it either: the plugin's own test fixture (`plugins/auth/tests/testing/auth-service-fixture.ts:106`) also builds its own guard. The issue's "Current surface" names this exact regression ("removed the auth service's authorization entirely would leave every gate green"), and it remains open for the auth service.
   - **Why the red controls don't cover it:** the native red controls (`generated-guarded-service_test.ts:168-176`) inject a short-circuit middleware into the probe's own listener. They prove the check can fail. They do not prove the gate catches a public auth service.
   - **Fix:**
     - Run the two anonymous refusals against the resident AppHost auth resource through the existing seam, `pluginExchangeCommand(context, 'auth', '/api/v1/auth/signout', { method: 'POST', expectStatus: 401 })`, and the same for `/api/rpc/v1/auth/signout`. That is exactly how `behavior.auth-session-unauthenticated` and `behavior.auth-me-unauthenticated` already work, and the contract supports `POST`.
     - For the cases that need a credential, either compose the listener through the real `createAuthService` entrypoint, or add a regression test asserting that `main.ts` wires `createAuthServiceGuard`.
     - Restate in the PR body which boxes are proven against the real composition and which against the recomposed listener.

2. **minor** (honest names, box 12): `runtime/behavior-gates.ts:331`.
   - **What:** every case is titled "…native sessions through generated auth and users REST/RPC". The auth half is the plugin's source router recomposed by the probe, with harness environment variables and a fake IdP `fetch`. It is not the generated project's auth service.
   - **Fix:** retitle each case per what it actually exercises, for example "plugin auth router (in-process composition)".

3. **minor** (performance): `probe-generated-guarded-service.ts:21, 46`.
   - **What:** each of the 6 new gates repeats a full scratch scaffold (`init`, `plugin install auth`, `service add users`, `generate aspire`), then mints 3 sessions. That is about 10 s per case with a warm cache, about 60 s per run, on top of the 2 scaffolds `behavior.generated-guarded-service` already does. The cases also sit in the BEHAVIOR phase even though they never use the AppHost.
   - **Fix:** after finding 1, only the credentialed cases still need the scratch project. Scaffold once and emit verdicts for each case (or reuse the `behavior.generated-guarded-service` scratch). Move them next to `GENERATED_GUARDED_SERVICE` in the pre-start block.

4. **minor** (disclosed): `probe-generated-guarded-service.ts:196-220`.
   - **What:** the users 401/403/200 checks run against a procedure the harness adds (`users.protected`), because the generated users routes are public by design.
   - **Status:** this is disclosed under Drift and the generated authenticator/authorizer is left unmodified, so it is acceptable. It should also appear in the #1388 acceptance table row for "service-api", not only in Drift.

5. **nit**: PR body.
   - **What:** the body says "No expensive-gate label is added", but the PR currently carries `e2e-cli-gate`. If the coordinator added it, the sentence is stale.
   - **Hygiene:** no local paths, hostnames or session ids found in the body.

6. **nit**: `generated-auth-checks.ts:103-118`.
   - **What:** `assertActive` hand-rolls the status, bounded-body and JSON checks instead of using a `json`-predicate `HttpExchangeContract`, which can't express "session.id equals the token" today. It's acceptable, but the double status check (`judgeHttpResponse` and then `assertEquals`) is redundant.
