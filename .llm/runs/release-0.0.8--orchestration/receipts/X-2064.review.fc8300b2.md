### Findings

1. **minor**: `packages/cli/src/kernel/adapters/secrets/installation-secret-file.ts:46-70,90-95`. **What:** every project with a backend now provisions under `~/.secrets` at AppHost start, and does so without asking. Startup hard-fails, with one generic message, if `~/.secrets` already exists with group/world bits, is owned by someone else, or the home directory cannot be written (read-only home in a CI container). The message names no path and no remedy, even though the owner directory is not hostile input. The `NETSCRIPT_INSTALLATION_SECRET_FILE` override does not help either, because `readSecret` also requires an owner-only parent directory. **Fix:** keep content and cause redacted, but give a stable remedy hint. For example: "ensure the owner secrets directory is mode 0700 and owned by you, or set NETSCRIPT_INSTALLATION_SECRET_FILE to an owner-only file in an owner-only directory". Document this behaviour in the L4 recipe.
2. **minor**: same file, lines 52-58. **What:** this does not follow the existing AppHost secret convention. `ensureDatabasePassword` in `_aspire-compat.ts.template:673` keeps secrets inside the project at `.data/aspire-secrets`. This PR keeps them outside the project, in a directory named by a hash of the installation root. That has real benefits: the secret is out of the workspace and out of reach of workspace-scoped `--allow-read`. The cost is that every throwaway scaffold (e2e runs, temp projects) leaves a `~/.secrets/netscript/<sha256>/` entry that nothing cleans up, and moving a project silently gives it a new identity. **Fix:** record the deliberate divergence and its cleanup story in the L4 docs leaf. Have the e2e teardown, or an `--owned-root`-style cleanup, remove the per-run directory.
