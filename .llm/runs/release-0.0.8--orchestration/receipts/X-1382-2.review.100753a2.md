### Findings

1. **blocker** — `docs/site/services-sdk/how-to/add-a-service.md:272-277`. The new ` ```ts ` fence is a bare object-property fragment (`auth: { public: true, … },`), which is not valid TypeScript. The PR body's Markdown evidence only covers `deno fmt` and the README checker, not the snippet check CI runs. **Fix:** make the snippet a complete statement. 2. **major** — `packages/cli/src/kernel/adapters/service/auth-policy.ts:57-60`. Renamed-plugin detection matches `plugin.PackageSpecifier === '@netscript/plugin-auth'`. No CLI path writes a `PackageSpecifier` field into a `NetScript.Plugins` entry. `appsettings-entry-builders.ts` emits only `Enabled/Runtime/HostPort/Entrypoint/Workdir/RequiresKv/RequiresDb/Permissions/…References`, and a repo-wide grep finds `PackageSpecifier` only in this file and the new tests. So after `plugin install auth --name identity`, `service add` silently emits the public opt-out, whose reason ("Authentication is not installed") is now false. That is fail-open in a supported install mode.
   - The tests hide this: `scaffolder_test.ts:74-78`, `add-service_test.ts:52` and `generated-guarded-service_test.ts:22-25` all build an appsettings shape the installer never produces.
   - The PR body claims "supports renamed plugin keys".
   - **Fix:** find auth the way installed plugins are already identified. `plugin-reference-reconciler.ts` reads each installed plugin's `scaffold.plugin.json` canonical name and the configured plugin directories. Then test against the entry the real `plugin install auth --name <x>` writes. Alternatively, drop the renamed-key claim and support, and say so explicitly. A false "not installed" reason should not ship either way.

3. **minor** — `probe-generated-guarded-service.ts:13-23` and `capability-suites.ts:100`. The gate runs `service add --name guarded --force` inside the shared runtime project and leaves the service there. It therefore becomes an AppHost resource, with a `PluginReferences: ['auth']` dependency, for every later gate (restore, start, health, quality). The neighbouring guarded-plugin gate is documented as "never an AppHost resource". This one is, and that isn't stated. **Fix:** either document it in the suite comment and accept the extra resource, or remove the service after the probe.

4. **nit** — `auth-policy.ts:52-56`. `JSON.parse(...) as {…}` without shape validation. A malformed `appsettings.json` surfaces as a bare `SyntaxError` from `service add`. This matches the existing reconciler, so it's consistency only.

5. **nit** — `auth-policy.ts:33` emits `serviceName: "…"` with `JSON.stringify` double quotes, so it depends on the generated-source formatter for house style. The identity-formatter tests assert the double-quoted form. That's harmless, but quoting single from the start would make the template and the formatted output match.
