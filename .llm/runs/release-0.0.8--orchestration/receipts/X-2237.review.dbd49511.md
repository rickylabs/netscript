2. **major: `.github/workflows/release-canary.yml:183`. A single failed production E2E now breaks later canaries.**
   - **What:** Labelling and release publication moved after `Await canary-pinned production E2E` and have no `if:`.
   - **Effect:** If the E2E for `0.0.8-canary.N` fails, the version is already on JSR (immutable) but gets no `canary:` label and no GitHub prerelease body. The next green canary then labels and publishes, and the drift check (`canary-label.ts:666`, scoped to the train) finds `canary:0.0.8-canary.N` missing and exits 1.
   - **Result:** "Record green canary pair" is skipped and "Record failed canary pair" posts a failure status for a canary whose publish and E2E both passed. This repeats on every later canary in the train until someone labels or republishes by hand. On main, labelling ran before the E2E dispatch, so this could not happen.
   - **Fix:** Keep the labelling unconditional once the publish succeeds. One option is to run the step with `if: always() && steps.publish.outcome == 'success'` and phrase the intro from the actual E2E outcome ("passed" only when `steps.e2e` succeeded, otherwise "production E2E failed" plus the link). Another is to label and create the prerelease before the E2E, then patch the body afterwards.
   - **Test:** Add a test asserting the step's `if:` (or ordering) so a failed E2E still labels.

3. **minor: `canary-label.ts:427`. One bad `Refs #N` can fail the post-publish notes step.**
