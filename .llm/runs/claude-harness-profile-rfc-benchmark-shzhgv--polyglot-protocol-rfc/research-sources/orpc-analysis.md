Analyst pass over source group `orpc`. Grounding extracts:

- `/home/user/netscript/.llm/tmp/docs/orpc-raw-01-transports-and-protocol.md` (cited as **E1 §n**)
- `/home/user/netscript/.llm/tmp/docs/orpc-raw-02-peer-protocol-and-stdio.md` (cited as **E2 §n**)

Analyzed against the current NetScript polyglot engine: tasks receive only `TASK_ID` +
`TASK_PAYLOAD` env vars; the result is the last JSON line of stdout parsed into
`TaskResult {success: boolean} + bag`; the queue path drops `TRACEPARENT`/`CORRELATION_ID` (bug
D-4); there is no progress/cancel/heartbeat/attempt channel; errors are `error: string|null` +
`exitCode`; spawn is one-shot. The JS-side `JobContext` already has
correlationId/traceparent/tracestate/reportProgress — the citizenship gap is polyglot-only.

Conformance-tier convention used below (assumed RFC-5 mapping, flag if the RFC defines it
differently): **Tier 0** = minimal baseline every polyglot task must satisfy (env in, framed stdout
out); **Tier 1** = structured protocol citizen (correlated messages, structured errors, cancel);
**Tier 2** = full duplex citizenship (streams, resume, heartbeat/reconnect policy).

## 1. Message/verb inventory with wire shapes

oRPC has **two distinct wire layers**, and the distinction is itself a finding: a
transport-agnostic *peer message protocol* (framing + correlation + verbs) wraps a
transport-agnostic *payload serialization protocol* (the `{json, meta, maps}` envelope). Each can
be adopted independently.

### 1a. Peer protocol frames (WebSocket, Message Port, stdio) — E2 §6

One frame = one JSON object with three one-letter keys (E2 §6, verbatim d.ts):

```jsonc
{ "i": "<id>", "t": <MessageType?>, "p": <payload> }
```

- `i` — correlation id, "Client-guaranteed unique identifier". Generated by a
  `SequentialIdGenerator`; concurrent calls are multiplexed over one channel by `i` (E2 §6).
- `t` — `MessageType` enum: `REQUEST = 1`, `RESPONSE = 2`, `EVENT_ITERATOR = 3`,
  `ABORT_SIGNAL = 4`. Omitted when it is the direction default (REQUEST on the request direction,
  RESPONSE on the response direction) (E2 §6).
- `p` — payload, shape keyed by `t`:

| Verb | Direction | Payload shape (verbatim keys) | Notes |
| --- | --- | --- | --- |
| REQUEST (1) | client→server | `{u, b, h?, m?}` = url, body, headers (default `{}`), method (default `POST`) | `u` shortened: origin `http://orpc` serialized as leading `/` (E2 §6 "Origin shortening") |
| RESPONSE (2) | server→client | `{s?, h?, b}` = status (default `200`), headers (default `{}`), body | HTTP status semantics reused off-HTTP |
| EVENT_ITERATOR (3) | either | `{e, d, m?}` = event (`'message' | 'error' | 'done'`), data, optional `EventMeta` | stream chunks sharing the parent call's `i` |
| ABORT_SIGNAL (4) | either | `void` (`p: undefined`) | cancellation of the call with the same `i` |

Defaults are **elided on the wire** (`t`, `m`, `s`, `h` omitted when default) — deliberate
frame-size compression (E2 §6).

**Binary frame variant:** a frame is either a UTF-8 JSON string, or a binary buffer of
`utf8(json) || 0xFF || <blob bytes>` (`JSON_AND_BINARY_DELIMITER = 255`); exactly one blob per
frame (E2 §6 "Binary framing").

**Streaming handoff rule:** if a REQUEST/RESPONSE frame's headers carry
`content-type: text/event-stream`, the body is elided (`b: undefined`) and delivered as subsequent
`EVENT_ITERATOR` frames sharing the same `i` (E2 §6 "Body ↔ header normalization"). Presence of
`content-disposition` in frame headers is the File/Blob discriminator on decode (E2 §6).

### 1b. Payload serialization envelope (`{json, meta, maps}`) — E1 §4, §5

Bodies (HTTP and peer alike) use a JSON-superset encoding:

- `json` — plain JSON with rich types down-converted (Date→ISO string, BigInt→string, …).
- `meta` — array of type annotations locating the original type by path:
  - v1: `[type: number, ...path]`, numeric codes 0–7 (bigint, date, nan, undefined, url, regexp,
    set, map); custom types must pick a unique number > 20 (E1 §4, §5).
  - v2: `[handler: string, ...path]`, e.g. `["date", "createdAt"]` — string handler keys replace
    magic numbers (E1 §5).
- `maps` — with FormData: `[...path][]` pairing file parts to positions in `json` by order (E1 §5).

Success response body = `{json, meta}`; error response body = serialized `ORPCError` (see §4).
Supported types v2: string, number/NaN, boolean, null, undefined, Date (incl. Invalid Date),
BigInt, RegExp, URL, object, array, Set, Map, Blob, File, AsyncIteratorObject (root only),
`ReadableStream<Uint8Array>` (root only) (E1 §5).

### 1c. stdio framing (third-party adapter) — E2 §2–§4

`orpc-adapter-stdio` (community, v1-only, 0.0.1): newline-delimited UTF-8 text frames, each
prefixed with the 11-byte sentinel `\x00__ORPC__\x00`. Non-prefixed lines are ignored — that is the
`console.log` isolation mechanism (E2 §2, §4 verbatim source). Frames are `.trim()`ed on send and
receive; no length prefix; text-only (binary peer frames get corrupted through
`TextDecoder` + `.trim()` — E2 §4 "Consequence worth flagging").

There is **no verb for progress, heartbeat, attempt, or deadline** anywhere in the protocol.
Progress must be modeled as an application-level `EVENT_ITERATOR` stream; heartbeat exists only as
transport keep-alive (SSE comments, §3).

## 2. Lifecycle state machine (as actually implemented)

Reconstructed from `ClientPeer`/`ServerPeer` (E2 §5–§6) and the async-iterator docs (E1 §8). The
protocol has **no named states on the wire** — the state machine is implicit in frame sequences per
correlation id `i`:

```
Unary call (per id i):
  client: open(i) → send REQUEST(i) ─────────────► server handles
  client: ◄──────────────────────── RESPONSE(i)    [terminal: resolved]
  either side, any time before terminal:
          ABORT_SIGNAL(i) ──────────────────────►  [terminal: aborted]

Streaming call (per id i):
  REQUEST(i) → RESPONSE(i) with content-type: text/event-stream, body elided
  then: EVENT_ITERATOR(i, e:'message', d, m?) *      [streaming]
  terminal: EVENT_ITERATOR(i, e:'done')              [completed]
        or  EVENT_ITERATOR(i, e:'error', d)          [failed]
        or  ABORT_SIGNAL(i)                          [aborted]
  (request bodies can also be streams, same mechanism, request direction)
```

Concrete implementation anchors:

- `ClientPeer.open(id)` returns an `AbortController` per in-flight call; cancellation of that
  controller travels as an `ABORT_SIGNAL` frame with the same `i` (E2 §6).
- `ClientPeer.close(options)` tears down every in-flight call at once; `ClientPeerCloseOptions`
  has `abort?: boolean` `@default true` — closing the transport aborts everything by default
  (E2 §6).
- `ServerPeer.message(raw, handleRequest)` returns `[id, StandardRequest | undefined]` — the server
  side is per-message driven, matching the "per-message style" WebSocket adapters
  (`handler.message(ws, message)` + `handler.close(ws)` on socket close, E1 §3).
- Server-side handler teardown: v2 async-generator handlers receive a `signal`; "When the client
  closes the connection or an unexpected error occurs, oRPC aborts the provided `signal`. Use it to
  exit loops... Put cleanup logic in a `finally` block" (E1 §8). v1 had only the `finally` block
  convention, no signal.
- Stream completion semantics are explicit and oRPC-specific: generator `return` "ends the stream
  and marks it successfully completed — This behavior is exclusive to oRPC. Standard SSE
  clients... will automatically reconnect when the connection closes" (E1 §8) — i.e. `done` is a
  protocol-level terminal, not a transport disconnect.

**What's absent:** no `started`/`acknowledged` state, no attempt counter, no lease/heartbeat state,
no server→client unsolicited verbs outside an open call. The machine is strictly
request-scoped.

## 3. Heartbeat / cancellation / deadline mechanics

### Heartbeat (transport keep-alive only)

- SSE event streams: `initialComment` (enabled by default, sent immediately "to flush headers") and
  `keepAlive` ping comment, `interval: 15000` ms in v2 "measured after the last event" (default was
  5s in v1 — deliberately relaxed in the migration) (E1 §6, §9). Mirrored symmetrically on the link
  under `toFetchRequest.eventStream` for request-direction streams (E1 §6).
- Peer transports (WS/MessagePort/stdio): **no protocol-level heartbeat**. Liveness is delegated to
  the transport (WS ping/pong is not mentioned; nothing exists for stdio).

### Cancellation

- First-class wire verb: `MessageType.ABORT_SIGNAL (4)` frame carrying the call's `i`, empty
  payload (E2 §6). Client-side surface is a standard `AbortController` from `ClientPeer.open(id)`.
- Propagated to user code in v2 as the `signal` argument of the handler generator (E1 §8).
- Transport close ⇒ implicit abort of all in-flight ids (`abort?: true` default on close, E2 §6).
- Error-code vocabulary includes `CLIENT_CLOSED_REQUEST` (499) for representing it as an outcome
  (E1 §6).

### Deadline

- **No wire-level deadline/timeout field exists** in either frame layer. The only artifacts are:
  the `TIMEOUT` (408) and `GATEWAY_TIMEOUT` (504) error codes (E1 §6), and a v2 "Timeout" plugin
  named in the migration page's new-plugin list (E1 §9) — plugin mechanics UNVERIFIED, only the
  name appears in the extracts. Deadline is a client-local concern that surfaces as an abort.

### Reconnect / resume (client policy, v2)

- WebSocket link: `connect` factory + built-in `reconnect` config — `enabled` (default false),
  `delay: info => info.attempt === 1 ? 0 : 2_000`, `maxAttempt: Infinity` ("Should greater
  than 1"; exceeding it makes `getConnectedPeer` throw), and `onClose: {enabled, delay}` for
  proactive reconnect after socket close (E1 §3).
- Stream resume: `withEventMeta(data, { id, retry })` attaches an event id + retry hint; on
  reconnect the client sends the id back and the handler receives `lastEventId`; "Unlike
  traditional SSE, the Event Iterator does not automatically retry on error" — retry is an opt-in
  link plugin (E1 §6 v1 RPCLink, §8).

## 4. Error taxonomy — retryable vs terminal representation

### The error object

`ORPCError` serialized in the same `{json, meta}` envelope (E1 §4):

- v1: `{ defined, code, status, message, data }` — e.g.
  `{"defined":false,"code":"INTERNAL_SERVER_ERROR","status":500,"message":"...","data":{}}`.
- v2: `{ defined, inferable, code, message, data }` — `status` removed from the error body ("since
  `status` was removed from errors"), `inferable` added (E1 §4, §9). Semantics of `inferable`
  beyond its presence: UNVERIFIED (not explained in the extracts). `defined` marks whether the
  error is part of the typed contract (contract-declared vs ad hoc) — inference from the field
  name and oRPC's typed-errors feature; exact doc wording not in extracts, so treat as UNVERIFIED
  nuance.
- `data` is an arbitrary structured bag and participates in `meta` typing
  (`"meta":[["bigint","data","id"]]` in the v2 example) — errors carry rich typed payloads, not
  just strings (E1 §4).

### The code vocabulary

`COMMON_ERROR_STATUS_MAP` — 23 string codes mapped to HTTP statuses, from `BAD_REQUEST`/400 through
`GATEWAY_TIMEOUT`/504, including `TIMEOUT`/408, `CONFLICT`/409, `TOO_MANY_REQUESTS`/429,
`CLIENT_CLOSED_REQUEST`/499, `SERVICE_UNAVAILABLE`/503 (full table in E1 §6). The map is
customizable per handler via `errorStatusMap` (E1 §6).

### How retryable vs terminal is represented: **it isn't, explicitly**

There is no `retryable: boolean` or error-class field. Retryability is *implicit* in
HTTP-status-shaped semantics and enforced by client-side plugins:

- `RetryLinkPlugin` (v1 `ClientRetryPlugin`) and `RetryAfterLinkPlugin` (v1 `RetryAfterPlugin`)
  decide retry behavior client-side (E1 §6 v2 RPCLink, §9). Their decision inputs (which
  codes/statuses trigger retry) are UNVERIFIED — plugin pages were not in the fetched set.
- The 4xx/5xx split plus specific codes (429 + Retry-After, 503, 408) carries the conventional
  retryable signal.

Distinct failure channels worth cataloguing:

1. Error response (RESPONSE frame / HTTP 4xx–5xx with ORPCError body) — the request was processed.
2. Stream error (`EVENT_ITERATOR` `e:'error'` with `d` payload) — mid-stream failure, terminal for
   that stream (E2 §6).
3. Transport/decode failure — `MALFORMED_ORPC_RESPONSE` ORPCError synthesized client-side when the
   link can't decode a response (proxy/gateway answered); `cause` is a `MalformedResponseError`
   carrying `.response.status`/`.response.body` (E1 §6 v2 RPCLink). The "someone else answered"
   case is a named, first-class error rather than a JSON parse crash.
4. Abort (`ABORT_SIGNAL` / `CLIENT_CLOSED_REQUEST`).

## 5. Versioning + capability negotiation

**There is none, and the consequences are documented.** Findings:

- No protocol-version field exists in either the peer frame (`{i,t,p}`) or the payload envelope
  (`{json, meta}`). Nothing in E1/E2 shows a handshake, hello, or capability exchange on any
  transport.
- The v1→v2 migration states the cost verbatim: two wire formats changed (serializer format; error
  body gains `inferable`, loses `status`) and therefore "a v1 RPC Link or OpenAPI Link **cannot
  talk to a v2 server (and vice versa)**. Deploy the upgraded server and clients together."
  (E1 §9). Lockstep deployment is the versioning strategy.
- Extension points require **out-of-band bilateral coordination**: v1 custom serializers use
  numeric `type` codes that "must be unique and greater than 20 to avoid conflicts with built-in
  types in the future", configured identically on handler and link (E1 §5). v2 replaces numbers
  with shared string handler keys ("instead of matching a magic number", E1 §9) — better
  ergonomics, still zero negotiation.
- The closest thing to a capability *hint* is the `Standard-Server` response header
  (`file` | `octet-stream`): "If the receiver mistakenly handles this payload as a regular
  (non-file) body, set the `standard-server` header to help the receiver detect the actual data
  type" (E1 §5) — a shape disambiguator for middleboxes/receivers, not negotiation.
- Method allowlisting (`allowMethods`, default `['POST','PUT','PATCH','DELETE']`, optional `QUERY`)
  is a server-local security default, not negotiated (E1 §6).

For RFC-5 this is the strongest *negative* lesson in the group: oRPC controls both ends
(TypeScript client + server generated from one contract), so lockstep is tolerable. NetScript's
polyglot workers are exactly the situation where lockstep fails — a versioned envelope and a
capability/tier declaration are mandatory (see §7-S8).

## 6. Transport + framing choices, and why

- **Three transport families only** — HTTP/fetch, WebSocket, Message Port; every other "adapter" is
  a host-framework binding on one of those. "No stdio / pipe / Unix-socket adapter exists in either
  major" (E1 §1).
- **HTTP maximizes reuse of HTTP semantics**: pathname routing, status codes for success/error
  split, `Content-Type`/`Content-Disposition` for shape, SSE for streams, FormData for files
  (E1 §4–§5). The protocol adds only the `{json, meta, maps}` envelope on top.
- **Non-HTTP transports get a single shared peer core.** `@orpc/standard-server-peer` has "no
  transport dependency at all" (E2 §6); WebSocket, Message Port, and stdio adapters are all "the
  same two-line pattern — construct a `ClientPeer`/`ServerPeer` with a `send(message)` closure,
  pump inbound frames into `peer.message()`, call `peer.close()` on disconnect. Adding a transport
  to oRPC means supplying byte/string transport for opaque frames; it does **not** mean touching
  the RPC protocol." (E2 §5). The peer protocol *models requests as HTTP-shaped objects*
  (url/method/status/headers) so the entire handler stack is transport-oblivious.
- **Framing is delegated to the transport where possible**: WS and MessagePort are already
  message-framed, so a frame is one message. Where the transport is a byte stream (stdio), framing
  had to be invented — the third-party adapter chose sentinel-prefixed NDJSON, trading binary
  support and length-prefix robustness for `console.log` coexistence (E2 §4).
- **Structured-clone escape hatch**: `experimental_ClientPeerWithoutCodec`/`ServerPeerWithoutCodec`
  operate on decoded `[id, type, payload]` tuples for transports that carry structured values
  natively (Message Port with `experimental_transfer`) (E2 §6) — codec and correlation layers are
  separable.
- **Wire thrift by default-elision**: one-letter keys, omitted defaults (`POST`, `200`, `{}`
  headers, default message types), origin shortening (`http://orpc` → `/`) (E2 §6).
- **Binary attachment without base64**: single `0xFF`-delimited blob appended after the JSON
  section of a frame (E2 §6); at the HTTP layer, FormData with `maps` paths instead (E1 §4–§5).

## 7. STEAL CANDIDATES for NetScript's protocol

Each cites the extract, maps to a pillar (interop / observability / communication / lifecycle) and
a conformance tier (assumed mapping stated in the header).

**S1. Sentinel-prefixed NDJSON stdout framing (`\x00__ORPC__\x00` pattern).**
E2 §2, §4. Pillar: interop + communication. Tier: **0**.
This is a drop-in fix for NetScript's most fragile contract — "result = last JSON line of stdout".
A sentinel prefix (e.g. `\x00NSP\x00` + protocol line) makes protocol frames unambiguous, lets
tasks `print`/`console.log` freely, is implementable in any language in ~5 lines
(`isORPCMessage`/`parseORPCMessage` are trivial, E2 §3), and keeps Tier-0 tasks at "write one
prefixed line before exit". Steal the mechanism, fix the flaws: specify UTF-8 + `\n` explicitly,
do **not** `.trim()` frame content, and declare the stdout protocol text-only (binary via files or
higher tiers) — see §8-A2.

**S2. Correlated frame envelope `{i, t, p}` with per-id multiplexing.**
E2 §6. Pillar: communication. Tier: **1** (envelope), Tier 2 (multiplexing).
A single envelope of (id, type, payload) is the minimum viable structure for everything RFC-5
needs: multiple logical messages (progress, log, result, heartbeat) over one stdout pipe,
correlation with `TASK_ID`, and future long-lived workers running concurrent tasks over one
channel. Steal the shape; use readable key names unless measurement shows frame size matters
(NetScript frames are small and low-rate, unlike oRPC's RPC fan-out).

**S3. `ABORT_SIGNAL` as a first-class message type sharing the call id.**
E2 §6; v2 handler `signal` in E1 §8. Pillar: lifecycle. Tier: **1** (receive+ack semantics),
with the SIGTERM/SIGKILL escalation staying as the Tier-0 fallback.
Cancellation as an in-band frame (host→task on stdin) rather than only a POSIX signal gives
polyglot tasks a portable, Windows-safe, language-idiomatic cancel path, and mirrors oRPC's
pairing of wire frame ↔ local `AbortController`/`signal` handed to user code. Also steal the
teardown default: channel close implies abort of all in-flight ids (`abort?: true` default,
E2 §6).

**S4. Tri-state stream events `message | error | done` with terminal semantics distinct from
transport close.**
E2 §6; E1 §8 ("marks it successfully completed... exclusive to oRPC"). Pillar: observability +
lifecycle. Tier: **1** for the result/error terminal frames; Tier **2** for progress streams.
NetScript progress events should be `EVENT`-typed frames sharing the task id, with an explicit
`done`/`error` terminal so "process exited" and "task completed" are decoupled. This is exactly the
distinction NetScript currently lacks (exit code ≈ outcome). It also gives polyglot tasks parity
with JS `JobContext.reportProgress`.

**S5. Structured error object: `{code, message, data}` + a small closed code vocabulary + custom
status/code map.**
E1 §4, §6 (`COMMON_ERROR_STATUS_MAP`), §9. Pillar: lifecycle (error management). Tier: **1**.
Replace `error: string|null` with an ORPCError-shaped object. Steal the string-code vocabulary
idea (subset it: NetScript needs maybe 8–10 codes — INVALID_PAYLOAD, TIMEOUT, CANCELLED,
RESOURCE_EXHAUSTED, INTERNAL, UNAVAILABLE...), the typed `data` bag for machine-readable detail,
and — improving on oRPC (§8-A4) — add an **explicit `retryable` flag or code-class rule** so queue
providers don't have to infer retry semantics from HTTP-ish numbers.

**S6. Transport-agnostic peer core / ports-and-adapters split.**
E2 §5 ("Adding a transport... does not mean touching the RPC protocol"), E2 §6 (peer package has
no transport dependency). Pillar: interop (architecture). Tier: spec-level principle covering all
tiers.
This is the strongest architectural steal and matches RFC-5's stated "port/adapter packages" goal:
define the NetScript worker protocol as a pure codec + state machine package
(`@netscript/task-protocol`?) whose only I/O contract is `send(frame)` + `onFrame(frame)` +
`close()`; stdio, HTTP callback, WS, and future transports become tiny adapters. The stdio adapter
being a ~100-line third-party shell over the peer core (E2 §5) is proof the pattern keeps adapters
cheap — including for community-written language SDKs.

**S7. HTTP-shaped internal message model reused off-HTTP.**
E2 §6 (`SerializedRequestPayload {u,b,h,m}` / `SerializedResponsePayload {s,h,b}` + header-driven
body semantics). Pillar: interop + communication. Tier: 1–2 design choice.
oRPC reuses url/method/status/headers as the lingua franca on every transport, which lets one
handler stack serve all of them and reuses universally-understood semantics
(`content-type`, `content-disposition` as blob discriminator). For NetScript — which already has
an oRPC/zod workers HTTP surface — modeling the polyglot channel's request/response payloads with
the same shapes means the *same contract schemas* can validate both the HTTP surface and the
subprocess wire, closing the polyglot/JS citizenship gap with one vocabulary. Evaluate against a
leaner task-specific payload; the steal may be partial (headers as the metadata carrier for
traceparent/tracestate/correlation-id — directly fixing D-4 by putting trace context *in the
frame*, not just env, so requeues/retries re-propagate it).

**S8. The versioning lesson, inverted.**
E1 §9 (v1↔v2 hard break, "Deploy the upgraded server and clients together"), §5/§9 (numeric →
string handler keys). Pillar: interop. Tier: **0** (mandatory from the first frame).
Steal the *failure*: because oRPC shipped no version field, its only upgrade path was a flag-day
break. NetScript's first protocol frame (or an env var, e.g. `TASK_PROTOCOL=nsp/1`) must carry a
protocol version, and the host should advertise supported versions/capabilities to the task (env)
with the task echoing its chosen version/tier back in its first frame — cheap negotiation oRPC
never built. Also steal the micro-lesson: string-keyed extension points, never magic numbers
(the v2 migration explicitly fixed this, E1 §9).

**S9. Keep-alive comment + `initialComment` flush pattern, with tuned defaults.**
E1 §6 (`initialComment` enabled/`''`, `keepAlive` 15000 ms "measured after the last event"), §9
(default relaxed 5s→15s). Pillar: observability + lifecycle. Tier: **2**.
For long-running polyglot tasks, a periodic no-op heartbeat frame (only when no real event has
been sent within the interval) lets the host distinguish "alive and working" from "hung", enabling
lease renewal for queue providers. oRPC's numbers (15s, after-last-event) are a field-tested
starting default; the initial-flush trick maps to an immediate `started`/hello frame so spawn
success is observable before first output.

**S10. Resume tokens: `lastEventId` + `withEventMeta({id, retry})`.**
E1 §8. Pillar: lifecycle. Tier: **2**.
For re-run/retry of interrupted streaming tasks: events may carry an id; on re-spawn (attempt N+1)
the host passes the last seen event id (env or hello frame) so a resumable task can continue
instead of restarting. Pairs naturally with the attempt-number info NetScript wants to expose.
Adopt only at Tier 2 — it requires host-side event journaling.

**S11. Client-side reconnect policy surface as configuration shape.**
E1 §3 (`reconnect: {enabled, delay(info.attempt), maxAttempt, onClose}`). Pillar: lifecycle.
Tier: **2** (long-lived worker mode).
When RFC-5 grows persistent polyglot workers (beyond one-shot spawn), oRPC's v2 reconnect config is
a clean, minimal policy vocabulary (attempt-indexed delay function, max attempts, proactive vs
lazy) reusable for the host's respawn/backoff policy — and consistent with queue retry policy.

**S12. `MALFORMED_ORPC_RESPONSE`-style named decode failure.**
E1 §6 (v2 RPCLink). Pillar: observability + lifecycle. Tier: **1**.
When the host cannot parse a task's protocol frame (or a Tier-0 task's final line), synthesize a
distinct structured error (`MALFORMED_TASK_OUTPUT`) carrying the raw captured output as `cause`
data — instead of today's undifferentiated parse failure. Cheap and high diagnostic value.

## 8. Anti-patterns to avoid

**A1. No protocol version or negotiation on the wire.** Direct consequence documented in E1 §9:
total v1↔v2 incompatibility, lockstep deploys. Fatal for a polyglot ecosystem where task SDKs in N
languages upgrade at different speeds. (Mirror of S8.)

**A2. Text-only, trim-mutating, unlength-prefixed stream framing.** The stdio adapter runs binary
peer frames through `TextDecoder` + `.trim()`, so "binary payloads are lossy/corrupting on this
transport. There is also no length prefix — recovery depends on newline integrity" (E2 §4). If
NetScript adopts NDJSON framing (S1), the spec must forbid binary in frames, forbid content
mutation (`.trim()` of payload), and define desync recovery (drop-to-next-sentinel).

**A3. Magic-number extension registries requiring bilateral out-of-band coordination.** v1's
numeric serializer `type` (`unique and greater than 20`) forced both sides to agree on unregistered
numbers; v2 had to break the wire to fix it (E1 §5, §9). Use string keys and a registry section in
the RFC from day one.

**A4. Retryability left implicit in status-code folklore + optional client plugins.** No
`retryable` marker exists; retry semantics live in link plugins whose policy is external to the
protocol (E1 §6, §9). For a queue-backed system, retry classification must be normative in the
error object, or providers will diverge.

**A5. No deadline propagation.** Nothing on the wire carries a deadline/timeout budget; timeouts
exist only as an error code and a client plugin (E1 §6, §9). NetScript tasks should receive their
deadline (env/hello frame) so they can self-limit and checkpoint rather than being killed blind.

**A6. Heartbeat only at one transport (SSE comments), absent from peer transports.** Keep-alive is
a fetch-adapter option (E1 §6); WS/MessagePort/stdio peers get nothing, so a hung server is
indistinguishable from a slow one off-HTTP. NetScript should put heartbeat in the protocol (S9),
not the transport.

**A7. Feature-pair blind spots: `experimental_transfer` × Event Iterator metadata.** Enabling
structured-clone transfer silently breaks event metadata ("doesn't support all data types such as
Event Iterator's Metadata", E1 §2). Lesson: every optional protocol feature must state its
interaction matrix with the others; RFC-5's tiered conformance needs per-tier feature-interaction
rules.

**A8. Whole-payload memory buffering with a documented cliff.** "File and Blob are buffered in
memory by default"; ">100 MB use a dedicated upload solution... oRPC does not support chunked or
resumable uploads" (E1 §7). NetScript task payloads/results over the protocol should have a
normative size bound, with a spillover convention (file path handoff) instead of a docs-only
warning.

**A9. Single-blob-per-frame limitation baked into the codec.** The binary framing carries "exactly
one blob per frame" (E2 §6) — an invisible constraint that surfaces as FormData re-encoding
gymnastics (E2 §6 body normalization). If NetScript ever adds binary attachments, decide the
multiplicity rule explicitly.

**A10. Silent drop of non-conforming lines with no diagnostics channel.** The stdio adapter drops
every non-prefixed line (E2 §4) — correct for isolation, but combined with no logging verb it means
misframed protocol output vanishes. NetScript should capture non-frame stdout/stderr as task logs
(observability pillar) and count/report dropped-frame parse errors (pairs with S12).
