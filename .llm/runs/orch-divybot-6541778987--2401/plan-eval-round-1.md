**Blocker 1: the start/follow ordering decision is left open, and it forces rework.** The plan says to "inspect subscribe/start ordering during implementation; if necessary arm follower before start". The plan-gate does not allow an open decision that would force rework to be deferred. The facts needed to decide are already in `research.md`: `WatchAsync` sends the current snapshot first, so a follower's first record is the resource's current state. On a resident AppHost, `<configKey>-cli` keeps the terminal state and exit code from its previous run. That makes both unlocked options wrong as written:
- **Start, then follow, take the first terminal record.** If `resource start` returns before the state update is published, the runner reads the previous run's exit code. That can mean a false success, then stopping the resource and deleting the request file while the real run is still going.
- **Follow before start, where "armed" means the process has spawned.** If the follower connects after a fast run has finished, its first record is that run's terminal state. A "skip until a nonterminal transition" rule then discards it and waits until the deadline, ending in a false timeout.

Required fix: lock the sequence in `plan.md` now. Spawn the follower and wait for its first record (the initial snapshot) within the operation deadline. Only then issue `resource start`. Accept a terminal record with a numeric exit code only after a nonterminal record has been seen following that start. Name the regression fixtures: a stale prior terminal record followed by a new run, and a fast run whose terminal record arrives right after the initial snapshot.

**Blocker 2: the negative-control and reaping proof is not specific enough to be checked.** "Negative control restores old polling and must fail" does not say which test or gate fails. The polling guard is "only if needed", and `research.md` notes that its current scope misses the DB runner. Required fix:
- Name the assertion that fails when the old loop is restored. For example: a runner test whose fake executor records calls and requires exactly one `describe <resource> --follow` stream and zero snapshot `describe` calls while waiting for completion. Alternatively, commit to widening `check-aspire-resource-polling` to shipped CLI source and show that the restored loop is flagged.
- Name the reaping controls for early return, timeout, abort and malformed input. Each must assert that the child was killed, its status was awaited and stderr was drained.
- Make sure reaping cannot outlive the deadline: after a bounded grace period with SIGTERM, escalate to a forced kill, then await status.
